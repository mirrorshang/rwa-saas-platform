### 首版发行模式的批准前提（R-05）

**V1.0按合法适用的持续认购、事前批准的基础配售设计**。M05-F011（集中募集）、M10-F009（部分认购调整）、M12-F009（部分配售）、M12-F010（集中配售）当前归属V2.0。**若确定的首发Instrument或法域必须集中募集、批次或部分配售，须在V1.0整体冻结前重新审核这些ID及必要依赖**，不能用“这些功能属于V2”规避法律要求，也不能自行将其加入已批V1。

## 三、V2.0与V3.0的具体边界

**V2.0：22项。** 包含M14-F001～006（受控申请、受让资格、许可、对价结算、名册及Token同步、纠纷纠正；**不默认公开交易所**），M15-F001～007（多Issuer高级White-label品牌/域名及授权运营、退出交接），以及企业SSO、实施与服务工单、专业协作、集中募集/部分订单/批次配售和营销消息偏好等增强。V1基础门户、合约级合法转让限制、资金退款/对账和基本通知**不能推迟至V2**。

**V3.0：20项。** 包含M16-F001～007（商业Open API/SDK开发应用、授权、发行认购API、Webhook、Sandbox、文档与用量等），复杂资产组合、多链合约/升级、动态定价、复杂大额/超额认购、法币多通道、专业服务商市场/竞价、CRM分析、复杂公司行动、低代码规则/流程、预测BI、安全自动化、服务商智能选择等。均仍需未来单独制定详细PRD/开发排期/法域门。

**待规划TBD：5项（正式编号保留）**：

| 功能ID | 功能 | 为什么不是V3必交 |
|---|---|---|
| **M08-F010** | 高级推荐及个性化营销 | 需确认真实商业价值、客户诉求及数据边界 |
| **M09-F009** | 跨机构共享KYC数据网络 | 不可默认跨租户敏感数据共享；法律责任需独立审核 |
| **M14-F007** | 公开订单簿撮合及AMM | 非首期战略目标，涉及交易场所/流动性监管与另行立项 |
| **M15-F008** | 多级代理经销管理 | 新商业层级和权限法律边界未形成批准方案 |
| **M16-F008** | 开发者应用商店 | 不是商业Open API基本交付所必需，需要独立生态验证 |

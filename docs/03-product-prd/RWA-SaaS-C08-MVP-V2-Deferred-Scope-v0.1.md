## 1. 本文件目的

本文件把 C08-R2 当前 MVP 必须先完成的产品范围，与因复杂度、依赖或完整业务规则尚未成熟而延后的能力分开，避免 MVP 为追求多资产覆盖而过早引入复杂字段、角色、审批和特殊业务引擎。

本文件属于 C08-R2 的产品设计及 UI 实施顺序，不是对原 193 项功能的重新分配，也不替代 Master PRD v0.2、Frozen 文档、DEC 或 SCOPE。

## 2. MVP 范围原则

1. **先完成最常见、可验证的基础闭环。** 先让企业能够完成房地产资产建档、权益结构配置、发行方案配置、发行准备及模拟/受权发布流程。
2. **底层保留多资产扩展，不等于 MVP 同时实现所有资产模板。**
3. **不同资产类型必须独立模板。** 不允许将房地产字段简单改名后套用于债权、股票/股权、实物或衍生品。
4. **MVP 不做企业内部多成员分权。** 一个企业操作账号即可完成当前 MVP 流程，不增加内部审核人。
5. **简化页面不等于删除关键业务数据。** 发行数量、Token 数量、Token 单价、权益容量、剩余额度及 Token 映射必须被明确表达。
6. **文件融入业务流程。** MVP 不设置独立文件中心作为必经入口，但真实文件上传、版本、关联和披露控制仍然是必要能力。
7. **生产边界继续独立。** Free Sandbox 仅模拟；Standard 订阅、KYB、法律适用条件、Provider、Signer、资金及链上生产 Gate 不得互相替代。

## 3. MVP / V1 当前交付范围

### 3.1 企业账号与权限

| 能力 | MVP 要求 |
|---|---|
| 企业操作账号 | 每家企业一个操作账号，满足当前单人操作闭环。 |
| 企业成员邀请 | 不建设。 |
| 企业内部角色 | 不建设多角色体系。 |
| 内部审核人员 | 不设置独立审核人员。 |
| 内部审批流 | 不建设提交/审核双人流程。 |
| 细粒度权限配置 | 延后至 V2.0。 |
| 个人账号安全 | 仍按现有登录、安全与账号规则处理；单账号不等于降低身份验证要求。 |

本项只简化发行企业租户内部的人员与审批模型，不删除平台后台依法或按商业运营需要执行的租户管理、安全支持及生产准入职责。

### 3.2 资产管理与资产模板

| 能力 | MVP 要求 |
|---|---|
| 多资产底层模型 | 保留可扩展结构，不把底层数据模型写死为单一房地产结构。 |
| 房地产资产模板 | 当前优先开发并开放。 |
| 其他资产模板 | 当前不开放独立建档模板，按后续版本规划。 |
| 资产基础信息 | 按房地产资产特性设计独立信息结构。 |
| 权属及法律证明 | 在资产创建/详情流程中上传、版本化并关联。 |
| 资产运营信息 | 仅纳入当前房地产 MVP 明确需要的字段；复杂运营与特殊场景另行评审。 |
| 字段规则 | 每个字段明确必填、选填、条件必填、自动计算及校验方式。 |
| 投资者展示 | 区分企业内部资料与允许向投资者展示/披露的资料。 |

房地产资产模板的详细产品设计已在 R2-02 完成并审核通过，是当前 MVP 唯一已完成详细设计的资产类别模板。其他资产类别模板尚未完成，必须按各自资产特征独立设计；本文件不把房地产字段套用于其他资产类别。

### 3.3 权益结构

| 能力 | MVP 要求 |
|---|---|
| 权益结构独立管理 | 保留独立导航与业务对象，不把权利条款混入资产基础信息。 |
| 与资产关联 | 一个资产可以关联多个权益结构。 |
| 拆分与独立引用 | 权益结构可按明确权利范围拆分，并在发行方案中独立引用；拆分规则需完成详细设计。 |
| 权利定义 | 至少能清楚表达当前 MVP 允许的权利内容、权利范围、期限/限制及有效文件引用。 |
| 容量及额度 | 必须表达总容量/上限、已占用或预留数量、剩余可发行额度及本轮最大可发行量。 |
| Token 映射 | 明确权益单位与 Token 单位之间的映射关系，不默认所有权益 1:1。 |
| 复杂权益 | 多层级、复杂优先顺序、复杂收益瀑布、混合权利组合等不纳入当前 MVP，后续版本单独评审。 |

R2-03 的权益结构详细产品设计已完成并审核通过。MVP 已批准且仅包含三类权益结构：**Equity、Debt、Income Participation**；Rights Capacity Pool、容量计算、发行方案预留与释放、固定 Token 映射、版本快照、状态和异常规则均已形成 UI-Ready 规格。发行方案模块后续应直接引用这些已完成规则，不应将其重新列为待设计事项。更复杂的多层级/混合权利、复杂收益瀑布等能力仍延后。

### 3.4 项目管理、发行方案与发行准备

| 模块 | MVP 交付要求 |
|---|---|
| 项目管理 | 系统自动创建/关联 Project；企业查看项目概览、关联资产/权益结构、发行方案轮次及状态，不重复手动创建空项目。 |
| 发行方案 | 配置一轮具体发行，包含发行数量、Token 数量、Token 单价、认购币种、认购窗口、限额、参与条件和披露等必要信息。 |
| 发行准备 | 汇总本轮信息、检查必填资料与规则、预览投资者展示页、确认文件版本与企业声明，作为发行前最终准备入口。 |
| 文件管理 | 文件上传、版本、关联和可见性嵌入资产、权益结构、项目、发行方案及发行准备。 |
| 导航 | 一级「资产与发行」；二级为「资产管理」「权益结构」「项目管理」「发行方案」「发行准备」。 |

项目管理、发行方案和发行准备保留不同职责：项目管理关注项目整体组织与进度；发行方案关注某一轮具体参数；发行准备关注发布前完整性、预览和最终确认。

### 3.5 环境与发行边界

- Free Sandbox：允许使用模拟数据演练资产、权益结构、项目、发行方案及发行准备；不得产生真实资金交易、真实链上发行或真实投资者权益。
- Standard：提供正式商业订阅权益；真实发行仍须完成适用 KYB、具体资产/权益/Offering 条件、法域及外部合法主体要求，并通过原有生产准入门。
- 订阅状态不得直接作为真实发行成功、真实资金到账、法定登记完成或 Token 已上链的证明。
- Provider、Signer、网络、合约部署及真实资金/Token 操作继续按既有 Draft/Open 决策门管理。

## 4. V2.0 延后范围

### 4.1 企业组织与权限

- 企业多成员及成员邀请/停用；
- 多角色与角色权限配置；
- 页面、数据、项目和发行方案级细粒度访问控制；
- 企业内部提交、审核、复核和批准流程；
- 高风险操作职责分离及内部审批记录；
- 与多角色配套的通知、待办、审计和异常处理。

### 4.2 多资产模板扩展

| 资产模板候选 | 当前状态 | 后续设计方向 |
|---|---|---|
| 房地产 | MVP；R2-02 详细设计已完成 | 使用已完成的房地产资产模板设计；后续进入 Project/Offering 及发行流程设计与开发。 |
| 债权相关资产/标的 | 延后 | 独立设计债务人、债权来源、偿付安排、担保/增信及相关证据字段；具体法律权利仍由权益结构表达。 |
| 股票/股权相关资产/标的 | 延后 | 独立设计发行主体、股权类别、股东/登记关系及适用公司文件；不得把资产标签直接当作股东权利。 |
| 实物资产 | 延后 | 独立设计资产识别、批次/序列、保管/托管、权属及交付/赎回证据。 |
| 衍生品及其他特殊类别 | 长期扩展候选，版本未定 | 需独立评估标的、合约关系、计价、结算、保证金/风险及法律适用性，不预先承诺纳入 V2.0。 |

上述模板是产品字段与业务流程的独立设计方向，不等于已获准在任一法域真实发行该类资产或金融工具。

### 4.3 复杂房地产与复杂权益

- 在建项目、开发阶段、分期建设及复杂工程进度管理；
- 多物业、多 SPV、多层持有结构及组合资产；
- 复杂物业运营、租约、现金流和多方分账模型；
- 多层级权益、优先/劣后结构及复杂收益瀑布；
- 可转换、附条件、混合或多维权利组合；
- 复杂估值、NAV、重估及自动触发规则；
- 复杂赎回、退出、清算和实物交付流程。

这些能力需要根据实际客户、法律结构和业务样本独立评估，不能因底层模型可扩展就直接纳入 MVP。

### 4.4 高级项目与发行能力

以下项目如需进入 V2.0，应另行定义范围与审批，不作为本文件自动承诺：

- Project 的高级组织、跨资产组合和复杂关联；
- 一个发行方案关联多个资产/多个权益结构的高级组合配置；
- 多轮发行之间复杂额度调拨、优先级及冲突协调；
- 高级投资者资格策略、复杂限额和条件化发行；
- 高级投资者披露、文件协作及多方签署流程；
- 复杂收益/使用权益的计算、分配及履约引擎。

## 5. MVP 与 V2.0 边界总表

| 领域 | MVP / 当前优先 | V2.0 / 后续 |
|---|---|---|

| 企业内部审核 | 无独立审核人、无内部双人审批 | 多角色审核、复核、职责分离 |
| 资产模板 | 房地产模板 | 债权、股权/股票、实物等独立模板 |
| 衍生品 | 不在当前 MVP | 长期候选，版本待定 |
| 房地产复杂场景 | 常见基础场景 | 在建、组合物业、多 SPV、复杂运营 |
| 权益结构 | R2-03 已完成：Equity、Debt、Income Participation 三类；容量池、Token 映射、版本/状态/异常规则 | 多层级/混合权益、复杂优先级与收益瀑布 |
| Project | 系统自动创建/关联及基础项目视图 | 高级项目组合与复杂组织能力 |
| Offering | 单轮发行的基础参数配置 | 多资产、多权益组合及复杂轮次协调 |
| 发行准备 | 完整性检查、投资者预览、企业确认 | 多角色审核、复杂外部签署与高级审批 |

| Token 映射 | 明确数量、单位、价格与权益映射 | 复杂多 Token、多链、多层映射 |
| 生产执行 | 继续受既有生产 Gate 限制 | 仍需独立技术、法域及运营批准，不因版本升级自动开放 |

### 5.1 R2-04 MVP投资者资格简化（2026-11-04新增批准范围）

- 投资者只有在KYC**核验通过且有效**时自动取得当前MVP的基础认购资格；不把“KYC资料已提交/流程已发起”误作通过。
- Issuer的Offering配置不建设独立投资者资格配置、不按自然人/机构或地区细分设置企业准入规则、不维护Offering专属白名单或逐人内部审批。
- 下一阶段仍须由系统执行必要的AML/制裁/法域生产限制、当前可售状态、必要签署、余额和订单保护；这些不是企业二次资格审核。如实际法律要求更严格的适格要求且MVP无法满足，对应真实发行必须Fail-Closed。
- 对应的Offering专属资格分类、企业名单/邀请、地区受众及资格审批、复杂持有/投资上限策略等，已放入[V2.0需求池 §3.6](RWA-SaaS-V2-0-Requirements-Backlog-and-Planning-Pool-v0.1.md)。
- 原正式ID M09-F005/F007/F008、M19-F003仍按DEC-017的V1版本归属保留，存在产品实施深度/版本映射冲突，须单独DEC处理；不因本次MVP交互简化而擅自改动193项主表。
- 详细决策记录：[R2-04分批决策记录](RWA-SaaS-C08-R2-04-Project-Offering-Token-Decision-Log-Draft-v0.1.md)。

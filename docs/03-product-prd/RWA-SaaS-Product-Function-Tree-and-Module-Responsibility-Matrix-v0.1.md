## 1. 产品架构总览与编号

产品服务的三条商业交付线：**Issuer SaaS（发行机构工作台优先）**、**White-label**、**Open API/SDK**；配套发行机构自有投资者门户及 SaaS 平台管理。全球产品设计，不默认为所有市场均可合法启用具体金融活动。投资者主要由发行机构自行拓展；不默认建设 SaaS 厂商自营全球资产聚合市场或公开二级交易场所。

| 一级能力域 | 模块 | 数量 |
|---|---|---:|
| A. SaaS 客户与平台治理 | M01–M03 | 3 |
| B. 资产与发行 | M04–M07 | 4 |
| C. 投资者与认购 | M08–M12 | 5 |
| D. 发行后管理 | M13–M14 | 2 |
| E. 商业产品扩展 | M15–M16 | 2 |
| F. 共享基础能力 | M17–M22 | 6 |

## 3. 核心对象模型及 Issuance Project / Offering 关系

### 3.1 关键对象

Tenant / SaaS Customer → Organization / Legal Entity → Asset、Instrument、Issuance Project → Offering → Investor、Eligibility、Subscription → Payment / Reconciliation → Allocation / Register 与 Token / Chain Transaction → Lifecycle / Transfer。

上述为**逻辑关联**，不是单一线性事务或数据库外键设计；Asset 与 Instrument、Instrument 与多个 Offering 的精确基数应结合首发金融工具细化。

### 3.2 已确认关系

1. **Project 是发行项目管理容器与工作台核心入口**：关联资产、金融工具、团队、文件、专业审查、多个发行轮次及后续存续期事项；自身有独立项目状态。
2. **Offering 是一次具体发行/募集安排**：独立保存条款版本、数量/价格/时间窗口、资格与支付条件、投资者认购、配售及状态；具有独立轮次身份。
3. **一个 Project 可关联多个 Offering**；首条业务闭环可优先支持“一个项目、一轮发行”，但数据模型不应限制未来多轮。
4. **Asset ≠ Instrument ≠ Project ≠ Offering ≠ Token ≠ Register**。投资者实际法律权利、持有人权威登记以及 Token 的地位必须依具体金融工具和法律安排界定。
5. 具体待决：一个 Offering 是否可关联多种 Instrument；一个 Asset 对应多少 Instrument；后续 Offering 是否复用 Token 合约或另行发行；登记及 Token 操作的法律先后顺序。

### 3.3 Offering 发布与变更控制

- 发布前需核对组织与业务授权、金融工具与文件完整性、必要审批、投资者准入规则、支付和外部服务设置，以及适用的法律/合作方上线门槛。
- 条款、披露、资格规则、价格、认购窗口等关键内容应版本化，记录生效时间及审批证据。
- 变更后必须识别已提交、审核中、已付款、已配售等在途认购，定义通知、重新确认、保留旧版本或受控取消/退款等适用路径；具体规则留待第 04 份流程规格与首发工具详细 PRD。
- 不能把“文件上传完成”或“配置完成”当作自动获准发行。

## 5. PAY-001｜投资者认购的链上稳定币支付优先

### 5.1 已确认产品方向

- 认购支付**主要面向加密货币**，优先支持指定区块链上的 **USDT、USDC 等稳定币**。
- 法币及其他数字资产支付可预留扩展，不是首个支付场景的强制交付范围。
- 支付币种与链上发行出来的 **RWA Token 是不同的资产/业务对象**，不得混淆。
- 每个 Offering 按适用授权配置可用网络、稳定币、币种合约地址/精度、计价规则、付款金额、有效期及收款安排；不能仅按“USDT”名称判断任意合约资产有效。

### 5.2 默认业务流程

认购申请与必要审核 → 明确适用条款及支付要求 → 提供经授权的网络/稳定币/收款地址等支付信息 → 投资者以外部钱包转账 → 监测交易及确认/最终性 → 到账事实识别 → 与 Subscription 匹配并对账 → 按获批准 Offering 规则处理配售、权威登记和 RWA Token 操作。

此为示意依赖，不提前决定配售、登记、Token 和法律交割在所有金融工具下的固定顺序。**链上转账广播 ≠ 网络最终性 ≠ 资金已可用/已对账 ≠ 配售完成 ≠ 登记完成 ≠ Token 交付或合法权益交割完成。**

### 5.3 支付异常与退款

至少考虑：错误网络、错误合约/非允许币种、金额不足/超额、分批到账、重复交易、无可匹配订单的入账、支付超时/未知、链上重组、服务商不可用、收款方或退款地址异常、资格失效、Offering 取消及部分退款。退款必须区分申请、授权、执行中、交易确认、到账核对、失败和未知状态；防止重复支付或退款。

### 5.4 收款钱包与责任

**优先推荐**发行机构或经适用法律/合同认可的托管、支付等服务商管理真实收款钱包及必要私钥。SaaS 提供付款信息、链上监测、状态编排与对账，**不默认自行收取、持有或控制投资者资金**。生产收款、退款执行权限、Gas/费用、稳定币发行人风险及钱包安全责任须在适用市场、合作方和法律意见下另行明确。

### 5.5 模块协同

- M05 Offering 定义允许的链、稳定币、条款和支付限制；
- M08 投资者门户展示支付信息、外部钱包支付及进度；
- M09 按适用规则完成资格及相关地址风险控制；
- M11 持有支付/到账/对账/退款的业务状态及外部权威引用；
- M12 根据获准配售及登记规则记录权益，不以稳定币到账直接替代；
- M07 负责发行的 RWA Token 合约与链上执行，而非支付的 USDT/USDC；
- M22 负责 RPC/链上事件、钱包、支付或托管方技术接入；
- M13 可在后续按金融工具和责任安排规划以稳定币进行收益/偿付，但本条不构成生产付款授权。

**未决定**：首发链/币种/合约、收款地址方案、钱包控制人和对账权威来源、是否允许分批付款、稳定币支付服务商、退款手续费与责任、真实支付许可与生产启用。

## 8. 首条 Issuer SaaS 业务闭环的验收场景（建议测试基线）

1. SaaS 客户取得授权，创建可隔离的机构工作空间与成员权限。
2. 创建一份 Asset、一个 Instrument、一个 Issuance Project 及一轮 Offering；能够查询并区分对象。
3. 形成文件、条款版本及必要审批；未过发布门槛时不能误发布。
4. 投资者在发行方获授权门户访问 Offering，完成必要身份核验、资格判断和条款确认。
5. 认购申请独立生成，不提前宣称已付款或获配售。
6. 在选定测试网络上展示可识别的稳定币（如 USDT/USDC）的合约、网络、金额与收款信息；能够跟踪提交、确认及对账。
7. 对付款不足、错误币种/网络、超时/未知、重复回调、对账差异和退款异常有可审查路径。
8. 经规定权限与规则确认配售，生成/引用权威登记，并独立核对 RWA Token 执行状态。
9. 投资者可以区分认购进度、已确认登记权益、链上相关状态、待核对差异及文件。
10. 发行方可管理至少一种适用于首发金融工具的存续期事件。
11. 关键记录可查到授权、操作人、时间、外部来源和更正记录。
12. SaaS 退出、权限撤销或服务商异常时，在途认购、款项、登记与存续期责任不会被直接删除或误标完成。

本表是后续场景化验收建议；不得视为生产资金或正式证券发行上线许可，也不规定最终测试用链、工具或实际机构。

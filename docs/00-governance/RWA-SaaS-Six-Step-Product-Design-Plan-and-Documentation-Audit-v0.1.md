## 三、什么才是一份可真正交给 UI/研发的“标准产品文档”？

**没有所有团队通用的固定文件数量或唯一 PRD 模板**。建议用“最少独立文档 + 每项需求必要内容完整 + 可追踪验收”的原则。RWA/多租户/真实资金/法定权利需要比普通内容类 SaaS 更严格的权威事实和异常边界。

### 3.1 详细 PRD 每一个功能点的标准栏目（Step 05 必须）

| 栏目 | 需要回答的问题 | 示例：投资者付款 |
|---|---|---|
| 唯一定位 | 端/页面组/模块/旧功能 ID、V1 条件、关联流程节点 | 投资者端付款，M11-F004～F006，节点 P-xxx |
| 需求目标、上下文 | 谁为何做、何时进入、哪些状态可见 | 某个有效订单按受权付款指令支付 |
| 执行角色和权限 | 人/系统/外部授权方、租户/项目/Offering 作用域及审批分权 | 投资者发起；外部链/资金方提供事实；Issuer 仅受权查看 |
| 输入/字段字典 | 每个字段的业务名、数据类型、是否必填、默认、长度/枚举/精度/来源/敏感级别/展示规则 | chain_id、token_contract、recipient、raw_amount、payment_intent |
| 前置条件与校验 | 必须满足的业务 Guard、重复提交及冲突处理 | Eligible、有效 Quote、可用额度、受权收款方案 |
| 操作和输出 | 业务命令/事件及正常可见结果 | 创建付款意图、收到 Tx、链确认、对账匹配 |
| 业务状态与版本 | 哪个对象状态变化、何者有权变更、生效时点 | Receipt 与 Reconciliation 是独立状态 |
| 规则/算法 | 金额、费率、发行份额/法定上限、记录日等可检验计算约定 | Decimal 精度、容差/少多付处理条件与证据 |
| 跨模块及外部接口 | 业务依赖、系统拥有者、入出参逻辑、Unknown/回调/幂等 | M10/M11/M12 与外部链服务结果 |
| 异常/边界/恢复 | 拒绝、失败、部分成功、超时、重复回调、取消、冲正 | 迟到真实款、错误链和对账异常 |
| 安全/隐私/审计 | 授权边界、敏感信息、证据/日志与留存 | 记录真实链事件与退款审批，禁止客服假设已到款 |
| 验收设计和非范围 | Given/When/Then 与可观察证据；哪些不做 | 回调重复不计双款；法币支付非默认 V1 |
| 决策与变更历史 | 已批准/待法域、责任人、依赖文档与版本 | 真实收款/退款方尚待 G-02 |

不必为每个功能单独新建 Markdown：可在**按端/模块组织的主文档**中用功能 ID 锚点和结构化表格维护，跨模块共用规则只引用一个权威来源，避免数据字典和权限表分叉。

### 3.3 不建议额外制造的文档

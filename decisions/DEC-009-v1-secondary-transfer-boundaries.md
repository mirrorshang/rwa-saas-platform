# DEC-009｜V1 二级转让能力边界（提案）

- 提案日期：2026-10-19
- 状态：**Proposed（待产品负责人确认；尚未批准）**
- 关联决策：DEC-001（客户独立资产门户与授权分发）、DEC-002（客户层级与交付模式）、DEC-003（多资产与初始范围）、DEC-004（受监管活动责任边界）、DEC-008（认购资金、结算与退款原则）
- 关联文档：[第 02 份《产品战略与商业模式》](../docs/02-product-strategy/RWA-SaaS-Product-Strategy-Business-Model-v01.md)
- 本提案只界定软件产品能力边界，不构成任何法域下开展证券交易、经纪、撮合、交易场所运营、结算或托管活动的法律判断。

## 1. 需要决策的问题

投资者持有 Token 或其他数字化权利后，可能希望向另一投资者转让。但“链上可转移”并不等于法律权利可自由转让，也不意味着 SaaS 平台可以经营公开二级市场、撮合交易、执行交易或控制交易资金。

需要确定 V1 是以受控的转让工作流与记录能力为主，还是将公开市场、订单撮合或平台运营的二级交易能力纳入首期范围。

## 2. 建议的 V1 产品原则（等待确认）

1. **V1 默认不建设公开二级交易市场。** 不将公开订单簿、公开 C2C 撮合、连续竞价、自动做市、K 线/行情交易终端或平台自营流动性纳入默认 V1 范围。
2. **先支持受控转让工作流。** 在具体资产、法律工具、客户合同和适用法域允许的前提下，产品可研究提供转让申请、资格校验、必要审批、状态跟踪、登记/链上更新和审计记录等工作流能力。
3. **转让请求不等于交易成立或权利变更。** 申请提交、双方意向、发行方同意、合规检查通过、付款/交割、权威登记更新和链上交易确认必须分开建模；不得以其中一个状态自动代替其余状态。
4. **转让规则由具体 Instrument/Offering 与法定文件决定。** 可能包括锁定期、合格投资者要求、发行方同意、优先购买权（ROFR）、转让限制、持仓/数量限制、通知期、费用和税务/报告义务；规则必须版本化、可追溯，不可把某一资产的规则直接套用于全部资产。
5. **资格检查必须重新评估。** 转让方与受让方的身份、投资者类别、适用法域、制裁/AML 状态、持仓及项目资格均须按本次转让的规则检查。此前通过 KYC 或曾持有该资产，不自动代表本次受让资格有效。
6. **授权与权限明确。** 由谁申请、审核、同意、执行登记、确认交割和处理争议，应按已确认的法律责任、合同与角色分配。管理员不能仅凭系统权限绕过限制。
7. **链上执行和权威登记分离。** 链上转移能力、交易确认和法律登记的效力需按具体法律工具确认；若链上记录不是权威登记，产品必须明确记录二者状态并支持对账和差异处理。
8. **资金交割不默认由平台处理。** 若转让涉及对价、托管、付款或结算，沿用 DEC-008 的资金状态与责任边界；未完成法律评估、合格合作方确认、合同安排和上线批准，不启用真实资金流程。
9. **异常与可逆性须受控。** 需处理审批拒绝、资格过期、双方取消、ROFR 触发、付款未完成、链上失败/确认不足、登记失败、重复请求、争议及人工更正；不能随意覆盖历史或把未知状态当成完成。
10. **允许将更高级能力作为后续独立决策。** 机构间转让、经批准的私有转让网络、第三方交易场所集成或更完整的二级市场可单独研究，但不能因接口预留或客户要求而默认进入 V1。

## 3. 建议的核心对象与状态分层

| 对象/阶段 | 状态示例（非最终状态字典） | 关键规则 |
|---|---|---|
| Transfer Request / 转让申请 | Draft、Submitted、Under Review、Rejected、Cancelled、Expired | 记录转让方、受让方、资产/Instrument、数量、申请时间及适用规则版本 |
| Eligibility / 资格检查 | Not Started、Pending、Eligible、Ineligible、Needs Review、Expired | 保存检查依据、规则版本、时间、结果和必要原因 |
| Issuer Consent / 发行方同意 | Not Required、Pending、Approved、Rejected、Expired | 仅在相关法律文件/规则要求时启用；记录审批主体与依据 |
| ROFR / 优先购买权 | Not Applicable、Notice Pending、Open、Exercised、Waived、Expired、Disputed | 按具体条款确定通知对象、期限、行使结果与证据 |
| Consideration / 对价交割（如适用） | Not Required、Pending、Processing、Unknown、Confirmed、Failed、Reversed | 依 DEC-008 管理权威来源、结算确认、对账与异常 |
| Register Update / 权威登记更新 | Not Started、Pending、Submitted、Confirmed、Failed、Needs Reconciliation | 区分提交更新与权威登记确认 |
| On-chain Execution / 链上执行（如适用） | Not Required、Pending、Submitted、Confirming、Confirmed、Failed、Reorg/Needs Review | 按网络最终性要求管理；不能仅凭交易哈希确认法律权利变更 |
| Transfer Completion / 转让完成 | Not Complete、Pending Reconciliation、Completed、Disputed、Reversed（仅按合法受控流程） | 只有满足该 Instrument 已批准的全部必要条件后才能完成 |

以上状态为讨论示例，不是最终状态机。不同资产可省略不适用步骤，但必须明确省略依据，不能删除其法律与业务规则要求的控制。

## 4. 建议的 V1 能力范围

### 建议纳入研究与产品规格

- 转让限制与规则配置（按资产/Instrument/Offering 版本管理）；
- 转让申请及双方/相关机构的工作流；
- 受让方资格校验与补充审查；
- 发行方同意、ROFR 或其他约束流程（仅在适用时）；
- 外部支付/托管/登记/链上服务的状态接入与关联；
- 业务状态、权威来源、外部引用、事件时间和审计记录；
- 拒绝、取消、过期、状态未知、失败重试、对账差异及人工升级；
- 按租户、发行方、资产和角色隔离数据与操作权限。

### 建议默认排除在 V1

- 面向公众的资产列表与自由交易市场；
- 公开订单簿、自动撮合、竞价、做市或平台提供流动性；
- SaaS 平台自行作为经纪商、交易场所、结算机构或资产/资金托管方；
- 默认的跨发行方资产自由流通；
- 不经项目规则和资格检查的自由转让；
- 以链上可转移性替代法律可转让性、权威登记或交割确认。

## 5. 必须覆盖的关键异常

1. 转让双方资格变化、资料过期或受让方不符合准入条件；
2. 发行方拒绝、审批超时、ROFR 被行使或通知有争议；
3. 双方取消、重复提交或并发申请导致持仓冲突；
4. 对价付款未知、失败、部分完成或与转让状态不一致；
5. 链上交易失败、确认不足、重组或与登记记录不一致；
6. 权威登记服务不可用、拒绝更新或返回结果不确定；
7. 规则版本变化后，正在处理的申请应采用哪个版本；
8. 人工纠错、争议处理、客户退出或外部服务商切换；
9. 未获授权的跨租户/跨发行方查看、申请、批准或执行；
10. 完成状态与资金、链上及权威登记事实不一致时的阻断、调查和审计。

## 6. 仍需后续验证的问题

- 目标客户是否有明确且频繁的二级转让需求，还是首期只需发行与存续期管理？
- 首批资产/法律工具是否允许转让，限制条款和登记机制具体是什么？
- 是否需要发行方同意、ROFR、锁定期、投资者分类或其他限制？
- 受让方资格检查、制裁筛查及 AML 责任由谁承担，依赖哪些合格服务方？
- 若有对价，付款/结算权威来源是什么，谁承担资金责任，如何处理退款与争议？
- 哪一方维护权威持有人登记，链上 Token 与法定登记之间的关系是什么？
- 客户是否只需要工作流与 API，还是希望接入第三方获准交易场所？
- 各候选法域是否允许拟议的转让流程，具体许可/注册和合同责任是什么？

## 7. 建议的验收标准

若本提案获原则性确认，后续规格至少应确保：

- V1 不会在默认配置下启用公开二级市场、撮合或平台自营交易；
- 每次转让均关联资产/Instrument、转让双方、数量、规则版本和资格检查；
- 申请、审批、ROFR、对价交割、登记更新、链上执行及最终完成状态相互区分；
- 未完成必要审批、资格检查、交割或权威登记时，不会错误显示为完成；
- 未知/处理中状态有查询、对账和升级路径；
- 跨租户及未授权跨发行方访问/操作受到阻断并可审计；
- 人工更正、拒绝、取消和争议处理保留完整历史；
- 任何真实转让/资金路径上线前完成具体法律评估、合作方确认、合同安排和上线批准。

- **B｜同意基本方向，但需修改部分原则**；
- **C｜暂不确认，先补充客户需求、合作方方案或法律意见。**

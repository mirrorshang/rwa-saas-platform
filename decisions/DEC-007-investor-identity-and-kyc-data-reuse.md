# DEC-007｜投资者身份与 KYC 数据复用原则

- 决策日期：2026-10-19
- 状态：**Approved（已由产品负责人原则性确认）**
- 决策说明：原则上同意本提案；实现细节、客户场景与具体法域的法律要求仍须逐项验证。**
- 关联决策：DEC-001（客户独立资产门户与授权分发）、DEC-002（客户层级与交付模式）、DEC-004（受监管活动责任边界）、DEC-006（全球产品与市场选择）
- 关联文档：[第 02 份《产品战略与商业模式》](../docs/02-product-strategy/RWA-SaaS-Product-Strategy-Business-Model-v01.md)
- 本提案只定义产品和数据治理原则，不构成任何法域下 KYC/AML 合法性、数据跨境、数据保留或许可要求的法律结论。

## 1. 需要决策的问题

旧版需求材料存在“完成一次 KYC 即可在平台范围内无条件复用”的倾向。该假设不应自动成为本项目要求。产品需要区分身份基础资料、核验事实、合规审查结果、项目投资资格与最终业务决定，并确定这些信息能否在不同客户、发行方、资产、项目或法域之间复用。

## 2. 已确认的产品原则

1. **默认租户隔离。** 投资者数据按 SaaS 客户、发行机构、门户和授权范围实施最小权限访问。任何跨租户访问或共享均不得仅因系统技术上可关联而默认开放。
2. **区分数据与决定。** 至少在产品模型上区分：
   - 身份基础资料与身份核验材料；
   - 核验事件/事实（核验服务方、时间、方法、状态、有效期及可验证引用）；
   - KYC/AML 或其他尽调审查结论与风险标记；
   - 特定发行、金融工具、投资者类别和法域下的资格判断；
   - 针对具体认购或业务活动作出的最终决定。
3. **核验完成不等于资格通行。** 即使可依法复用某项身份核验事实，也不代表投资者自动符合其他发行方、资产、项目或法域的准入条件；资格必须按相应规则重新判断，并保留判断依据及时间。
4. **复用须满足明确前提。** 跨客户或跨场景复用前，应确认适用法律依据、必要的告知与授权（如适用）、目的限制、数据最小化、服务商合同与权限、数据驻留/跨境条件、有效期及撤回/失效处理。具体前提须按实际法域与业务模式由法律顾问及合规负责人确认。
5. **原始敏感材料不默认共享。** 身份证件影像、原始 KYC 文件、尽调备注、内部风险判断及其他敏感信息不得默认向其他租户暴露。优先评估是否可以通过受限访问、可验证的核验状态或服务商提供的引用/凭证满足业务需求；不得将该设计偏好视为所有场景均足够或法律上必然允许。
6. **每个项目独立执行准入检查。** 资格规则应可配置并关联发行方、资产/金融工具、Offering、投资者类别、法域和时间点；系统应记录规则版本、检查结果、阻断原因及人工覆核/例外审批。
7. **授权与访问可审计。** 对数据查看、导出、复用授权、跨租户共享、资格判断、人工覆核和权限变更保留可追踪审计记录，包括主体、时间、目的/业务上下文及结果；审计数据本身也须按权限保护。
8. **有效期、更新与纠错不可缺失。** 核验结果应支持过期、需更新、撤回、失败、服务商不可用、数据不一致和人工复核等状态。旧核验结果不得被永久视为有效。
9. **删除与法定留存按规则处理。** 产品应支持数据访问、更正、删除/限制处理请求及留存期限管理；是否可删除、需保留哪些记录及保留多久，必须由具体法域和业务责任主体的法律要求决定，不预设所有资料都能立即删除或必须永久保留。
10. **客户可治理其合法控制范围。** 在合同、权限和法律允许范围内，为客户提供数据来源、处理目的、访问范围、服务商、留存规则与导出/退出处理的可见性和管理机制；不得让一个租户读取或管理另一租户的数据治理配置。

## 3. 建议的数据与决策分层

| 层级 | 典型内容 | 默认产品处理建议 |
|---|---|---|
| A. 身份资料 | 姓名、联系方式、身份属性、证件资料等 | 高度受限；按目的最小化收集与访问，不默认跨租户共享 |
| B. 核验事实 | 核验状态、服务商、核验时间、方法、有效期、可验证引用 | 评估在明确合法依据、授权与合同条件下有限复用；复用不自动授予资格 |
| C. 尽调/风险结果 | KYC/AML 审查结论、风险标记、人工尽调记录 | 单独设定责任主体、可见范围与共享依据；不默认向其他租户暴露 |
| D. 项目资格判断 | 某投资者是否满足某发行/资产/法域规则 | 逐项目/发行判断；记录规则版本、时间、结果与原因 |
| E. 业务决定与执行 | 认购接受/拒绝、配售、资金状态等 | 由经确认的责任主体和授权流程决定；不能仅凭身份核验状态自动执行 |

以上为建议的数据逻辑分层，不要求所有实现都采用独立数据库或特定技术架构；实际数据模型需在总体 PRD、隐私设计和技术设计中进一步确定。

## 4. 关键边界

- “平台可技术复用”不等于“平台有权复用”。
- “投资者同意”本身不必然满足所有法域下的数据处理、金融合规或跨境传输要求。
- 第三方 KYC 服务商给出的状态或报告，不自动替代发行方、运营商或其他依法承担义务主体的判断与责任。
- 白标运营商管理多家发行机构，不意味着所有子发行机构可以互相访问投资者数据。
- 不应为减少重复操作而默认建立平台全局共享投资者库；若未来确有需求，应另行明确数据控制角色、用途、授权模型、客户合同、法律依据和退出机制。
- 本提案不确定平台、发行方、运营商或 KYC 服务商谁在任何特定法域中属于数据控制者、处理者或其他责任角色；需依据真实安排逐项确定。

## 5. 对产品的影响（实现细节仍待验证）

1. 设计投资者身份、核验事件、项目资格和认购决定之间的独立关联。
2. 在多租户权限模型中加入跨租户访问阻断与显式授权机制。
3. 为 KYC 服务商接入定义状态映射、有效期、失败/过期和人工复核流程。
4. 为每个 Offering 配置投资者资格规则与审计记录。
5. 在管理后台设计数据来源、访问授权、复用范围、留存/删除规则与服务商配置。
6. 为投资者提供适当的告知、授权、更新与数据请求流程；具体文案及流程需由法律顾问审查。
7. 在 API/SDK 中对身份资料、核验状态、资格结果和业务决定实行不同权限等级与最小字段返回。

## 6. 仍需回答的问题

- 产品是否允许投资者主动维护一个可复用的身份资料档案？由谁提供、控制和访问？
- 跨发行方复用核验事实时，是否由投资者主动授权、由各发行方逐次授权，或两者同时要求？
- 平台是否仅保存服务商的核验状态/引用，还是在特定客户合同和法域下保存部分原始材料？
- 不同租户之间是否允许共享风险标记或尽调结果？哪些数据绝对禁止共享，哪些可在明确条件下共享？
- KYC 更新、过期、撤回授权或服务商结果变更后，既有资格与未完成认购如何重新评估？
- 数据保留、删除、导出、客户终止及服务商替换的要求分别是什么？
- 各类记录由发行方、白标运营商、SaaS 提供方及服务商中的哪一方负责？该角色需按合同、真实控制关系及法域法律意见确定。

## 7. 建议的验收标准

后续产品规格至少应能验证：

- 未获授权的租户无法访问其他租户的身份原始材料、尽调记录或投资者列表；
- 核验状态被复用时，系统不会自动将其他项目的资格结论复制为当前项目的资格决定；
- 每次资格判断可追溯到适用规则版本、时间、结果与原因；
- 过期、待更新、撤回、失败和人工复核状态有明确处理路径；
- 数据复用授权、访问、导出和人工例外均有审计记录；
- API 返回字段和操作权限按数据敏感度分级；
- 留存、删除、数据请求及客户退出流程可按具体配置和法律要求执行；
- 未完成相应法域法律评估的市场/业务组合不得仅凭配置项开启真实业务。

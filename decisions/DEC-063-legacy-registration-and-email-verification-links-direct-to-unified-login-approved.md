# DEC-063｜历史注册与邮箱验证链接直接进入统一邮箱登录批准

> 日期：2026-11-10  
> 状态：**Approved**  
> 批准依据：用户明确要求「整个就是一个邮箱登录的过程，用户输入邮箱、获取验证码、输入验证码即可」，不向用户解释内部注册/登录整合决策。  
> 上位决策：DEC-060、DEC-061、DEC-062  
> 维护分支：docs/r2-current-product-baseline｜PR #8 Draft / Open / Unmerged

## 一、批准事项

官网企业账户的用户可见体验统一为一个简洁的邮箱验证码登录流程。用户不需要了解系统内部如何区分首次使用与已有账户。

### 用户实际看到的流程

1. 输入邮箱。
2. 点击「获取验证码」。
3. 输入收到的验证码。
4. 验证成功后进入企业工作台或对应的企业下一步。

### 系统内部处理

- 首次验证成功：自动创建账号并建立登录会话。
- 已有账号：直接建立登录会话。
- 不在页面上要求用户选择「注册」或「登录」；不需要向用户解释首次自动注册。

### 历史 URL 处理

- 旧注册地址 `/register`：直接进入统一邮箱登录页面，不显示注册兼容说明页。
- 旧邮箱验证地址 `/verify-email`：直接进入统一邮箱登录页面，不显示「验证方式已整合」等解释页。
- 如旧链接携带合法的 Standard 升级意图，可安全保留该意图；不得回显未经验证的邮箱或敏感参数。
- 不显示「原邮箱验证方式已取消」「注册与登录已整合」等内部产品决策说明。
- OTP 的发送、输入、错误、过期和重发等交互全部发生在同一个邮箱登录流程中。

## 二、体验原则

用户只需理解「邮箱 + 验证码」即可登录。首次账号创建是系统内部行为，不成为用户额外的页面、步骤或概念负担。

## 三、边界

- 本决策不改变邮箱验证码安全策略、有效期和频控的最终确定责任。
- 邮箱发送和真实账户服务未开放时，页面如实显示当前服务不可用；不得假装发送或登录成功。
- 本决策不代表真实账户服务已经开放，也不授权修改官网源码或开展技术开发。
- 不改变 U01 的企业创建、KYB、Free/Standard、企业钱包与订阅规则。
- 不修改 Frozen、193 项正式功能 ID 与首次交付版本归属；不关闭 X-01～X-13；不合并 PR #6 或 PR #8。

## 四、后续

W-10 的页面设计以简洁统一的两步邮箱验证码登录为唯一用户流程；W-08、W-09 仅作为历史 URL 路由兼容，不再作为独立用户可见页面。

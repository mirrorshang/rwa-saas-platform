## 二、逐项产品决策（A 已获批准，B 仅历史备选）

### CR-01｜企业 SaaS 在线注册、KYB、订阅及自动开通

- **原ID/领域**：M01-F008 / M01-F001～007 / M03 / M19。
- **A（推荐）**：V1.0 包含官网自助申请、套餐选择、完成KYB后商业付费/订阅、授权Tenant自动或半自动开通，允许审核及线下合同例外。
- **B（备选）**：V1.0 仅官网申请/人工合同与Tenant开通，在线自动订阅 V2.0。
- **验收与依赖**：自动收费与企业KYB前后次序、收款服务商、退款、账单/发票、合同/隐私、暂停/续费/失败恢复均应有受控状态。SaaS 订阅费不能和认购投资款同一账本。
- **我推荐A的原因**：优先完成自助商业闭环，但 KYB/商业合法条件不满足时不能把“付费成功”当成真正发行授权；没有实际收费通道与合法契约时不得宣称生产可用。
- **当前状态**：**Approved（选择 A，参见 DEC-013）**；真实法域、技术、服务商和逐项 V1.0 交付仍需单独核验。

### CR-02｜Issuer 标准独立投资者门户与高级 White-label 划界

- **原ID/领域**：M08-F001/002/003 + M02 / M15-F004。
- **A（推荐）**：V1.0 每个Tenant具有可访问的标准独立URL、机构名称Logo、条款及Offering访问控制；V2.0 才支持自定义域名/高级品牌主题/多Issuer白标运营商。
- **B（备选）**：V1.0 只允许平台共享主域固定页面，完全独立URL/门户品牌配置 V2.0。
- **验收与依赖**：标准URL、站点状态、公开/定向Offering、投资者账户绑定Tenant、受限访问、邀请和隐私链接要可验收；明确高级域名与M15原ID的关系，避免把M15完整商业模块挪入首期。
- **我推荐A的原因**：首期有发行机构自己的投资者前台是核心销售闭环；标准URL与高级White-label不混同。
- **当前状态**：**Approved（选择 A，参见 DEC-013）**；真实法域、技术、服务商和逐项 V1.0 交付仍需单独核验。

### CR-03｜受控金融工具模板和标准发行向导

- **原ID/领域**：M04-F008 / M04-F003～007 / M05 / M06。
- **A（推荐）**：V1.0 包含A债权及B SPV股份两类最小有审查版本的表单模板与向导，必须在适用法域依法审核后才能发布；高级模板市场 V2.0/后续。
- **B（备选）**：V1.0 只允许空白自由表单，自带模板全部后置。
- **验收与依赖**：模板必须指向 InstrumentVersion、真实法律权利、适用证据/必填项/风险提示和审批对象；‘收益型/利息型’只是用户表达，不能代替债权/股权/合同权益法律分类。
- **我推荐A的原因**：模板提升标准化发行效率，但不可以自动生成法律效力、公司/SPV合法存续或默认收益承诺。
- **当前状态**：**Approved（选择 A，参见 DEC-013）**；真实法域、技术、服务商和逐项 V1.0 交付仍需单独核验。

### CR-04｜专业服务由谁承担及平台协作深度

- **原ID/领域**：M06-F001～008 / M04 / M22。
- **A（推荐）**：V1.0 以Issuer自选律师/评估/SPV服务商、上传其成果和受控审核引用为默认；完整服务商在线协作、竞价与Marketplace在 V2.0/V3.0。
- **B（备选）**：V1.0 必须配套完整律师/评估/SPV在线撮合及工作空间。
- **验收与依赖**：资产权属、法律文书、评估、公司实体与SPV设立、有效签署、责任主体及法域证明分别列清单；复核/补件、有效期和版本归档首期必须可用。
- **我推荐A的原因**：降低首发外部服务集成依赖；不存在‘选了SPV模板就自动合法成立公司’的产品承诺。
- **当前状态**：**Approved（选择 A，参见 DEC-013）**；真实法域、技术、服务商和逐项 V1.0 交付仍需单独核验。

### CR-05｜合约模板 Factory 与部署自动化

- **原ID/领域**：M07-F001～010 / M22 / M05。
- **A（推荐）**：V1.0 支持经批准合约版本和单一受权链的模板参数→审查→DeploymentIntent→由合法受权签名主体自动/半自动部署→链上Finality与恢复；认购合约与收益合约是否独立由产品模式选择。
- **B（备选）**：V1.0 只允许手工外部部署并录入合约地址，合约Factory V2.0。
- **验收与依赖**：需要确认标准、Token权益映射、审计过的合约模板、签名权限、可升级/冻结权限、沙盒/生产隔离、部署Unknown恢复；并非每笔订单部署新合约，Mint须在合法配售和适用登记后单独触发。
- **我推荐A的原因**：自动化提高发行效率，但不能因自动化让 SaaS 平台默认控制全部生产私钥或法定Token权益。
- **当前状态**：**Approved（选择 A，参见 DEC-013）**；真实法域、技术、服务商和逐项 V1.0 交付仍需单独核验。

### CR-06｜投资者钱包：EOA 与嵌入式账户

- **原ID/领域**：M08/M09/M07/M22及候选CAND-02。
- **A（推荐）**：V1.0 提供连接外部钱包及一个安全审查通过的嵌入式钱包方案（MPC可选但不是唯一技术实现），包括创建、恢复、风险控制与签名、手续费提示。
- **B（备选）**：V1.0 仅支持外部钱包连接，嵌入式钱包 V2.0。
- **验收与依赖**：嵌入式钱包供应商、密钥模型、托管/非托管责任、恢复失窃、EOA/智能账户兼容、Gas、KYC法律主体与付款/Token接收地址映射须单独验证。
- **我推荐A的原因**：无钱包经验的投资者能完成首购，但不能用钱包等同法律身份、法定股东名册和KYC。
- **当前状态**：**Approved（选择 A，参见 DEC-013）**；真实法域、技术、服务商和逐项 V1.0 交付仍需单独核验。

### CR-07｜募集资金合法结算与发行方提取

- **原ID/领域**：M11/M21/M17/M20/M22及候选CAND-03/04。
- **A（推荐）**：V1.0 提供真实募集款收款/冻结/受限/合法可划拨/划拨中/已实付/Unknown的报表和经授权的结算提取申请，由实际有权资金方执行出款。
- **B（备选）**：V1.0 只做付款到账对账，发行人资金划拨全部线下不纳入产品。
- **验收与依赖**：谁实际收款/托管、募集是否成功或达到释放条件、退款准备金、净额/费用、企业合法收款账户和提现白名单、审批、外部出款/到账、重复划款风险要明确。
- **我推荐A的原因**：这是业务闭环缺口，但 SaaS 不默认开设投资者法币钱包或直接持有/挪用募资款。
- **当前状态**：**Approved（选择 A，参见 DEC-013）**；真实法域、技术、服务商和逐项 V1.0 交付仍需单独核验。

### CR-08｜收益实际注资和 Push/Claim 分配

- **原ID/领域**：M13-F004/005/006 + M07/M22/M08/M21及候选CAND-05/06。
- **A（推荐）**：V1.0 必须具备合法收益事件/RecordDate快照/审批/资金注入/资金足额确认，并首期选择一种可依法履约的执行方式；推荐 Claim-first，Push预留架构接口。
- **B（备选）**：V1.0 只提供收益核算与人工出款对账，自动分配与Claim全部 V2.0。
- **验收与依赖**：A债权到期票息/本金是法定义务；B SPV分红仅合法决议后产生。Claim须落实Gas、领取期限、暂停冻结、Unclaimed/Partial、名单争议与真实法律清偿时点；‘Funded’不等于Paid。
- **我推荐A的原因**：你的11步明确把收益分配当成核心，首期应有真实可运行的一种合规分配闭环；不得对任意SPV强加固定年化/保证回购。
- **当前状态**：**Approved（选择 A，参见 DEC-013）**；真实法域、技术、服务商和逐项 V1.0 交付仍需单独核验。

### CR-09｜到期、回购、赎回与 Token Burn

- **原ID/领域**：M13/M12/M07-F009/M17/M22。
- **A（推荐）**：V1.0 支持A债权本金到期清偿、部分付款/逾期及其必要的登记/Token冻结销毁；B SPV有真实批准的回购/注销/清算事项才按合法条件触发，复杂重组后置。
- **B（备选）**：V1.0 不支持到期本息及任何合法退出，只显示资产持仓。
- **验收与依赖**：M07-F009历史P1，但针对A参考样本需要最低链动作；法律清偿、真实资金实付、名册变化、Token Burn/Freeze四套事实分离。
- **我推荐A的原因**：A债权首期若不支持到期还本会破坏完整业务模型；B股份不应默认有固定到期和本息。
- **当前状态**：**Approved（选择 A，参见 DEC-013）**；真实法域、技术、服务商和逐项 V1.0 交付仍需单独核验。

### CR-10｜历史187功能向版本的转换及新功能缺口

- **原ID/领域**：DEC-012 / 187原ID / CR与CAND新增候选。
- **A（推荐）**：保留187原ID及已批原则，审核原187到V1.0/V2.0/V3.0的唯一版本映射，必要的门户/钱包/结算/收益和合约Factory能力先核原ID可否扩深，真正新增再正式编号和调整总数。
- **B（备选）**：直接把原187按P0=V1、P1=V2、P2=V3批量转换，不做完整业务场景核验。
- **验收与依赖**：禁止改写Frozen/Approved历史；只有产品负责人批准了的新版本清单才是实际V1.0开发范围，Step02图v0.3和Step03双向矩阵作为审批证据；V1不再包含可选P1。
- **我推荐A的原因**：转化的核心是消除版本模糊与遗漏，不是把历史优先级简单换名字。
- **当前状态**：**Approved（选择 A，参见 DEC-013）**；真实法域、技术、服务商和逐项 V1.0 交付仍需单独核验。

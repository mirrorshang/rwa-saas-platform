1. 需求背景
1.1 为什么做
平台业务方向从"自营房地产 RWA 应用"升级为"多资产 RWA 基础设施 + 对外发行 SaaS"。V1 的身份体系与"发行—认购—分红"链路均围绕房地产单一场景写死，无法支撑新资产类型的多期发行、多权益类型（收益型/使用型）以及"一次认证全平台复用"的开放平台诉求。
1.2 当前存在的问题
- 资产模型写死：Property → Token 一对一，无法拆分多期、多权益对外发行。
- 身份不可复用：KYC 与单一钱包地址绑定，换链、换钱包需重新认证。
- 认购体验差：确认耗时约 15s，代币由后台脚本延迟发放，发售规则不可验证。
- 资金流转不透明：募集资金进平台账户后人工划转，分账比例不可自定义、不可验证。
- 收益兑付成本高且不透明：平台批量代发收益、垫付 Gas 又扣用户手续费；"收到收入"与"可以分钱"两个口径混同，容易做出无法履约的承诺。
- 使用型资产缺少标准化的销毁/核销能力：算力等使用型权益缺乏平台侧统一的持仓管理与销毁（Burn）能力，导致外部生态难以低成本对接。
- 超发无硬约束：没有 Capacity 概念，超发风险仅靠人工控制。
1.3 解决什么问题
建立"一次 KYC、全平台复用"的全局身份体系；建立 Asset → Right → Offering → Token 四层发行模型；打通资产从登记发行 → 认购 → 收益核算分配（或使用型兑付）→ 退出的完整一级市场闭环，并使认购与分账在链上自动、透明、可验证地完成。

2. 产品目标
2.1 业务目标
- 支撑同一资产多期、多权益类型对外发行，新增一期发行从"开发排期"降为"后台配置"。
- 认购资金分账方式灵活可配置，满足不同资产背后不同参与方（Owner/Operator/发行方等）的分成诉求，同时平台手续费收入统一、可控、不可被发行方绕开。
- 收益分配与使用兑付成本与用户规模解耦（Merkle Claim / 差额回退机制），平台不再垫付 Gas。
- 建立"资产不可超发""收益口径不混同""使用兑付有据可查"三项可验证承诺，作为发行方与投资者的信任背书。
2.2 用户目标
- 投资者：一次认证全平台可用；认购快速透明；收益/使用兑付有清晰状态可追踪，且长期不因未及时领取而作废。
- 发行方：自助完成资产登记与发行配置，资金分配方案自主可控；收益上报与核算流程清晰，知道钱从"上报"到"可分配"经过了哪些环节。
- 平台运营：统一审核资产、发行计划、收益上报，掌握手续费收取的统一管控权，具备分级熔断能力应对异常。

4. 需求范围
4.1 本期做什么
1. 身份与登录：钱包直连、邮箱登录自持钱包、KYC 提交与审核、KYC 通过后的多钱包绑定与解绑。
2. 资产登记（Asset Onboarding，发行方须先完成 KYB）。
3. Right 与 Capacity 定义。
4. Offering 发行配置：发售规则、单一认购币种、自由配置的资金分配方案（含平台固定手续费项）、收益发放周期（无收益/按天/按月/按季度）、Exit Rule。
5. 一级市场认购全流程。
6. 收益核算与分配（Revenue Core）：收益上报 → 核实 → 归集 → 扣费 → 可分配 → 快照 → Merkle 分配 → 用户 Claim（仅适用于配置了收益发放周期的 Offering）。
7. 使用型权益的发行与销毁能力（Usage Core，平台侧最小闭环）：平台负责 Usage Token 的发行、持仓管理、标准化销毁（Burn）能力与销毁记录展示；不负责具体消费场景设计（如何冻结、如何计量用量、提供什么服务，均由接入的第三方生态自行负责）。
8. 退出与结算（Settlement Core）：Exit Rule 的规则框架与触发条件（各退出类型详细执行流程标记待确认，见 14.7）。
9. 异常分级熔断（资产/Offering 状态管理，五个独立开关）。
10. 平台手续费统一配置（Admin）。
4.2 本期不做
- 二级市场交易（挂单、撤单、成交、AMM）——见《二级市场 PRD》。
- 合约层具体校验规则、Token 标准选择、Merkle Distributor 等技术实现——见《合约功能 PRD》。
- Open API 对外契约、SDK、沙箱、多租户/白标——见《Open API / SaaS / 白标 PRD》。
- 跨链认购与跨链身份（本期默认单链）。
- 历史数据迁移、灰度双跑等实施性工作。
- 个人作为发行方的 KYC 流程（待确认后决定是否补充）。
- 使用型权益的具体消费场景设计（如何冻结、如何计量用量、提供什么服务、Provider 履约与仲裁机制）——由接入的第三方生态自行负责，不属于平台产品范围。

5. 产品流程
5.1 身份认证总流程
用户进入平台
  ├─ 已有账号 → 登录（钱包直连 / 邮箱）→ 关联已有 ONCHAINID
  └─ 新用户 → 选择登录方式
        ├─ 钱包直连：连接钱包 → 生成/关联 ONCHAINID → 绑定当前钱包地址
        └─ 邮箱登录：邮箱验证 → 生成嵌入式自持钱包 → 生成/关联 ONCHAINID → 引导设置恢复方式
  ↓
是否已完成 KYC？
  ├─ 是 → 直接可用，可在"钱包管理"中追加绑定/解绑其他钱包
  └─ 否 → 提交 KYC 材料 → 平台/供应商审核
        ├─ 通过 → 解锁认购等能力
        ├─ 拒绝 → 提示拒绝原因 → 用户修改材料后重新提交（可反复，无次数限制【待确认是否限次】）
        └─ 审核中 → 认购入口置灰
5.2 资产发行总流程（发行方/Admin 视角）
发行方完成 KYB → 提交资产登记（Asset Onboarding）
  → Admin 审核资产资质 → 通过/驳回（驳回可修改重提）
  → 发行方定义 Right（权益类型、Capacity 总量）
  → 发行方创建 Offering：
       发售规则 + 单一认购币种 + 资金分配方案（发行方自定义各方比例，
       系统自动追加 Admin 配置的平台手续费项，合计=100%）+ Exit Rule（必填）
  → Admin 审核 Offering → 通过后按配置时间自动/人工发布
  → 发售中，接受认购，直至售罄/到期/人工关闭
5.3 投资者认购流程
浏览 Marketplace → Offering 详情页 → 点击认购
  → 校验前置条件（KYC通过、资格合规、未超个人累计限额、发售中、Capacity充足）
      ├─ 不通过 → 提示具体原因，阻断下单
      └─ 通过 → 输入数量（币种为该 Offering 唯一认购币种，无需选择）
  → 确认 → 钱包签名 → 广播
  → 前端乐观反馈"已提交"（<1s）
  → 链上确认（P95≤5s）：同一笔交易内完成 扣款 → 按分配方案拆分到各接收方 → 铸造/转移 Token
      ├─ 成功 → 认购成功，Token到账，持仓更新
      └─ 失败 → 展示失败原因，资金不扣除，可重试
5.4 收益核算与分配流程（Revenue Core，仅适用于配置了收益发放周期的 Offering）
Offering 配置的"收益发放周期"（按天/按月/按季度）到期
  → 发行方/Operator 按周期上报收益（Reported，含金额与凭证）
  → Admin/平台运营核实（Verified）
  → 确认现实资金已到账（Collected）
  → 扣减约定费用，得到可分配净额（Distributable）
  → 按 Record Date 生成持仓快照（Snapshot），选定本次收益发放币种（单一币种）
  → 生成 Merkle Root 并上链（Distribution）
  → 用户凭 Merkle Proof 自助 Claim（Paid），自付 Gas，永不过期

若 Offering 的"收益发放周期"选择为"无收益"，则不进入上述流程。
5.5 使用型权益的发行与销毁（Usage Core，平台侧最小闭环）
平台完成 Usage Token 发行（Asset Onboarding → Right/Capacity → Offering → 认购，均同前述流程）
  → Token 进入用户持仓（Available）
  → 用户在第三方生态/应用内实际使用与消费（具体消费场景、计量方式、服务内容均由该生态自行设计，不在本平台产品范围内）
  → 第三方生态通过平台开放的标准化销毁接口，对相应数量的 Token 发起核销（Burn）
  → 平台侧记录销毁事件、同步扣减该 Right 的现实 Capacity（Consumed 账）
  → 用户可在持仓页查看销毁/消耗历史（数据来源于链上事件解析）
5.6 退出与熔断（简述）
Offering 到期或触发 Exit Rule 约定条件 → 进入对应退出流程（Redemption/Liquidation/Expiry/UsageBurn）
资产/Offering 出现异常 → Admin 按需触发熔断开关（NORMAL/WARNING/SUSPENDED/CLOSED）
  → 五个开关（新认购/交易/收益分配/使用/赎回）可独立控制，不必须全停

6. 功能需求
模块一：身份与登录
功能 1.1 钱包直连登录
- 功能描述：Web3 用户通过已有钱包直接登录，无需注册账号密码。
- 操作流程：点击"连接钱包" → 选择钱包类型 → 钱包内确认授权 → 检测该地址是否已关联 ONCHAINID → 未关联则创建并绑定 → 登录成功。
- 页面元素：登录入口、钱包选择列表、连接中 Loading、连接失败提示、已连接状态展示。
- 业务规则：一个 ONCHAINID 可绑定多个钱包地址、多条链；同一钱包地址仅可绑定一个 ONCHAINID；平台不持有、不托管用户私钥。
- 成功结果：登录成功，若已有 KYC 记录直接可用，否则进入 KYC 引导。
- 异常情况：钱包插件未安装/未解锁、用户拒绝授权、网络不匹配、连接超时。
功能 1.2 邮箱登录（自持钱包）
- 功能描述：Web2 用户通过邮箱验证码登录，系统自动生成用户自持的嵌入式钱包。
- 操作流程：输入邮箱 → 接收验证码 → 校验通过 → 首次登录自动创建嵌入式钱包与 ONCHAINID → 引导设置恢复方式 → 登录成功。
- 页面元素：邮箱/验证码输入、倒计时重发、恢复方式设置引导（设备绑定/社交恢复/导出备份，至少完成一项）。
- 业务规则：平台侧不落任何私钥/分片；导出私钥/助记词前需二次验证；【产品建议】验证码 5 分钟有效、60 秒内不可重发。
- 成功结果：登录成功并生成/关联 ONCHAINID。
- 异常情况：验证码错误/过期、邮箱格式错误、频繁请求触发限流。
功能 1.3 KYC 材料提交与状态查询
- 功能描述：用户提交身份认证材料，平台/供应商完成审核，结果全局复用。
- 操作流程：填写信息并上传证件 → 提交 → 审核中 → 审核完成更新状态并通知。
- 页面元素：信息表单、证件上传、提交按钮（提交后置灰）、状态卡片（未提交/审核中/已通过/已拒绝，含拒绝原因文案）。
- 业务规则：
  - 一次认证、全平台全链全资产复用；identity/kyc 全局唯一，不按租户隔离。
  - 【已确认】审核被拒后需重新提交材料，系统需写明拒绝原因；【待确认】是否限制重新提交次数或增加冷却时间以防滥用。
  - 审核中不可重复提交新材料。
- 成功结果：状态变为"已通过"，解锁认购等能力。
- 异常情况：上传失败、审核超时、供应商接口异常。
功能 1.4 钱包绑定与解绑管理【新增】
- 功能描述：用户 KYC 通过后，可在同一 ONCHAINID 下追加绑定其他钱包地址，也可解绑已绑定的钱包（当前登录钱包除外）。
- 操作流程：
  - 绑定：进入"钱包管理" → 点击"添加钱包" → 连接目标钱包 → 钱包签名证明地址控制权 → 校验该地址未绑定其他 ONCHAINID → 绑定成功。
  - 解绑：进入"钱包管理" → 选择目标钱包 → 确认解绑（若该钱包名下有持仓/待领收益，弹窗风险提示）→ 解绑成功。
- 页面元素：已绑定钱包列表（含地址、绑定时间、是否为当前登录钱包、持仓概览）、添加钱包按钮、解绑按钮与二次确认弹窗。
- 业务规则：
  - 仅 KYC 已通过用户可使用该功能；未通过 KYC 不开放（因身份尚未与合规资格挂钩）。
  - 【待确认】账号下至少保留 1 个绑定钱包，不可全部解绑；当前登录中的钱包是否允许自我解绑（建议不允许，需切换登录钱包后再解绑）。
  - 新增钱包需签名验证私钥控制权，防止绑定他人地址。
  - 已绑定其他 ONCHAINID 的钱包地址不可重复绑定。
  - 解绑不影响该钱包地址在链上已持有的 Token（Token 仍归属该地址），但解绑后该地址的持仓不再计入本 ONCHAINID 的合并持仓/限额统计。
- 成功结果：钱包列表更新，绑定/解绑生效。
- 异常情况：签名验证失败、目标地址已被其他账户绑定、尝试解绑最后一个钱包被阻止、尝试解绑当前登录钱包被阻止。

模块二：资产登记与发行配置（发行方/Admin）
功能 2.1 发行方入驻与 KYB 认证
- 功能描述：机构主体完成入驻并通过 KYB 审核后方可发起资产登记。
- 操作流程：机构提交主体资质材料（营业执照、受益人信息等）→ Admin 审核 → 通过后开放资产登记入口。
- 业务规则：【已确认】本期发行方仅支持机构主体；个人发行方【待确认，见 14.4】暂不支持，若后续开放需补充个人材料清单与差异化审核规则。
- 成功结果：机构获得发行方权限。
- 异常情况：材料不全/驳回、重复提交同一主体。
功能 2.2 资产登记（Asset Onboarding）
- 功能描述：发行方提交现实资产的基础信息与分类元数据，供平台审核后作为后续发行的载体。
- 操作流程：新建资产 → 按资产类型填写动态元数据表单 → 上传证明材料 → 提交审核 → Admin 审核 → 通过/驳回。
- 页面元素：资产类型选择器、动态元数据表单、材料上传区、审核状态与驳回原因展示。
- 业务规则：资产类型只驱动元数据表单与配置，不隐含固定业务行为；审核中不可创建 Right/Offering；【待确认】通过审核后关键字段修改是否需重新审核。
- 成功结果：资产状态变为"已登记"。
- 异常情况：必填缺失、材料格式不符、重复提交、驳回后修改重提。
功能 2.3 Right 与 Capacity 定义
- 功能描述：为已登记资产定义可对外发行的权益类型（收益型/使用型）及总量上限（Capacity）。
- 操作流程：资产详情下新建 Right → 选择权益类型 → 填写 Capacity 总量与计量单位 → 提交。
- 页面元素：权益类型选择、总量输入、已创建 Right 列表（Total/Reserved/Tokenized/Consumed/Available 五个口径）。
- 业务规则：
  - Offering 创建时按认购上限预占 Reserved；募集失败或 Offering 关闭时释放未使用部分【与 14.6 联动】。
  - Available 为 0 时不可创建新 Offering，或新 Offering 上限不可超过 Available。
  - 同一 Right 下可关联多个 Offering（分期发行）。
- 成功结果：Right 创建成功，Capacity 账本初始化。
- 异常情况：总量非法、并发创建导致 Available 竞态（预占失败即时提示当前可用余量）。
功能 2.4 Offering 发行配置（含资金分配方案）
- 功能描述：基于某个 Right 创建一期具体发行计划，配置发售规则、认购币种、自定义资金分配方案与退出规则。
- 操作流程：选定 Right → 新建 Offering → 配置基本信息/发售规则/认购币种/资金分配方案/收益发放周期/Exit Rule → 提交审核 → Admin 审核 → 通过后按配置时间开售或人工发布。
- 页面元素：Offering 配置表单（分区：基本信息/发售规则/币种/资金分配方案/收益发放周期/退出规则）、分配方案编辑器（可增删分配项，每项为"接收方名称+钱包地址+比例"，末尾固定展示只读的"平台手续费"项）、比例合计校验提示（须=100%）、收益发放周期选择器（无收益/按天/按月/按季度）、预览页、提交按钮。
- 业务规则：
  - Offering 为链下一等对象，链上以 1 Offering = 1 Token 合约或 1 tokenId 映射（详见《合约功能 PRD》）。
  - 发售规则（起止时间、限购、状态、认购币种、分配方案）全部写入链上 OfferingConfig。
  - 费率按 Offering 单独设置。
  - 【已确认，本次新增】收益发放周期：发行方在创建 Offering 时选择"无收益 / 按天 / 按月 / 按季度"之一。选择"无收益"的 Offering（典型如纯 Usage Right 型资产，或发行方明确不做期间性分红）不进入模块四"收益核算与分配"流程；选择按天/按月/按季度的 Offering，系统按对应频率提醒发行方进行收益上报。
  - 【已确认，本次澄清】认购币种为单选：发行方在创建 Offering 时从 Currency Registry 已启用币种中选择唯一一种作为本期认购币种，投资者认购时无需选择、按该币种支付；不同期 Offering 可选择不同币种。
  - 【已确认，本次澄清】收益发放币种同理为单选：每次收益分配（Distribution）时选定唯一一种发放币种，不同期分配可选择不同币种（详见模块四）。
  - 【已确认，本次新增】资金分配方案自由配置：发行方可自定义多个分配项（如 Asset Owner、Operator、发行方自身等），每项指定接收钱包地址与比例；系统自动追加一项平台手续费，其比例由 Admin 后台统一配置，发行方不可编辑、仅可查看；全部分配项（含平台手续费）比例合计必须=100%。
  - 【已确认】Exit Rule 为发行时必填项，缺失不可提交审核。
  - 【已确认，本次澄清】Offering 发布后仅允许修改"结束时间"与"发行状态"（如暂停/关闭），其余字段（含分配方案、认购币种、限购规则等）创建审核通过后不可修改。
  - 单用户认购上限（最小/最大限购）与 Offering 总量上限（等于 Right 预占量）需分别配置，不可混淆。
- 成功结果：Offering 通过审核并按时上线，进入"发售中"状态。
- 异常情况：必填缺失（尤其 Exit Rule、分配方案比例不足/超过100%）导致无法提交、审核驳回、认购币种未在 Currency Registry 启用、发布时间早于当前时间。
功能 2.5 平台手续费配置（Admin）【新增】
- 功能描述：Admin 统一配置平台在认购资金分账中收取的固定手续费比例及归集地址，作为所有 Offering 资金分配方案中不可编辑的固定项。
- 操作流程：Admin 进入手续费配置页 → 设置比例与归集地址（国库合约）→ 保存生效 → 后续新建 Offering 自动带入该固定项。
- 业务规则：
  - 【待确认】手续费比例是否支持按资产类型/发行规模分级配置，还是全局统一比例。
  - 【产品建议】Offering 创建时应锁定当次生效的手续费比例快照，避免已提交审核或已发布的 Offering 因全局配置变更而被动改变分账结果。
- 成功结果：新建 Offering 自动带入当前手续费配置。
- 异常情况：比例设置超出合理范围（如≤0%或>100%）时校验拦截。

模块三：一级市场认购（投资者）
功能 3.1 资产/发行计划浏览
- 功能描述：投资者浏览可认购的资产与发行计划列表及详情。
- 操作流程：进入 Marketplace → 按资产类型/状态筛选 → 进入 Offering 详情页。
- 页面元素：分类 Tab、发行计划卡片（类型、募集进度、剩余额度、状态标签）、详情页（资产介绍、权益说明、发售规则、费率与分配方案说明、认购币种说明、Exit Rule、KPI展示、数据来源说明、认购入口）。
- 业务规则：未 KYC 用户可浏览但认购按钮置灰；已售罄/已结束 Offering 展示对应状态标签。
- 成功结果：用户获取足够信息决定是否认购。
- 异常情况：列表为空、详情加载失败、资产被熔断下架但用户通过旧链接访问。
功能 3.2 认购下单
- 功能描述：投资者对目标 Offering 发起认购，完成链上支付与代币获取。
- 操作流程：见 5.3 节。
- 页面元素：认购数量输入（币种固定展示为该 Offering 唯一认购币种，无需选择）、应付金额与预计到账Token数量实时计算、确认按钮、"等待签名"/"链上确认中"分状态 Loading、成功/失败结果页。
- 业务规则：
  - 前端直连合约，认购在同一笔链上交易内完成"扣款+按分配方案拆分+发币"。
  - 合规校验（KYC、限购、Capacity、发售状态）由合约实时校验。
  - 认购数量需满足单笔最小/最大限购、不超过个人累计限额（【已确认】按自然人/ONCHAINID合并统计，见模块一钱包绑定后的合并口径）、不超过剩余 Capacity。
  - Gas 费由用户承担。
  - 提交后至链上确认前禁止重复提交。
- 成功结果：交易确认成功，Token到账，持仓更新，认购记录生成。
- 异常情况：钱包拒绝签名、余额不足、Gas不足、Capacity并发售罄、Offering提交瞬间被暂停、确认超时、链重组回滚。
功能 3.3 认购结果与持仓展示
- 功能描述：展示用户历史认购记录与当前持仓（按合并后的 ONCHAINID 口径聚合多个已绑定钱包）。
- 操作流程：进入"我的持仓/订单"页 → 查看列表 → 点击查看详情（可跳转区块浏览器核验）。
- 页面元素：订单列表、持仓列表（按资产/Right聚合，注明来自哪个绑定钱包）、区块浏览器跳转链接。
- 业务规则：平台展示数据为链上数据经 Indexer 解析后的投影，与链上保持一致。
- 成功结果：用户可自助核验每一笔认购与持仓。
- 异常情况：Indexer 解析延迟导致短暂展示滞后（见 14.8）。

模块四：收益核算与分配（Revenue Core）
功能 4.1 收益上报
- 功能描述：发行方/Operator 按 Offering 配置的收益发放周期（按天/按月/按季度）上报某 Right 下的现实收益（如租金、分成、算力经营收益）。
- 操作流程：系统按配置周期提醒 → 进入收益管理 → 选择 Right/周期 → 填写收益金额与凭证 → 提交，状态进入 Reported。
- 页面元素：周期选择（受 Offering 配置的发放周期约束）、金额输入、凭证上传、历史上报记录列表。
- 业务规则：
  - 仅"收益发放周期"不为"无收益"的 Offering 需要走本流程；"无收益"的 Offering 不出现在收益上报列表中。
  - 同一 Right 同一周期不可重复上报（需先撤回或走修正流程【待确认修正机制】）。
  - 【待确认】某周期若实际无收益（如淡季），是否要求发行方显式上报"本期收益为0"，还是允许跳过不上报？【产品建议】显式上报0更规范，便于投资者看到"已确认无收益"而非误解为"未上报/失联"。
- 成功结果：生成一条 Reported 记录，等待平台核实。
- 异常情况：凭证缺失、金额为负、重复上报同一周期。
功能 4.2 收益核实与归集确认
- 功能描述：平台运营对上报的收益进行核实，并确认现实资金已到账。
- 操作流程：Admin 审核队列 → 查看凭证 → 核实通过（Verified）→ 确认资金到账（Collected）。
- 页面元素：审核详情页（凭证预览、通过/驳回操作、备注）。
- 业务规则：每一跳独立留痕（操作人、凭证、时间、金额差异说明）；核实与归集为两个独立环节，不可合并跳过。
- 成功结果：状态推进至 Collected。
- 异常情况：凭证不实被驳回、核实中发现金额与凭证不符需发行方补充说明。
功能 4.3 费用扣减与可分配净额确认
- 功能描述：从已归集收益中扣除约定的运营费用等支出项，得到可分配给持仓人的净额。
- 操作流程：Admin 录入 Expense 明细 → 系统计算 Distributable = Collected − Expense → 确认。
- 页面元素：Expense 明细录入表、净额计算结果展示。
- 业务规则：Expense Type 可配置（不同资产类型的费用项不同）；前台需明确展示 Reported / Collected / Distributable 三个口径，不混同展示。
- 成功结果：得到 Distributable 净额，可进入分配环节。
- 异常情况：Expense 超过 Collected 导致净额为负，需阻断并提示核查。
功能 4.4 快照与 Merkle 分配生成
- 功能描述：按 Record Date 生成持仓快照，计算每个持仓人应得份额，选定本次发放币种并生成 Merkle Root 上链。
- 操作流程：选定 Distributable 记录 → 设定 Record Date → 系统生成快照 → 选择本次发放币种（单选）→ 生成 Merkle Root → 提交上链 → 状态进入 Snapshot → Distribution。
- 页面元素：Record Date 选择、发放币种选择器（单选）、快照预览（持仓人数、总份额）、生成结果展示。
- 业务规则：Record Date 之后的持仓变动不影响本次分配资格；发放币种为单选，不同期可不同；生成后不可撤销，如有差错需走【待确认：分配差错的补救机制】。
- 成功结果：Merkle Root 上链，对应资金注入分发合约。
- 异常情况：快照生成时资金未足额注入、发放币种未在 Currency Registry 启用。
功能 4.5 用户 Claim 领取
- 功能描述：用户凭 Merkle Proof 自助领取应得收益，支持跨期跨 Offering 批量领取。
- 操作流程：进入"我的收益" → 查看可领取列表 → 单笔或批量勾选 → 钱包签名 → 广播交易 → 到账。
- 页面元素：可领取金额汇总（按币种分组）、明细列表（来源Offering/期数/金额）、"一键领取全部"按钮、领取历史。
- 业务规则：
  - 【已确认】收益永不过期，用户可随时领取；对应资金常驻分发合约，平台侧无回收接口。
  - Gas 由用户承担。
  - 【产品建议】低于一定阈值的收益自动归集到下一期合并展示，避免用户因 Gas 成本高于收益额而放弃领取（阈值待确认）。
- 成功结果：收益到账，可领取列表更新。
- 异常情况：Gas不足、重复领取被合约拒绝（Merkle Proof 一次性核销）、领取金额过小导致用户放弃（体验提示而非强制限制）。

模块五：使用型权益的发行与销毁能力（Usage Core，平台侧最小闭环）
【已确认，本次澄清】平台对使用型权益的产品边界仅到"发行 + 标准化销毁能力开放 + 销毁记录展示"为止。具体如何冻结、如何计量用量、提供什么服务、消费场景如何设计，均由接入的第三方生态/应用方自行负责，不属于本平台产品设计范围，原方案中"Freeze → External Execution → Usage Confirmed → Consume → Burn"的完整闭环及 Provider 信任模型，简化为下述两项能力。
功能 5.1 标准化销毁（Burn）能力开放
- 功能描述：平台向已获授权的第三方生态/应用方开放标准化的 Usage Token 销毁接口，用于代表现实世界中的一次消费行为对相应数量的 Token 进行核销。
- 操作流程：第三方生态在自身应用内完成一次消费 → 调用平台开放的销毁接口，指定用户身份（或由用户在其应用内以自身钱包发起销毁）与销毁数量 → 平台/合约校验后完成销毁。
- 页面元素：本功能主要面向 B 端生态方，不涉及本平台投资者端页面；具体接口调用方式、鉴权与准入机制见《Open API / SaaS / 白标 PRD》。
- 业务规则：
  - 销毁数量不可超过用户当前持仓。
  - 【待确认，新增】销毁操作的授权模型——是要求终端用户在自己的钱包中直接签名发起销毁（平台不代签，与 F6 原则一致），还是允许已获平台准入资质的生态方持有代为销毁的权限（需要额外的授权/白名单机制）？这决定了销毁接口的调用方式与信任边界，需要产品与技术共同确认。
  - 销毁后同步扣减该 Right 的现实 Capacity（Consumed 账）。
- 成功结果：Token 按实际消费数量完成销毁，Capacity 账本同步更新。
- 异常情况：销毁数量超过持仓被拒绝、未获授权的调用方发起销毁被拒绝、链上交易失败需可重试。
功能 5.2 消耗/销毁记录展示（投资者端）
- 功能描述：投资者可在持仓页查看自己 Usage Token 的历史销毁/消耗记录，用于自助核验。
- 操作流程：进入持仓详情 → 查看"消耗记录"列表 → 可跳转区块浏览器核验单笔销毁交易。
- 页面元素：消耗记录列表（时间、数量、剩余持仓、关联的第三方生态名称【若可获取】）、区块浏览器跳转链接。
- 业务规则：数据来源于链上事件经 Indexer 解析后的投影，平台不解释具体消费内容（如"消费了什么服务"），仅展示"销毁了多少数量、何时销毁"。
- 成功结果：用户可自助核验持仓变动的真实性。
- 异常情况：Indexer 解析延迟导致短暂展示滞后（见14.8）。

模块六：退出与结算（Settlement Core，框架级）
功能 6.1 退出规则配置校验
- 功能描述：确保每个 Offering 在创建时已配置合法的 Exit Rule，作为后续触发退出的依据。
- 业务规则：Exit Rule 类型包括二级转让（Secondary Sale）、现金赎回（Cash Redemption）、资产清算（Asset Liquidation）、权益到期（Right Expiry）、使用型销毁（Usage Burn），发行时必选其一或组合【待确认是否支持多选组合】。
- 说明：【待确认，见14.7】各退出类型的详细触发条件、执行流程、资金来源（尤其现金赎回的资金从何而来）本期仅定义规则框架，具体执行细则需后续专项补充，可能需要单列一份《退出与结算 PRD》。
功能 6.2 到期/触发处理（框架）
- 功能描述：Offering 或 Right 达到 Exit Rule 约定条件（如到期日）时，系统提示 Admin/发行方启动对应退出流程。
- 业务规则：本期仅要求系统能够识别到期时间并发出提醒，具体清算/赎回操作流程待确认后补充。
- 异常情况：到期时仍有未核销的使用型余量、未领取的历史收益，需明确是否影响退出流程的启动（待确认）。

模块七：异常分级熔断
功能 7.1 资产/Offering 状态管理
- 功能描述：Admin 可对资产/Offering 设置 NORMAL / WARNING / SUSPENDED / CLOSED 四级状态，并独立控制五个业务开关。
- 操作流程：Admin 进入资产/Offering 详情 → 选择状态或单独开关 → 填写原因 → 生效。
- 页面元素：状态选择器、五个开关（新认购/二级交易/收益分配/使用兑付/赎回）独立勾选、生效原因记录、变更历史。
- 业务规则：
  - 五个开关相互独立，可仅关闭其中一项而不影响其他（如仅暂停新认购，不影响已持仓用户领取收益）。
  - 【待确认】SUSPENDED 期间已广播未确认的链上交易如何处理（大概率因合约层校验失败而回滚，需前端有对应提示文案）。
- 成功结果：状态/开关生效，对应功能入口在前端相应置灰。
- 异常情况：状态变更与用户正在进行的操作产生竞态（如刚提交认购交易时被暂停）。

8. 业务规则
8.1 金额与数量
- 单笔认购需满足最小/最大限购数量；个人累计认购不超过单户上限。
- Capacity 五账关系：Total ≥ Reserved ≥ Tokenized，Available = Total − Reserved。
- 资金分配方案各项比例（含平台手续费）合计必须=100%。
- 使用型权益的销毁数量不可超过用户当前持仓。
8.2 时间
- Offering 严格按配置的开始/结束时间开放认购。
- 收益发放周期为 Offering 级配置，可选"无收益/按天/按月/按季度"，决定是否进入收益核算流程及上报节奏。
- 收益 Record Date 之后的持仓变动不影响本次分配资格。
- 收益永不过期，可随时 Claim。
- KYC审核时长SLA【待确认】；验证码有效期【产品建议】5分钟。
8.3 权限
- 仅 KYC 已通过用户可发起认购、Claim 收益。
- 仅完成 KYB 的机构发行方可创建资产/Right/Offering。
- 仅平台运营可审核资产、Offering、收益上报，配置平台手续费，执行熔断。
- 平台手续费比例仅 Admin 可配置，发行方不可编辑。
8.4 状态
- 详见第9节状态流转，各状态机不可跳跃、不可逆（终态除外）。
8.5 限制条件
- 认购币种、收益发放币种均为单选（每期可不同）。
- 平台不代签，写操作由前端/API构造待签交易，用户钱包签名。
- 至少保留1个绑定钱包，不可全部解绑。
8.6 计算规则
- 应付金额 = 认购数量 × 单价（单一币种计价，无跨币种汇率换算问题）。
- 分账金额 = 应付金额 × 各分配项比例（含平台手续费项），合约内一次性拆分至各接收地址。
- 可分配净额 Distributable = Collected − Expense。

9. 状态流转
9.1 KYC 状态
未提交 → 审核中 → 已通过
              → 已拒绝 → （用户修改材料）→ 审核中（可反复循环）
已通过状态下不可逆（吊销资格属合规冻结机制，非本PRD范围）
9.2 资产登记状态
草稿 → 待审核 → 已登记
           → 已驳回 → （修改后）→ 待审核
9.3 Offering 状态
草稿 → 待审核 → 已驳回 → （修改后）→ 待审核
             → 已通过 → 待发售 → 发售中
发售中 → 已售罄（Capacity耗尽，自动）
发售中 → 已结束（到达结束时间，自动；发布后可延长结束时间）
发售中/待发售 → 已暂停（Admin人工，可恢复）→ 发售中/待发售
任意状态 → 已关闭（Admin人工，终态）
9.4 认购订单状态
已创建（等待签名）→ 已签名广播（等待链上确认）
已签名广播 → 已确认成功（终态）
已签名广播 → 已失败（终态）
已创建 → 已取消（用户放弃签名，终态）
9.5 收益状态（Revenue Core）
Reported → Verified → Collected → Expense(核算完成) → Distributable
Distributable → Snapshot → Distribution（Merkle Root上链）→ Paid（用户逐笔Claim，非整体状态推进）
9.6 使用型权益状态（Usage Core，平台侧最小闭环）
Available（已发行、在用户持仓中）→ Burn（第三方生态发起销毁，终态）
说明：Freeze / External Execution / Usage Confirmed 等消费过程中的中间状态属于第三方生态自身的业务逻辑，不由平台的产品/数据模型管理，本文档不定义。
9.7 资产/Offering 熔断状态
NORMAL ⇄ WARNING ⇄ SUSPENDED → CLOSED（终态）
（五个业务开关：新认购/交易/收益分配/使用/赎回，独立于上述状态单独可控）

13. 验收标准
正常场景
- 用户完成KYC后可在钱包管理中新增绑定/解绑钱包，合并持仓与限额统计正确更新。
- 机构发行方可完整走通"KYB → 资产登记 → Right创建 → Offering创建（含自定义分配方案+平台手续费只读项）→ 审核通过 → 发售"全流程。
- 投资者可完整走通"浏览 → 认购 → 链上确认（P95≤5s）→ 持仓更新"全流程，资金按分配方案实时到账各接收方。
- 收益可完整走通"上报 → 核实 → 归集 → 扣费 → 快照 → Merkle分配 → 用户Claim"全流程，口径清晰不混同；且仅"收益发放周期"非"无收益"的 Offering 会出现在该流程中。
- 使用型权益可完成"平台发行 → 用户持仓 → 第三方生态调用标准化接口销毁 → 平台记录并展示销毁记录"的最小闭环，平台不参与消费场景本身的判定。
异常场景
- 未通过KYC用户的认购/Claim入口均被禁用，即使绕过前端也应被合约拒绝。
- 资金分配方案比例合计不为100%时无法提交Offering审核。
- Offering售罄瞬间的并发认购不产生超发。
- 未获授权的调用方尝试发起Usage Token销毁应被拒绝。
边界场景
- 认购数量恰好等于最小/最大限购边界值可正常提交。
- 账号仅剩1个绑定钱包时解绑按钮正确置灰。
- 收益金额恰好被Expense全部扣完（Distributable=0）时不生成无意义的Merkle分配。
- 销毁数量恰好等于当前全部持仓时可正常完成销毁，销毁后持仓为0。

14. 风险与待确认事项
14.1 产品风险
- 【产品建议】资金分配方案改为"发行方自由配置多接收方+比例"后，相比原技术方案中"固定66.7%/33.3%两方分账"的设定发生了实质变化（由两方固定比例升级为N方自定义比例+平台固定手续费）。这会直接影响合约层的分账逻辑设计（需支持任意数量接收方而非硬编码两个地址），需与技术团队在《合约功能PRD》中重新确认可行性与上链方式。
14.2 业务风险
- 认购币种与收益币种改为"单选"后，简化了汇率处理问题，但仍需明确：若某资产分多期发行、各期认购币种不同，用户对"为什么不同期要用不同币种支付"的认知成本，建议在Offering详情页显著说明。
14.3 技术依赖
- 认购体验（P95≤5s）依赖Compliance合约与Capacity链上约束已完成开发与审计，属强前置依赖。
- 依赖Indexer服务作为持仓、收益、使用记录展示的唯一数据来源。
14.4 待确认问题（发行方主体）
- 个人是否可作为发行方？若开放，需补充个人材料清单、审核规则及与机构发行方的权限差异。本期默认不支持。
14.5 待确认问题（KYC相关）
- 是否限制KYC重新提交的次数或增加冷却时间，防止恶意反复提交消耗审核资源。
14.6 待确认问题（资金与募集失败）
- 【已部分确认】认购资金按配置的分配方案实时到账（不等待整体募集成功才分账）。
- 【仍待确认】若不存在"最低募集目标"概念，"发行失败"具体指什么场景（如资产权属纠纷、法律合规问题导致中途终止）？一旦触发，已经分账给各接收方（含发行方）的资金是否需要退还、由谁承担退还责任、投资者已获得的Token如何处置？这是一个需要产品、法务共同设计的资金安全网机制。
14.7 待确认问题（Exit Rule 与退出细则）
- 各类 Exit Rule（二级转让/现金赎回/资产清算/权益到期/使用型销毁）的详细触发条件、执行流程、资金来源，本期仅有框架定义，需要后续专项设计，可能需要单独产出《退出与结算 PRD》或并入《合约功能PRD》。
- 到期时若仍有未核销使用量或未领取历史收益，是否影响退出流程的启动时点。
14.8 待确认问题（数据一致性体验）
- Indexer解析延迟导致"链上已确认、平台未更新"窗口期的最大可容忍延迟及前端兜底提示文案。
14.9 待确认问题（使用型权益的销毁授权模型）
- 【已确认，本次澄清】平台对使用型权益的产品边界仅到"发行 + 标准化销毁能力开放"为止，具体消费场景、用量计量、服务内容、Provider信任与仲裁机制均由第三方生态自行负责，不再是本平台的产品设计范畴。
- 【仍待确认】销毁接口的调用权限模型：是要求终端用户在自己钱包中直接签名发起销毁（与平台"不代签"原则一致），还是允许已获平台准入资质的生态方持有代为销毁的权限？若为后者，需要设计生态方的准入审核、权限授予与滥用监控机制。
- 【仍待确认】Exit Rule 中的"使用型销毁"（到期强制销毁剩余未使用 Token）与生态方发起的正常消费销毁是否需要在合约与展示上加以区分（前者是资产退出机制，后者是日常消费），避免用户混淆。
14.10 待确认问题（平台手续费配置）
- 手续费比例是否支持按资产类型/发行规模分级配置，还是统一比例；已创建Offering是否随全局手续费变更而变化，还是创建时锁定快照（产品建议：锁定快照）。

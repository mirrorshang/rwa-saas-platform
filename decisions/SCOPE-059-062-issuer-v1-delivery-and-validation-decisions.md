## 二、对功能矩阵的影响（不改动既定分级）

- **M15-F001～F007：仍保留“交付批次待定”**，但“是否必须与 Issuer V1 同期”现已有明确答案：**不强制同期，单独里程碑**；不等于确定 V2 日期。
- **M16-F001～F007：仍“交付批次待定”**，ARCH-001 已要求 Issuer V1 的内部 API-Ready；M16 完整开发者商用体验仍独立批准上线批次。
- **M05-F005、M10-F001～F008、M11、M12 等持续购买核心闭环维持 V1 优先**；M05-F011、M12-F010 等 P1 继续留在长期架构中，其实际首发范围为**条件性待定**；若首发 Instrument/法域强制则升级所需最小能力。
- **M04、M06、M07、M09、M13 条款/权利/链上与存续能力**继续全球可配置设计，不将日本/中东等候选市场写成已批准首发；**首发参考工具选择之前不得宣布 P1 最终可删或 V1 完全冻结**。
- 187 个 Mxx-Fxxx 原始 ID 及 125 P0 / 21 P1 / 21 P2 / 6 V2 / 14 待定分级记录一律不变。调整的是**交付原则与判定门**，不替代每条功能的 V1 交付深度审批。

## 四、不可逾越的规则

- Issuer SaaS 的 API-First **不等于**首发商业 Open API 已交付，不得为未来 White-label/API 重建第二套发行/认购/配售/Token 核心。
- “持续购买完整支持”必须包含对应的真实支付/对账、异常处置、统一额度、依法登记和链上 Token 交付；不得用虚拟账户余额代替 Token，也不能无条件承诺任意法域合规。
- “集中募集后置”不等于忽略法定必要性；一旦首发工具触发该模式，相关最小业务能力必须重新进入范围审核。
- 未选参考工具/法域之前可以**撰写通用产品 PRD**，但不能冻结依赖它们的最终 V1 必交清单或对外声称金融业务生产获批。
- 冻结第 02/03/04 份历史正文与 DEC-001～011 原文不追溯改写；PR #6 保持 **Draft / Open / Unmerged**，本次不授权开发、合并或金融生产活动。

## 验收矩阵（最低）
- A：已存在/新邮箱；协议未确认；验证码错、过期、已用、重复、频控、网络异常；重新登录草稿恢复。
- B：未创建、草稿、已提交、审核中、补件、未通过、通过；文件扫描失败、过大、重复提交、版本比较；UBO多人及比例校验；联系人邮箱；法律主体变更再审核。
- C：从每个一级/二级菜单点击、输入深链、直接请求API；未认证只显示统一KYB状态；选中态保留；认证后立即恢复已授权页面；状态查询失败默认拒绝。
- D：KYB通过事件重复投递仅一企业一自动MPC开通任务/结果，Provider未知状态先查再试；MPC失败Free仍有效；多个自有钱包逐一签名、地址/网络/重放校验；默认钱包切换不变更旧Offering；解绑限制、并发默认冲突；Offering快照保存。
- E：月/年、USDT/法币；价格缺失时禁止真实订单；支付失败/未到账/迟到账/多付/错网络/重复Webhook；支付确认幂等；自动扣款授权可用/不可用；提醒提前7/3/1/0；取消自动续费不截断已付周期；宽限7天不新发真实Offering；降级业务历史只读；重新订阅恢复。
- 全局：单账户单Tenant；V1无成员角色；所有界面中文；Free无真实资金、真实Token/投资者认购；Standard也需法律和技术门；不得丢失原数据或未经授权迁移真实账。

## 真正实施前的决策/证据门
1. 确定开发目标分支与 commit、当前本地未提交文件（先只读列举），确认旧 Mock 与生产数据迁移/保留策略；不得将 GitHub 远端快照当作本地最新。
2. KYB 审核由谁执行、证据保全/访问控制/数据保护、适用法域及非标准材料流程在生产上线前明确。
3. MPC Provider 与签名/密钥授权责任、企业钱包控制模式、链上地址可用性/网络、自动创建失败恢复、合约钱包签名等需技术、安全及法律批准。**不允许“创建一个随机地址就算真正的 MPC 钱包”。**
4. 订阅最终价格、法币渠道、USDT 网络/Token、报价有效期、税费、支付确认/退款、授权自动续费服务商均需批准后启用真实支付。
5. 既有发行存续保障由谁执行、资金/签名/权限责任及故障处理需要独立落地，不能因为企业降级取消合同义务。

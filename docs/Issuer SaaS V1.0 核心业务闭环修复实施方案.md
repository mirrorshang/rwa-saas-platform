## 0. 审核决定及实施基线门槛

### 0.1 产品负责人已确定的规则

1. **Standard 演示：**使用明确标识的 Mock Standard 升级；不增加复杂计费、不展示虚构价格、不将 Mock 支付写成真实付款或真实订阅生效。
2. **发行确认：**MVP 只用当前企业账号直接确认 Offering，不增加企业内部审批角色；Platform P-15 仅用于未来 M 渠道上架审核，不参与企业资产发行审核。
3. **Mock 认购：**付款确认、配售、模拟持有人登记、Token 模拟交付按独立步骤和状态完成。付款成功不等于合法持有人；模拟持有人记录显示环境及来源。
4. **住宅收益：**案例 `1000 U` 是当期可分配净额；依据 Record Date 有效权益比例计算，保留六位小数、尾差及正式批次防重。
5. **债权计息：**采用 Actual/365 Fixed 和实际计息天数；固定演示日期为起息 `2026-12-01`、首个付息日 `2027-01-01`、到期 `2028-12-01`。`4000 U` 仅是年息除以 12 的简化参考值，不写死月息；不加入复杂节假日、提前还款或违约处理流程。
6. **债权到期：**应付本息模拟支付完成、模拟持有人登记按规则更新、Token 后续处置完成且无未结义务，四项全部成立才显示“模拟清偿完成”。
7. **Project：**首次创建 Offering 时自动建立或关联内部业务容器；企业没有额外的“创建项目”步骤。
8. **状态：**Offering、发行执行、认购销售、Contract、Token 各自保留状态；页面突出当前状态、未完成事项、下一步按钮。不新增没有独立业务意义的 Offering `Pending Issuance`。
9. **Mock 控制区：**创建模拟投资者、模拟支付、模拟登记等测试动作集中到独立测试控制区；正常 SaaS 页面展示业务记录及正常业务操作，避免塞入大量测试按钮。测试控制区须显示环境、租户、可重置范围与操作来源。

这些决定只收口**Mock 演示实施深度**，不把生产法律、支付、法定登记、链上责任或已批准的跨端功能删除。用户本人应确认的条款／声明仍由本人操作。

## 2. 原型内统一对象方案候选（正式应用待重新设计）

**以下仅适用于 `prototypes/website-ui-preview` 内部两套模型的分析，不得直接用于 `apps/issuer`。**在原型内部，Portfolio Asset/Instrument 支持债权且被订单／收益页面引用，适合作为原型统一来源；正式 V1 `apps/issuer` 已有自己的 `AppState` 与 `rwa-issuer-state-v3`，其真实对象、可复用操作和数据迁移需要在产品负责人确认主实现后另作模块 01 设计。

1. 建一个明确的租户级 Issuer 业务仓库接口，统一提供 `Asset → Instrument → Project → Offering` 的创建、按 ID 查询、版本与事务式状态转换。Demo 可使用有版本号的本地仓库；生产适配器将来接权威服务，界面不直接依赖某个浏览器存储键。内部其他模块通过仓库读取统一 ID。所有 Mock 写入带 `environment=sandbox`、tenant、actor、事件时间和意图 ID。
2. 保留已有 Portfolio Asset/Instrument 的 UUID、编号、版本和文件引用。`Project` 为一个 Asset 的工作容器，首次创建 Offering 时原子地创建或复用非归档 Project；Project 1:N Offering，每轮有唯一 `round`。Offering 固定 `assetId/assetVersion`、`instrumentId/instrumentVersion`、`projectId/projectVersion`、权益映射及披露文件版本。确认后不可静默改绑；关键资料变更需新版本、重新检查或新轮次。
3. `OF-0001/OF-0002` 原草稿保留原 ID、显示编号和历史版本；升级为统一 Offering 的 Draft，不因迁移自动 Confirmed 或 Published。旧 `wdex-issuer-issuance` 中若已有独立记录，先按租户、原 ID、来源存储、版本做盘点和冲突清单；仅能确定等价关系的记录可映射，无法确定的保留只读历史并提示人工核对。**不可按相同 `OF-xxxx` 编号自动合并**，因为两套编号策略不同。
4. 迁移只在 Demo 命名空间做一次：先导出／校验原存储，生成迁移清单、旧 ID→统一 ID 映射及校验和，再写新仓库并核对数量、引用、文件可读性、版本连续性。失败保持原记录可读，不删旧键、不修改已关联订单或收益记录。重复运行须幂等。包含 localStorage、sessionStorage 与 Portfolio 文件的 IndexedDB 引用；会话存储失效时明确提示无法恢复，不能伪造历史。
5. `/issuer/assets/:id` 的“新建发行方案”与 `/issuer/offerings/new`、Project／Instrument 详情的入口都调用同一创建命令；列表和详情调用同一查询。统一草稿页提供“确认发行方案”；确认后显示“进入发行准备”，带同一个 Offering ID 到 `/issuer/issuance-check?offeringId=...`。调整路由分流，避免同一路径按两个不同存储对象猜页面。既有门户、Token、订单、资金、报表的 Offering 引用逐一改为统一 ID。

**模块 01 的迁移验收先于任何新增交易数据。**对 A/B 重新打开原草稿仍能看到金额、文件、历史版本；独立发行列表、Project 详情和发行准备识别同一个 ID。全局 ID 唯一、编号按租户单调分配，版本写入校验期望版本；冲突返回可核对结果，不静默覆盖。

## 3. 状态与页面下一步：保持业务维度分离

不把 `Draft/Ready/Pending Issuance/Issuing/Issued` 塞入一个字段。`Pending Issuance` 当前不是 Offering 的独立状态：若意指已发起待执行，展示执行任务的“已提交／待准入”；若只意指准备检查通过，就与 Confirmed 和检查结果重复。本方案不新增该 Offering 状态。`Issuing` 对应执行任务“执行中”，`Issued` 含义不清，界面分别写“Sandbox 已发布”“Contract 模拟成功”“Token 模拟交付已确认”。已批准流程中的审批、异常及长期状态仍保留，若需变更须另行审批。

| 维度 | V1.0 Mock 状态／触发 | 页面展示与下一步；不得混淆的事实 |
| --- | --- | --- |
| Asset | Draft → Ready：保存资料与文件后点“标记资料就绪”；变更后重检 | 资产页显示资料状态；Ready 只可进入权益准备，不等于发行许可 |
| Instrument | Draft → Ready：权益页完成法律依据、容量与映射检查；发布后可显示 Active | 权益页显示独立状态；Ready 可供 Offering 引用，不能代替持有人权益 |
| Project | 自动创建／复用，关联多轮 Offering；归档受存续义务约束 | 项目页显示工作容器及各轮次，不用 Project 的 Active 表示已发行 |
| Offering 确认 | Draft → Confirmed：点“确认发行方案”，固定关联版本并预留容量；有任务或资金事实后不得随意撤销 | 发行方案页显示“已确认 · 进入发行准备”；**不增设 Offering Ready**，草稿资料检查通过显示为检查结果 |
| 发行准备 | 七组检查 PASS/PENDING/BLOCKED/UNKNOWN；责任声明须当前版本有效 | 检查页给出阻断原因和回源按钮；全部 PASS 后才显示可执行的下一步 |
| 执行任务 | 未发起 → submitted → running → verified；另有 pending-admission/failed/unknown | “确认并发起发行”建立唯一 Intent/Task；Unknown 查原任务，不重复模拟部署 |
| Offering 发布／销售 | Confirmed → Published（受控 Sandbox Publication Snapshot）→ Active（窗口及资格满足）→ Ended → Settling → Completed | “已发布”与“认购开放”分开展示；暂停新单不删除已有订单；Completed 需未结义务核清 |
| Contract | 未请求 → Sandbox simulated／failed／unknown；生产链执行另有独立确认中和最终性 | 合约页只能标“模拟 Contract”，不得显示真实地址或“链上部署成功” |
| Token | 方案草稿／待证据、Mint 请求／模拟结果／交付结果分别记录 | Offering 发布不自动 Mint；订单配售、登记、Token 交付分别确认，Mock 记录带环境标识 |

已有 `offeringDomain.ts` 的 `draft→confirmed→published→active→ended→settling→completed` 和 `issuerReadiness.ts` 的 Task 状态可作为规则来源；生产检查目前明确 BLOCKED。界面可在工作台用“资料准备、待执行、模拟已发布、认购中、已结清”摘要减少认知负担，但明细始终呈现对象、环境、版本、证据和下一步按钮。商业 Standard Mock 标签、KYB Mock 通过、模拟钱包均不得打开生产执行通道。

现有业务流程文档还定义了 Offering 的“提交审核／获批准未发布”等长期责任节点。范围 B 的 MVP 按已批准决定由**当前企业账号直接确认**，记录账号、时间、固定版本和确认动作，不增加内部审批角色；这仍只是 Sandbox 确认，不得把 Platform P-15 渠道审核或检查 PASS 误称为真实发行审批。

## 5. 实施顺序、联调门槛与交付检查

**主序 01 → 02 → 03 →（04 与 05）。**模块 01 的统一身份是全部下游前提；模块 02 产生可认购的 Sandbox Publication；模块 03 固定可用名册。04 与 05 可以在模块 03 的快照、批次、支付接口冻结后并行，但不应同时改写同一状态仓库／支付引擎：先由一个负责方完成共享契约和幂等测试，再分别实现租金规则与债权规则，最后做 A/B 串行端到端验收。各模块完成时保留前一模块可运行路径，不用预置办公室情景替代 A/B 验收。

| 关口 | 必须留下的证据 |
| --- | --- |
| 01 → 02 | 迁移报告、A/B 原草稿及文件可读、统一 Project／Offering 列表和版本／容量不变量；不存在两条可修改的同名 Offering |
| 02 → 03 | A/B 各自唯一 Sandbox Task、Contract 模拟结果、Publication Snapshot、Published 与 Active 分离；生产路径始终明确阻断 |
| 03 → 04/05 | 三名投资者 A/B 的订单、模拟付款、配售、登记、Token 交付分别可查；快照按记录日冻结，可复现且跨页金额／权益守恒 |
| 04/05 → V1.0 演示 | 住宅 1000→500/300/200 U；债权按日数计算月息并独立偿还 400000 U 本金。正式模拟批次唯一，失败／部分成功／Unknown 不误报到账；企业能从工作台查完整历史 |

工程验证在未来授权开发后执行：相关领域单元测试覆盖金额精度、版本冲突、幂等、跨期和异常恢复；页面端到端测试用全新可重置租户分别跑 A/B；执行 `build:demo` 与现有测试；最后人工按操作手册逐页核验。不得通过直接改浏览器存储、种子源码或测试脚本伪造页面通过。真实 Provider、真实资金、链上和 V/M/P 联调只做边界检查，不纳入范围 B 的成功结论。

## 6. 已收口规则与尚待确认的代码基线

九项业务决定已写入第 0.1 节，不再把 Mock 价格、企业内部审批角色、住宅可分配净额、固定债权日期及到期四项条件列为待决。Mock 认购按既有主线采用满足条件后的逐笔配售；付款、配售、模拟登记、Token 交付仍各自核验。金额采用六位小数并记录确定性的舍入和尾差；复杂节假日、提前还款、违约处理不加入本轮。

**当前必须由产品负责人确认的实施基线：**是否同意以 `release/v1-engineering-handover-20261116` 的 `apps/issuer` 为 V1.0 唯一主实现，在新开发分支／工作树实施模块 01，并把本地 `prototypes/website-ui-preview` 保留为历史审计与可选择的规则来源。确认后先输出正式应用自身的对象差异和迁移清单，再编码；原型两份草稿的浏览器数据不能未经核验直接写入正式应用。

## 7. 交付边界

此方案中“模拟发行成功”“模拟支付成功”“模拟登记生效”“模拟完成”都要在数据和界面带环境标识，且与真实有权事实分开。继续保留 V 门户预览、M 申请及 P-15/P-16 预留；范围 B 的验收不用它们的真实响应。实施完成的定义是工程师在 **Issuer SaaS 单站点** 使用可重置 Mock 数据，按真实按钮走通两组案例，并能在企业后台追溯每个对象、状态、金额、版本、事件和异常处理结果。

# DEC-012｜交付范围改用 V1.0 / V2.0 / V3.0 版本规划
> **Approved — 2026-10-23，仅版本治理方法。** 产品负责人明确提出：不再在第一版中使用 P0/P1/P2 作为交付承诺，**V1.0 就是首版需要开发、验收、交付的全部功能**；后续回复“V1.0 完整产品闭环 + V2.0/V3.0 后续版本规划”“按你的建议执行”。据此批准新版本管理方法与历史需求的转换流程，并非逐项批准 187 项的归属或 CR-01～10 的实现选择。

## 正式批准的产品版本管理原则
1. **V1.0**：产品负责人逐项批准纳入的**第一版完整交付清单**。列入后按冻结 PRD、验收要求开发交付；不再在 V1.0 内以 P0/P1/P2 混淆“必须开发”和“可选开发”。真实法域/外部执行主体仍是上线前置条件。
2. **V2.0、V3.0**：明确的未来计划版本；经批准后每项功能有唯一目标交付版本。后续版本按商业价值和技术/法域依赖编排，不得简单用旧 P2/V2 标签自动替代。
3. **待规划**：不足以合理承诺任一版本的新功能或独立商业产品，明确为 TBD 并要求后续裁决，不能藏在 V1.0 的“可选”列表里。
4. **历史保留**：187 原 ID、源表的 P0/P1/P2/V2/待定历史分类、SCOPE-001～205 等原决策及 Frozen 基线继续保留原文作为审计历史。**新主表只显示目标版本**，历史分级仅用于迁移对照。版本变化建立追加决策，不回写历史批准事实。
5. **跨版本拆分规则**：同一个原 ID 中的“V1 基础能力”和“V2 高级增强”必须在后续功能规格中拆成**不同且可验收**的交付单元，并明确同源 ID / 新扩展编号。不能把 V1 的最低必要功能改称 V2，以免破坏端到端闭环。
6. **审核顺序**：先集中审阅 Step 02 v0.2 的 [CR-01～10](../docs/04-business-workflows/RWA-SaaS-Step-02-Four-Lane-Core-Flow-Expanded-v0.2-Draft.md)；生成流程图 v0.3；再逐项核对原 187 和新缺口，建立由产品负责人审核通过的唯一版本归属；字段级 PRD 和最终范围冻结在后。流程图 Draft 不等于范围已冻结。
7. **产品形态目标**：V1.0 首发以 Issuer SaaS 的**发行机构开通 → 独立投资者门户 → 合法 Asset/Instrument → Offering 与 Token 受权部署 → 投资者准入/认购/真实支付 → 法定配售/登记/Token 交付 → 募集资金合规结算 → 适用收益分配 → 到期/回购/退出/存续责任**为完整闭环；各节点的具体技术、外部金融权限和支持模型另行审核。
8. **禁止越界**：本决策**不自动变更原 DEC-011 等既有 V1/V2 阶段具体日期或范围**；例如受控二级转让原规划后续（V2），如要移到 V3 必须额外批准。White-label / 商业 Open API 不因为使用相同版号就合并为同一 SaaS 实施模块。
9. **工程状态**：没有批准实际 UI、软件开发、真实资金/链上执行，也不允许合并 [PR #6](https://github.com/mirrorshang/rwa-saas-platform/pull/6)。PR 保持 Draft / Open / Unmerged。

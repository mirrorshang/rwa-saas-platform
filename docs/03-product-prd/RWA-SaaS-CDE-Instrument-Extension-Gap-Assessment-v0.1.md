> **审计范围**：识别 C（基金/集合投资份额）、D（合同收入/版税参与）、E（实物权属/托管凭证）与既有 M01～M22 的**可复用能力、必须配置的差异、未来专有业务缺口**。本稿不构成 C/D/E 生产支持；**不新增正式 Mxx-Fxxx ID、不更改 187 项原分级、不新增第 23 模块，也不把 A/B 验证状态改为 PASS**。

## 一、审查结果总览

- **共用骨架足够**：Tenant、组织权限、Asset/Instrument/Project/Offering、专业文件、投资者/资格、认购、指定链真实稳定币到账与独立对账、审批、配售、法定登记引用、真实 Token 执行、异常与审计的责任划分可长期复用。
- **不能只复用现有普通认购的业务规则**：C 的 NAV 截止/确认与开放式申赎，D 的第三方收入核验及收入分成公式，E 的库存/托管权属证明与提货/兑换都不是 A 的到期还本或 B 的股份/分红直接等价物。
- **有扩展字段 ≠ 有实际支持能力**：可以在产品模型中定义可配置的权利/凭证/生命周期和不可用状态；若某家族尚未建立端到端业务闭环、适格外部主体及法律依据，则发行按钮、公共 API 生产命令与商业宣传须显示未开放/不可用。
- **A/B 范围不膨胀**：已确认的 A/B 两样本继续先完成全量产品需求验证。C/D/E 专有功能属于未来独立增量 PRD/版本门；不能因本报告自动变成 Issuer SaaS V1 交付项。

## 二、22 模块对照表（架构归属分析，非正式新增需求）

标记：**复用** = 共享权限、业务/状态与事件权威不另建；**扩展** = 需将现有可配置边界及字段/审查流程适配到家族；**新能力** = 原 187 项缺少的专用端到端业务能力，未来增量 PRD；**条件** = 首发法域/合规主体/合同和技术依赖未确认。

| 模块/既有 ID 锚点 | C 基金/集合投资份额 | D 合同收益/版税 | E 权属/托管凭证 | 主体责任/后续处理 |
|---|---|---|---|---|
| **M01** 客户开通/授权 | 复用；核查是否需基金管理人/适格发行人 | 复用；核查收入源/合同权利人资格 | 复用；核查托管/资产所有权责任人 | 租户商业授权并不等于获监管许可 |
| **M02** 组织与权限 | 复用；管理人/估值复核权限扩展 | 复用；收入证明提交与审核分权 | 复用；保管人证明与交付操作分权 | 权限 Guard 在服务器端，避免同人自证与审批 |
| **M03** SaaS 平台运营 | 复用；额外合规/服务支持条件 | 复用 | 复用 | 平台客服不承担基金管理或保管职责 |
| **M04-F001/F003/F005/F006/F007** | 扩展法律份额类别、基金文件、份额精度及权利 | 扩展计收口径、分配权利/上限、合同期限 | 扩展实物批次、权属/托管角色、兑换条件 | **M04 仍是 Instrument 权利唯一来源**，不新增资产即等于法定持有人 |
| **M05-F003/F004/F005/F011** | **新能力** NAV 定价/截止时点、申购窗口/确认 | 扩展募集规模/合同分成条款与引用 | 扩展实物单位对应 Token 发行量、赎回条件 | Offering 可复用，但 C 的申赎绝不等同 M05-F005 持续购买 |
| **M06-F003/F004/F006** | 扩展基金合同、说明书、审计/估值证据 | 扩展版税协议、授权范围和第三方收入报告 | 扩展仓单、权属证、保管报告、验真证明 | M06 文书/证据不自动形成权利效力 |
| **M07-F002/F004/F005/F007/F008** | 复用 Token 签名/真实 Mint/限制，可能扩展申赎后供应量 | 复用 Mint/限制，未来按收入权退出规则核验 | 复用 Mint/限制，**新能力**实物提取后的烧毁/权属冲销联动 | 生产执行依适格授权；Token 成功≠法定交割 |

## 五、建议的产品家族支持状态（Draft，具体字段非 API/数据库冻结）

建议在 Instrument **家族×法域×客户授权×合作方能力**层面定义清晰的可用性，而不只是一个 A/B/C/D/E 枚举。四种逻辑能力态供讨论：

1. **Modeled**：有权利分类及字段模型；**不能执行真实发行**。
2. **Validation Only**：可用于产品样例、测试和设计审核；不能冒充生产可用。
3. **Production Eligible**：某个特定 Instrument/法域/发行主体/服务商组合已经通过明确的产品、法律、技术与安全授权；仅对该组合开放对应业务命令。
4. **Disabled / Review Required**：条件不满足、暂停/撤权或权利安排尚待审查；不可被普通 Issuer 或商业 API 绕过。

**重要**：家族可用状态不是监管许可本身；适格许可、法定权威/托管/资金主体、客户适当性、数据隔离与审计仍依实际合规框架验证。即使“Production Eligible”也不能不核对每一次 Offering 的条款、权限、规则版本和法域约束。

## 六、本轮具体结论、后续计划与未决门

- **已确认的上游**：SCOPE-101～108 已批准五类长期产品能力体系；SCOPE-096～100 已批准 A/B 两类产品验证样本；ARCH-001 已确认共用 API-First 核心；SCOPE-059～095 的原 187 项范围归类规则继续有效。
- **本报告新提出但尚未获批**：18 条 GAP-C/D/E 的完整性、按 22 模块的差距归属、家族可用性状态定义以及下一次真正产品化时的增量需求切分。当前只做**分析和假设**。
- **不做**：现在开发基金 NAV、版税结算、托管仓储平台、储备托管、实物提货；不新增正式功能编号、不修改任何 187 项原等级、不决定 C/D/E 上市日，也不宣称 Brickken 的全部资产能力我们已实际支持。
- **下一步建议**：请产品负责人审核此报告，若原则认可则归档为**C/D/E 需求缺口参考基线**（仍不冻结具体增量功能）；随后按已批准的 A/B 验证方案真正梳理债权/权益发行参数与业务闭环，再提出真实 V1 范围冻结候选。
- **待定的重大事项**：C/D/E 的首个目标客户及商业必要性、真实法律定性/法域、适格基金管理/保管/收入审计主体、专用合约与 Token 权利关系、商业 White-label/Open API 发布批次、最终 Issuer V1 功能/API/UI 与开发授权。

**状态：Audit/Draft；上游 SCOPE-101～108 Approved；本报告 GAP-C/D/E 不等于正式新增需求或研发授权。**

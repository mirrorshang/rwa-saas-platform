## 0. 如何使用本文与文档优先级

### 0.1 本文的责任

本文集中回答五个问题：

1. RWA SaaS 是什么产品，由哪些产品端组成；
2. 官网、Issuer 企业工作台、投资者门户、平台后台和外部服务分别负责什么；
3. Issuer 当前九个一级导航、二级入口、五端 125 页面组和原 22 模块 + M23/M24 新增模块如何对应；
4. 官网、企业管理、资产与发行目前完成到什么程度；
5. 后续整体架构、模块产品设计、页面流程字段设计和 UI 工作按什么顺序推进。

本文不复制所有字段级 PRD，也不把所有候选页面、功能模块或历史方案重新写成已批准。每个领域的详细规则继续由对应专项文档承载。

### 0.2 冲突时的优先级

1. **用户最新明确批准的 R2 决策**：U01、U02 的最新批准文件、DEC-057/DEC-058/DEC-059 及后续修订优先，覆盖冲突的旧页面方案或旧套餐规则。
2. **正式 DEC / Frozen 基线**：未被后续明确决定覆盖的部分继续有效；不得静默改写原文。
3. **DEC-017 原 193 项功能主表及原 22 模块 Frozen 功能树**：原正式功能 ID、首次交付版号和模块责任以原文件为准；新增 M23/M24 11 项及 V1 归属按 DEC-057 追加追踪；DEC-058 仅细化既有 M04/M12/M13 页面，不新增功能 ID。
4. **历史 Master PRD**：用于追溯完整背景、其他产品端和跨端业务规则；与最新 R2 决策冲突时，不直接沿用旧描述。
5. **代码、Mock、自测报告**：用于描述实现和验收现状，不反向决定产品需求，也不代表真实生产能力。

### 0.3 状态用语必须区分

| 状态 | 含义 |
|---|---|
| 功能范围已批准 | V1 功能及业务责任已确认，但不代表模块页面设计完成 |
| 模块规划完成 | 模块职责、用户、功能、数据来源、业务流程和与其他模块的关系已明确 |
| 页面/流程/字段设计完成 | 页面入口、信息结构、字段、列表、操作、状态、异常和页面跳转已明确 |
| UI 设计稿完成 | 关键页面已有可审阅的视觉稿或可运行 UI 原型，并完成产品体验确认 |
| 待产品确认 | 推荐方案或候选细节尚未得到用户确认，不得写成现行规则 |
| 开发/生产状态 | 由后续同事独立记录，不作为本阶段产品设计完成的判定依据 |

### 0.4 当前协作边界

本阶段只做产品与 UI 工作：

- 明确产品范围、模块职责、用户、业务对象、数据来源和跨模块关系。
- 梳理业务流程、页面入口、导航、页面信息结构、字段、列表、按钮、弹窗、状态、异常和下一步引导。
- 形成可审阅、可交互的 UI 页面，确保用户易理解、易操作。
- 不规划 API、数据库、合约、Provider、Signer、部署、工程架构或开发排期；这些由后续专业同事负责。
- 一个模块必须先完成产品规划和业务流程，再做页面/字段设计，最后做 UI；不得把功能范围 Approved 或局部字段稿称为整个 SaaS 已 UI-Ready。

**2026-11-10 用户再次确认的固定工作顺序：** V1 范围核对 → 已有官网与 U01/U02 设计收口 → Issuer SaaS 架构与导航/功能完整性 → 逐模块业务流程 → 页面、字段、交互和异常 → 可审核 UI → 全局体验统一。以用户为中心，优先实现简洁、常见、基础的 V1 闭环，不提前抽象 V2 复杂能力；所有新页面文案与交互建议先区分 Approved/Candidate，再进入 UI。此工作原则适用于本项目后续对话。

## 1. 产品定位与总体原则

### 1.1 产品定位

RWA SaaS 是面向资产发行企业、资产管理机构及后续白标/API 客户的**全球标准化多资产 RWA 发行与管理 SaaS**。

V1 首版同时交付发行企业 SaaS、Issuer 独立投资者门户和平台统一投资端：发行机构管理企业准入、资产、权益结构、发行方案、投资者、认购、资金、配售登记、Token 与发行后存续；投资者既可进入单一 Issuer 的 V 门户，也可通过 M 统一入口发现并认购经批准上架的跨 Issuer 一级发行 Offering。

平台提供软件、工作流、资料组织、信息展示和受控技术集成；不因提供 SaaS 而自动成为底层资产所有人、法定发行人、承销商、投资者资金持有人、法定登记人或 Token 签名人。

### 1.2 MVP / V1 产品原则

- 先完成常见、基础、可实际跑通的闭环，避免复杂模型、过度配置和过早抽象。
- Asset、Instrument、Project、Offering、Investor、Subscription、Payment、Allocation、Register、Token、Lifecycle 是不同业务对象，不能因页面合并而混为一体。
- 每个页面应让用户看懂当前状态、缺少什么、下一步做什么。
- 页面导航尽量简洁；复杂业务对象可保留底层身份，但不要求全部变成独立菜单。
- V1 包含基础跨 Issuer 一级发行聚合和统一投资者账户；复杂资产模板、复杂权益分层、复杂审批、受控二级转让、高级白标及商业 API 按正式版本规划后置。
- USDable 仅作为功能列表、页面结构、字段和交互参考；不复制多方比例分账、Usage Right、TOTP、套餐硬配额或二级交易。
- 资料完整、内部 Ready、Standard 订阅有效均不等于真实发行合法或生产准入通过。

### 1.3 全局金额与网络口径

- 平台业务金额 UI 统一显示单位 **U**，按 USDT 计价。
- V1.0 投资者认购付款暂仅支持 **OP Mainnet（Optimism）USDT**。
- V1 每个 Offering 选择一个企业已配置的有效钱包作为最终收款钱包；不建立独立收款方名录，不支持多收款方比例分账。
- SaaS 商业订阅付款与投资者认购资金是两条独立资金链；商业订阅可选择 USDT 或法币，实际 Provider、商户、网络及收款准入另行核验。
- 不得把 SaaS 订阅费用、投资者认购资金、发行后收益/本息资金混成同一资金账户或业务状态。

## 2. 总体产品端架构

当前产品规划按职责区分以下产品端/渠道。它们不是同一个后台的不同菜单，也不意味着所有端都已开发或生产开放。

| 产品端/渠道 | 主要用户 | 核心责任 | 当前范围说明 |
|---|---|---|---|
| **W｜SaaS 官网** | 潜在发行企业、资产管理机构、访客及投资者访客 | 产品介绍、解决方案、套餐说明、帮助咨询、企业登录与开通入口；提供依法公开的 M 投资机会入口 | W-01～W-14 中文前端页面组已有实现和 Mock 测试记录；M 投资机会入口按 DEC-046/057 纳入 V1 范围，实际入口改造与生产发布仍需独立验收；真实注册、邮件、KYB、支付和正式法律内容仍需独立接入/发布验收 |
| **I｜Issuer 企业 SaaS 工作台** | 发行企业/资产管理机构 | 企业管理、资产与发行、投资者与认购、资金、Token、收益和报表 | 当前首要产品端；现行九个一级导航见第 4 章 |
| **V｜发行机构自己的投资者门户** | 该发行机构的投资者 | 该机构授权 Offering 展示、投资者登录/资格、认购、持仓、收益、文件与通知 | 与 Issuer 后台分离；Issuer 的门户设置入口为 I-13 |
| **M｜平台统一投资者入口/分发渠道** | 跨发行机构寻找投资机会的投资者 | 汇总展示经批准上架的 Offering，提供 M 统一账户、跨 Issuer 资格/认购、本人订单/持仓/收益查询 | **V1 产品范围已由 DEC-057 批准**；M23/M24 共 11 项纳入 V1，M-01～M-16 页面组纳入 V1 IA；详细 UI-Ready、开发、独立验收和生产准入仍待完成 |
| **P｜SaaS 平台运营后台** | SaaS 平台内部运营人员 | 租户/商业开通、平台运营、服务状态、受控支持、审计与平台规则 | 不复制 Issuer 的资产、资金、Token、法定登记等权威业务主账 |
| **X｜外部服务与合法责任主体** | 外部服务商/合作主体 | KYC/KYB、AML、签署、支付/资金、托管、钱包/Signer、链节点、法定登记等 | 是外部服务与责任协作边界，不默认建设成新的 SaaS 产品端 |

### 2.1 必须区分的两个投资者入口

- **V：Issuer 自有投资者门户**——某发行机构自己的门户，只展示该 Issuer 有权展示的 Offering。
- **M：平台统一投资者入口**——V1 跨 Issuer 一级发行聚合/分发渠道，需独立的 Offering 上架审核、披露授权、平台责任、投资者统一身份/资格编排和生产准入；不包含二级交易。

Issuer 的 I-13 是管理自身 V 门户的后台入口，不等于 M 平台运营后台，也不等于 Offering 已自动上架 M。

### 3.2 U01｜企业管理、账号、KYB、钱包与订阅

**当前产品基线：**

1. 登录采用邮箱 + 一次性验证码；不设置独立注册流程，首次邮箱认证自动建立账号并登录。
2. MVP 一个账号对应一个企业 Tenant；不做多企业切换、团队成员、角色权限和企业内审批分权。
3. 登录后工作台导航可见；企业 KYB 未通过时，业务内容由统一认证状态页拦截，不泄露业务详情。
4. 企业 KYB 采用五步：企业基本信息 → 企业业务信息 → 企业关联人员 → 企业证明材料 → 预览与确认提交；支持草稿、提交、审核、补件和版本追溯。
5. Free 与 Standard 共用工作台结构；KYB 均需完成。Free 可真实创建和保存资产、权益结构、发行方案等准备资料，但不能真实部署/Mint、公开上架、生成对外投资者门户、开展认购募资、持仓或收益运营。
6. Standard 在订阅有效且满足适用法律、发行、资金、Provider、Signer、网络和安全生产准入后，才开放对应真实业务能力；付费不等于发行许可。
7. KYB 通过后按已批准规则启动企业 MPC 钱包分配；可关联并验证企业自有钱包，发行时必须明确选择收款钱包。真实 MPC Provider 与密钥/Signer 生产准入独立于页面实现。
8. SaaS 订阅支持月/年周期、USDT/法币选择、自动续费、提醒、宽限期和降级/恢复规则；订阅资金与投资者认购资金隔离。

**当前产品设计判断：**

- U01 的账号、KYB、企业管理、钱包和订阅业务规则及主要页面流程已基本完整；本轮不重新设计其业务模型和企业管理导航。
- KYB 页面字段以已批准的 v0.3 五步版本为准，旧五步字段版本不再作为当前产品依据。
- 官网旧注册、企业开通、多企业选择和 Standard 升级说明与现行 U01 规则存在差异，须按单账号单企业、邮箱验证码首次自动建号、创建企业即进入 KYB、KYB 通过后激活 Free、月/年及 USDT/法币订阅进行统一。
- U01 专项 PRD 是企业入驻流程的规则权威；官网入口和营销说明必须引用该流程，不另造第二套注册/KYB/订阅路径。

### 3.3 U02｜资产管理、权益结构与发行

**当前产品基线：资产与发行采用集中式工作流程，不再恢复旧的五个独立二级菜单。**

#### 3.3.1 导航与资产详情

「资产与发行」仅保留三个二级入口：

1. **资产管理**：资产列表、创建、编辑、资产详情。
2. **认购记录**：跨资产、跨 Offering 查询认购记录。
3. **锁仓记录**：跨资产查询锁仓、解锁时间和状态。

选择资产后进入资产详情，固定四个顶部 TAB：

| TAB | 责任 |
|---|---|
| **资产概览** | 资产摘要、准备进度、阻断原因、唯一清晰的下一步操作 |
| **资产资料** | 基础信息、资产类型专属字段、权属/法律/估值材料、图片与文件版本 |
| **权益结构** | 该资产唯一当前有效 Instrument 的定义、Token 拆分、授权容量、版本 |
| **发行管理** | 该资产关联的多个 Offering，创建/编辑/准备/预览/发布及发行状态 |

以下旧方案不再作为前台独立二级入口：权益结构、项目管理、发行方案、发行准备、文件中心。它们的底层业务责任保留，但通过资产详情 TAB、Offering 页面和具体业务上下文承载。

**资产与权益结构设计状态：** 资产五步流程、公共字段和首批四模板已形成详细规则；子类单位/精度/部分控件与资产相关方整合仍待产品/UI 收口。Instrument 核心结构已明确，但主体选择、收益参与期限、版本编辑等仍有候选细节。

#### 3.3.2 Asset 资产分类与 MVP 模板

- 分类目录：8 大一级资产类别、24 个二级分类。
- MVP 先实现房地产基础闭环；首批开放住宅、写字楼、商铺、工业园/仓储物流四类模板。
- 资产相关方（SPV/资产持有主体、托管方、受托方、管理/运营方、估值机构及其他适用主体）已纳入 V1；角色卡片字段需整合到创建第③步和资产资料详情。
- 酒店、土地分类保留但暂缓实际模板开放；房地产不包含在建项目、期房或开发融资模板。
- 资产创建采用五步向导：分类 → 基础信息 → 法律与估值 → 子类专属属性 → 预览提交。
- 字段按全平台基础字段、一级资产类别公共字段、二级资产子类专属字段组织；不得用万能表单强制不同资产类型填写不适用字段。
- 必须文件单独列出并紧跟上传入口；选填材料按需添加；文件版本和历史引用可追溯。

#### 3.3.3 Instrument 权益结构

- MVP 一项 Asset 最多一套当前有效 Instrument。
- 股权、债权、收益参与权三类模板三选一；复杂混合、分层和多 Instrument 延后。
- 权益结构采用单页面三区域：权益定义、Token 拆分、法律文件。
- 用户填写权益总规模和 Token 份数，系统计算每 Token 对应权益量。
- 预期年化信息披露与债权周期付息已纳入 V1（DEC-059）；适用权益类型、具体字段、频率、日期规则、计息方法、披露文案及 M13 事件细节仍待 Instrument / M13 模块产品设计确认。
- 计算不能整除或缺少可靠精度规则时拒绝静默舍入。
- 多期 Offering 可引用同一 Instrument 的确定版本，并共享其授权容量；历史 Offering 不得因后续编辑而静默改变引用版本。

**Offering 设计状态：** R01～R36 业务规则已批准，但现有单页字段/UI 规格仍是候选稿；页面信息层级、字段控件、状态操作、空态/错误态、弹窗、最终投资者预览和跨页跳转仍需完成产品/UI 确认。

### 3.3.4 Project 与 Offering

- Project 保留为内部业务关联对象/容器；用户不需要单独从一级或二级导航创建 Project。
- 从资产详情创建 Offering 时，系统自动维护必要的 Project 关联。
- 一个 Asset 可以有多个 Offering；每一期 Offering 有独立发行参数、价格、时间、投资者条件、状态和历史快照。
- 只有当前 Asset 的 Instrument 完成 Ready 检查，且关键文件扫描成功、引用版本有效时，才允许创建 Offering Draft。
- Offering 使用单页分区编辑：A 发行信息、B 投资者认购条件、C 发行准备。
- 发行准备纳入 Offering 自身流程；不再单独建设「发行准备」二级菜单。
- Offering 详情提供常驻「预览投资者端」入口；发布前还须完成「最终预览与确认」。
- 预览读取当前真实配置，不得虚构募集进度、收益、订单或持仓。
- Free 可以完成业务资料准备和内部只读预览；不能真实发布、公开上架、部署合约、收款或 Mint。
- Standard 真实发布仍需全部独立生产准入。

**领域主账边界：**

- M09 负责身份核验结果与具体 Offering 资格决定。
- M10 负责认购订单与订单状态。
- M11 负责支付指令、到账证据、对账和退款状态。
- M12 负责配售决定及权威持有人登记引用。
- M07 负责 Token、合约和链上交易事实。
- M13 负责发行后权益事件、收益上报、应付收益/本息、基于 InstrumentVersion 的周期付息事件、清退/兑付计划、分配与清偿核验。
- M01 负责 SaaS 商业订阅，绝不与 M11/M13 投资者资金混账。
- M17/M18/M20/M21 负责协调、通知、审计和只读汇总，不覆盖上述领域主账。

- M 与 V 共用唯一订单、支付、配售、法定登记、Token 和收益事实；V 账户及历史持仓不会自动迁入 M。

## 6. 从企业入驻到发行后管理的端到端主流程

1. **官网获客与进入工作台**：访客了解产品、Free/Standard 和业务能力；通过邮箱验证码进入企业工作台。
2. **企业创建与 KYB**：创建企业、提交五步 KYB；通过后开放相应 Free 资料准备能力。
3. **企业管理与订阅**：管理企业资料、钱包和套餐；Standard 订阅有效仅代表商业权益，不代表生产发行许可。
4. **资产准备**：创建 Asset，按对应资产模板填写资料、上传权属和法律/估值材料，保存 Draft 并完成 Ready 检查。
5. **权益结构准备**：为该 Asset 建立唯一当前 Instrument，确定股权/债权/收益参与权类型、权益规模、Token 拆分及文件版本。
6. **发行方案准备**：从资产详情创建 Offering，自动维护 Project 关联；配置发行数量、单价 U、认购时间、投资者准入、收款钱包和文件；执行发行准备检查与最终投资者端预览。
7. **投资者展示与认购**：Issuer 可将 Offering 发布至自有 V 门户，并按单个 Offering 自愿申请 M 统一投资渠道；P 独立审核 M 渠道。投资者可从 V 或 M 进入，完成各自账户、资料授权、身份核验、逐 Offering 资格、认购和必要签署。M/V 账户独立，交易主账共享。
8. **资金、配售、登记与 Token**：由有权主体处理付款和资金事实；平台分别核对到账、订单、配售、法定登记与 Token 交付，不能把任一环节成功推断为全部完成。
9. **发行后存续**：维护 RecordDate/权益快照、收益计算、真实注资、分配与领取、到期、赎回、逾期和责任交接。

跨端入口、状态和异常必须返回原业务对象；任何“已读、已处理、Provider 恢复、工单关闭”都不能自动改变资金、登记、Token 或法律权利事实。

## 8. 后续整体架构与产品设计工作路线

新阶段先做整体架构完整性收口，再逐模块做详细产品设计，不重新打开已批准的官网、U01 和 U02 基础结论。

### 阶段 A｜整体架构完整性审核

- 复核 W/I/V/M/P/X 的边界、用户、入口、数据与责任主体。
- 复核五端 125 页面组：W14、I63、M16、V15、P17；页面组范围不代表 UI-Ready 或已开发。
- 复核原 M01～M22 Frozen 模块及 M23/M24 新增模块到五端、导航和页面组的映射。
- 与原 193 项正式功能及 DEC-057 新增 11 项做双向覆盖检查：功能是否有页面入口，页面是否有明确功能责任；当前 V1 为 157 项。
- 识别遗漏、重复、归属错误、跨端断点、业务主账重复和不必要导航。
- 不为了“看起来完整”而新增功能 ID、一级菜单、复杂业务模型或未批准生产能力。

### 阶段 B｜逐模块产品规划与业务流程设计

建议按业务依赖推进：

1. 投资者门户：I-13 管理端 + V 投资者前台，明确与 M 统一渠道的区别。
2. 投资者与认购：I-41～I-48，完成投资者、资格、订单、配售和登记闭环。
3. 资金与结算：I-49～I-53，完成收款、到账、退款、募集款结算的页面和责任边界。
4. Token 管理：I-37～I-40，完成合约、部署申请、Mint/交付、链上对账。
5. 收益与分配：I-54～I-58，完成存续、RecordDate、收益上报、收益计算/复核、注资、Claim/Push 对账、清退/兑付、到期退出。
6. 数据与共享能力：I-59～I-66，完成待办、异常、通知、规则、审计、报表、外部服务和安全。
7. P 平台后台：补齐平台运营页面、平台级权限、服务管理和责任边界。
8. M 统一投资端：产品范围已由 DEC-057 批准纳入 V1；下一步完善 M23/M24 字段级 PRD、跨 Issuer 账户/授权/资格、上架审核、M/V 共享订单路由和跨端验收，不混入 Issuer 自有门户。
9. USDable 参考项：DEC-058 已批准补齐 M04 资产相关方、M12 持有人管理、M13 收益上报及清退/兑付的 V1 UI-Ready；多方分账/Usage Right 后置 V2，TOTP/套餐硬配额/强制转账不纳入。

### 阶段 C｜页面、字段与 UI 设计交付

- 绘制 W/I/V/M/P/X 的端到端泳道流程。
- 对每个关键状态核对数据来源、主账归属、动作权限、通知、异常和恢复路径。
- 每个模块完成产品规划后，再逐页确定页面结构、中文字段、列表、表单、按钮、弹窗、状态、空态/错误态、权限、跳转和异常。
- 页面与流程确认后制作可审阅的 UI 原型/视觉稿；全 SaaS 产品设计完成后，再统一做体验收口。
- 本阶段不规划技术开发，不把 UI 设计完成等同于真实业务或生产能力。

Open API / SaaS 开放平台 / 白标

1. 需求背景
1.1 为什么做
平台定位从"自营应用"升级为"多资产 RWA 基础设施 + 对外发行 SaaS"，自营发行只是标杆案例而非产品主体。PRD-01/02/03 已经把身份、一级市场、二级市场、合约层的业务能力建设完成，但这些能力目前只服务于平台自营前端。若不建设一层可对外开放、可管理发行方数据权限与配额、可计量计费的"开放层"，SaaS 商业模式无法成立，平台仍然只是一个自营应用。
1.2 当前存在的问题
- 没有对外的 API 契约、SDK、沙箱、开发者文档，外部客户无法自主接入。
- 没有发行方后台数据权限管理能力，多个发行方接入后台数据会互相串数据，无法支撑白标与纯 API 两种交付形态并存。
- 缺少 API 版本管理与弃用策略，一旦有外部客户接入，任何接口调整都可能造成客户生产环境事故。
- 缺少用量计量能力，无法支撑按调用量/规模计费的商业模式。
1.3 解决什么问题
建立统一的 API Gateway（鉴权、发行方数据权限、限流配额、版本管理），配套 SDK、沙箱、开发者门户，支撑"白标"与"纯 API 接入"两种对外交付形态，同时通过 Dogfooding 机制强制自营前端与外部客户使用同一套公开 API，保证 API 覆盖面与产品覆盖面一致。
【已确认，本次澄清，取代此前版本的"多租户隔离"设计】"多租户"在本平台的实际含义远比常规 SaaS 更收窄，具体为：
- 发行方后台数据按归属隔离：每个发行方（无论自营、白标客户还是纯 API 客户）在其管理后台中，只能看到、管理自己名下登记的资产、Right、Offering、募集与认购数据。这本质是基于"资产归属"的行级权限，而非独立的租户数据孤岛。
- 一级市场投资端全平台统一、不隔离：任意投资者只要满足合规条件（KYC/Eligibility），均可浏览并投资平台上任意发行方发布的资产，不因访问入口（自营 App / 白标前端 / 客户自研前端）不同而看到不同的资产池。
- 二级市场（AMM + C2C）全平台统一、不隔离：所有资产在同一个公共市场中流通与撮合，不按发行方、客户或接入渠道做任何分区。
因此，白标与纯 API 客户获得的核心价值是"品牌化/自主化的发行与获客入口"，而非"一个与其他客户流动性隔离的专属小平台"——这一点需要在商务对外沟通中如实说明。

2. 产品目标
2.1 业务目标
- 建立 SaaS 收入结构（在"发行费 + 资产运营服务费 + 交易手续费"之外，新增订阅费/API调用计费/规模抽成等可能形式，具体计费模式见 14.1 待确认）。
- 首个白标客户与首个纯 API 客户完成上线，验证两种交付形态均可独立运转。
- 通过 Dogfooding 门禁保证"我们自己用不起来的 API，客户一定用不起来"，避免 SaaS 退化为项目制交付。
2.2 用户目标
- 纯 API 客户（外部开发者）：仅凭文档与沙箱、无需人工支持即可完成"发行→认购→Claim"全流程联调。
- 白标客户：不写代码，只需配置主题与域名即可上线，获得与自营前端一致的产品体验。
- 平台运营：能够自助化开通新租户（目标：1个工作日内完成），掌握每个租户的用量、配额与合规风险。

4. 需求范围
4.1 本期做什么
1. API Gateway：API Key/OAuth 鉴权、多租户路由、限流配额、统一错误码、幂等中间件。
2. Open API 能力开放：覆盖 PRD-01/02 定义的投资者侧与发行方侧全部业务能力，且自营前端与客户前端调用完全相同的公开 API（Dogfooding）。
3. Webhook 事件推送：KYC 状态变更、认购成功、收益可领取、成交、赎回等关键事件。
4. JS/TS SDK：封装待签交易的构造、签名唤起与广播。
5. 沙箱环境：测试网 + 模拟数据 + 测试 API Key，客户零成本联调。
6. 开发者门户：API Key 自助申请、用量与配额看板、OpenAPI 自动生成文档、变更公告订阅。
7. 发行方数据权限与市场统一性模型：身份/KYC 全局共享；发行方后台数据按归属过滤（谁的资产谁管理）；一级市场投资端与二级市场均为全平台统一公开市场，不做任何隔离。
8. 白标交付：复用平台前端（投资者端 + Issuer Console），仅换主题与域名，不做租户级功能定制；投资端模块展示全平台统一数据。
9. API 版本管理与弃用策略：/v1 路径版本化，破坏性变更需并行期与提前通知。
10. 接入方生命周期管理（Admin）：新接入方开通、配额配置、暂停/注销。
11. 用量计量埋点：为后续计费模式落地预留数据基础（计费模式本身见待确认）。
4.2 本期不做
- 具体计费账单系统与扣费流程（计费模式确定后再展开，见 14.1）。
- 任何形式的一级/二级市场按发行方或接入方的隔离机制（【已确认，本次澄清】不存在"独立租户市场"的产品形态，故本期及可预见未来均不做，不再作为待评估项）。
- 跨链能力（见 PRD-01 范围声明，本期默认单链）。
- RWA-native 私链（不排期，架构上不写死单链假设即可）。
- 租户级功能定制开发（白标只做主题+域名+权限+配额，有定制需求引导客户走纯 API 自研前端）。

5. 产品流程
5.1 纯 API 客户接入流程
客户在开发者门户注册账号 → 申请沙箱环境 API Key
  → 在沙箱环境使用文档 + SDK 自主完成联调（身份/KYC提交/认购/持仓/Claim/二级交易全流程）
  → 联调通过后，客户提交正式租户开通申请（含资质材料）
  → Admin 审核通过 → 开通正式租户，分配正式环境 API Key
  → 客户切换至正式环境上线
5.2 白标客户上线流程
客户提交白标合作意向 → Admin 审核资质
  → 通过后，Admin 在租户管理后台创建新租户
       → 配置主题（复用 PRD-01 C1 的 Design Token）、域名绑定
       → 分配该租户的 Issuer Console 与投资者端访问权限
  → 客户在自己的域名下即可看到已换肤的平台前端，无需写代码
  → 客户在 Issuer Console 中自助完成资产发行配置（复用 PRD-01 全部流程），该控制台只展示客户自己名下的资产与认购数据
  → 客户品牌前端中的"投资端"模块（Marketplace、二级市场）展示的是全平台统一的资产池与市场数据，与自营前端完全一致，不做任何隔离或收窄
5.3 租户开通流程（Admin 视角）
Admin 收到租户开通申请（含交付形态：白标/纯API）
  → 审核资质材料 → 通过后创建租户记录
  → 配置：租户配额（API调用限流/资产数量上限等）、计费方式【待确认，见14.1】
  → 若为白标：额外配置主题与域名
  → 租户状态变为"已开通"，通知客户
5.4 API 版本变更流程
平台需发布破坏性变更
  → 新增版本路径（如 /v2），旧版本 /v1 进入"已弃用"状态但继续可用
  → 通过开发者门户与 Webhook 提前通知所有订阅该接口的租户
  → 并行期结束后（时长见待确认）下线旧版本

6. 功能需求
模块一：API Gateway 与鉴权
功能 1.1 API Key / OAuth 鉴权
- 功能描述：为每个租户/开发者分配独立的 API Key 或 OAuth 凭证，作为调用 Open API 的身份凭证。
- 操作流程：开发者在开发者门户申请 → 系统生成 Key/Secret（或 OAuth Client ID/Secret）→ 开发者在调用时携带凭证。
- 业务规则：
  - 每个凭证唯一关联一个 tenant_id，网关据此识别调用方的发行方归属，作为后台管理类接口的数据权限过滤依据（不影响投资端/二级市场类接口，详见功能1.2、模块七）。
  - 【待确认】沙箱环境与正式环境的 Key 是否严格隔离（不允许沙箱 Key 访问正式数据，反之亦然）——【产品建议】必须严格隔离，避免测试数据污染生产环境。
  - 支持凭证轮换（Key 过期/重新生成），旧凭证在轮换后的宽限期内仍可用一段时间以避免客户服务中断。
- 成功结果：合法凭证的请求被正确路由到对应租户的数据域。
- 异常情况：凭证无效/过期/被吊销时返回统一的鉴权失败错误码。
功能 1.2 发行方数据权限路由
- 功能描述：网关根据请求凭证识别调用方所属的发行主体（tenant_id，本文档中其含义是"发行方/接入方归属标识"，用于后台管理数据的权限过滤与商务归因，不代表业务数据的强制隔离维度），仅对"发行方后台管理类"请求做归属过滤。
- 业务规则：
  - 【已确认，本次澄清，取代此前"所有业务数据强制按租户隔离"的设计】tenant_id 归属过滤仅作用于发行方后台管理类接口（资产/Right/Offering 的创建与管理、募集与认购数据查看等）——发行方只能查询/操作自己名下的数据。
  - 【已确认，本次澄清】一级市场投资端（资产浏览、认购）与二级市场（AMM/C2C）相关接口不做 tenant_id 过滤，任意调用方（无论走自营 App、白标前端还是客户自研前端）拿到的都是全平台统一的公开数据。
  - 身份/KYC 类接口同样不做归属过滤（全局共享），通过 tenant_user 关系记录用户来源渠道，仅用于归因统计，不影响该用户能访问的资产/市场范围。
- 成功结果：发行方后台数据不互相泄露，同时投资端与二级市场保持全平台统一体验，不产生流动性碎片化。
- 异常情况：发行方尝试查询/操作非自己名下的资产或认购数据应被拒绝并记录审计日志。
功能 1.3 限流与配额
- 功能描述：按租户配置 API 调用频率限制与资源配额（如资产数量上限、API 调用次数/秒）。
- 操作流程：Admin 在租户配置中设置配额 → 网关按配额执行限流 → 超出配额的请求被拒绝或降级。
- 业务规则：【待确认】超出配额后的行为——直接拒绝（429）还是降级排队？不同交付形态（白标/纯API）是否需要不同的默认配额档位。
- 成功结果：单一租户的异常调用不会影响其他租户或平台整体稳定性。
- 异常情况：配额配置错误导致正常客户被误限流，需要 Admin 可快速调整。
功能 1.4 统一错误码与幂等中间件
- 功能描述：为所有写操作提供统一的错误码规范与幂等键支持（防止网络重试导致重复提交）。
- 业务规则：写操作（认购、Claim、挂单、成交等）必须支持客户端传入幂等键，网关/后端保证同一幂等键的重复请求不会产生重复副作用。
- 成功结果：客户端可安全地进行网络异常后的重试。
- 异常情况：幂等键冲突但请求参数不同时应返回明确的冲突错误，而非静默使用首次请求的结果。

模块二：Open API 能力开放
功能 2.1 六类 API 能力域
- 功能描述：对外开放的 API 按能力域划分为 Identity / Asset / Offering / Order / Compliance / Blockchain 六类，覆盖 PRD-01/02 定义的投资者侧与发行方侧全部业务能力。
- 业务规则：
  - 【已确认】API 覆盖面必须包含投资者侧全流程：资产与 Offering 浏览、KYC 材料提交与状态查询、认购、持仓、收益 Claim、二级挂单/撤单/成交、赎回；不能只覆盖发行方后台接口。
  - 【已确认】自营前端与客户前端调用完全相同的公开 API（Dogfooding），不为自营保留私有接口。
  - 【已确认】边界：API 只开放"界面所需的数据与操作"，不开放基础设施的替换权——身份、KYC 结论、合规规则均无客户侧写入口（承接 PRD-01 B1）。
  - 【已确认】写操作（认购、Claim、挂单、成交、赎回）API 只负责校验参数、构造待签数据（calldata / EIP-712）并返回，不代签、不代持。
- 成功结果：客户仅凭 API 文档即可搭建出功能完整的产品，不需要向平台申请额外的定制接口。
- 异常情况：若发现某个自营前端功能背后没有对应公开接口，视为 Dogfooding 门禁违规，需要立即补齐或下线该自营功能。
功能 2.2 OpenAPI 文档自动生成
- 功能描述：API 契约以 OpenAPI 规范文件为唯一来源，文档站点自动生成，避免文档与实现漂移。
- 业务规则：接口变更必须先更新 OpenAPI 文件，文档与 SDK 均从该文件自动生成，不允许手工维护文档导致的不一致。
- 成功结果：文档始终与实际接口行为一致。
- 异常情况：OpenAPI 文件与实际部署接口不一致时应有 CI 校验拦截发布。

模块三：Webhook 事件推送
功能 3.1 事件订阅管理
- 功能描述：客户可在开发者门户订阅感兴趣的事件类型，平台在事件发生时主动推送。
- 操作流程：开发者门户 → 创建 Webhook 订阅 → 填写回调 URL、选择事件类型 → 保存 → 平台后续按事件推送。
- 页面元素：事件类型多选（KYC状态变更/认购成功/收益可领取/成交/赎回等）、回调URL输入、密钥签名展示（用于客户验证推送来源真实性）、推送日志与重试记录。
- 业务规则：
  - 推送失败需有重试机制，重试次数与间隔【待确认】，超过重试上限后需要客户可在门户中查看失败记录并手动重放。
  - 每个事件推送需包含签名，供客户验证请求确实来自平台。
- 成功结果：客户系统能及时收到关键业务事件通知，无需持续轮询。
- 异常情况：客户回调地址持续不可达时，应有告警并可能自动暂停该订阅（避免无意义重试消耗资源）。

模块四：JS/TS SDK
功能 4.1 待签交易签名与广播封装
- 功能描述：提供 SDK 封装"调用 API 获取待签数据 → 唤起钱包签名 → 广播交易 → 轮询/监听结果"的标准流程，降低客户接入成本。
- 业务规则：SDK 是 Open API 的封装层，不引入任何 API 之外的能力，本身不托管私钥、不代签。
- 成功结果：客户接入认购、Claim、二级交易等写操作时无需自行处理签名与广播的底层细节。
- 异常情况：SDK 版本与 API 版本的兼容性管理【待确认，见9.2 版本策略联动】。

模块五：沙箱环境
功能 5.1 沙箱环境与模拟数据
- 功能描述：提供独立于生产环境的测试网沙箱，配合模拟数据与测试 API Key，供客户零成本联调。
- 业务规则：
  - 沙箱环境的数据与正式环境完全隔离，不共享 tenant_id 空间。
  - 沙箱环境应提供典型场景的预置模拟数据（如已存在的测试资产、测试 Offering），减少客户从零搭建测试场景的成本。
- 成功结果：外部开发者可在无人工支持的情况下完成"发行→认购→Claim"全流程联调（对应 PRD 系列的最终验收目标之一）。
- 异常情况：沙箱环境与正式环境的 API 契约不一致导致客户联调通过但生产环境失败——需要保证两环境的接口行为严格一致，仅数据与链环境不同。

模块七：发行方数据权限与市场统一性
【已确认，本次澄清】本模块整体取代此前版本"多租户强制隔离业务数据 + 二级市场按租户撮合层隔离"的设计。平台的实际隔离边界远比常规 SaaS 多租户模型收窄，具体见下。
功能 7.1 发行方后台数据权限（基于资产归属，非市场隔离）
- 功能描述：定义身份/KYC（全局共享）与"发行方后台管理数据"（资产/Right/Offering/募集与认购数据）两层不同的权限策略。
- 业务规则：
  - 【已确认，承接 PRD-01】identity/kyc 全局唯一，不带 tenant_id；另设 tenant_user 关系表记录用户的来源渠道，仅用于归因统计，不作为访问权限的判断依据。
  - 【已确认】一人一 ONCHAINID，KYC 结果全平台复用，用户访问任何接入方（自营/白标/纯API）前端均无需重新认证。
  - 【已确认，本次澄清】资产、Right、Offering、募集与认购数据带 tenant_id 标记其归属发行主体，但该字段仅在发行方后台管理场景下作为查询过滤条件（发行方只能看自己名下的）；在投资端浏览、认购、持仓查询、二级市场等场景下不作为过滤条件，返回全平台统一数据。
  - 自营业务使用默认发行主体标识（tenant_id = 0），与其他发行方在投资端/二级市场展示上完全平等，不享有优先展示等特权（除非产品另行设计推荐位机制，见 14.6）。
- 成功结果：同一自然人可作为任意发行方/接入方的投资者，KYC 只需完成一次；发行方之间的后台管理数据互不可见。
- 异常情况：发行方越权查询/操作非自己名下的资产或认购数据应被拒绝（呼应功能1.2）。
功能 7.2 一级市场与二级市场的全平台统一性
- 功能描述：明确一级市场投资端（Marketplace）与二级市场（AMM + C2C）均为全平台统一的公开市场，不因发行方、白标客户或接入渠道不同而产生任何数据或流动性上的隔离。
- 业务规则：
  - 【已确认，本次澄清，取代原方案 B-5"撮合层隔离"设计】一级市场：任意投资者只要满足合规条件（KYC/Eligibility），均可浏览并投资平台上任意发行方（A/B/C…）发布的资产，不区分投资者从哪个入口（自营App/白标前端/客户自研前端）访问平台。
  - 【已确认，本次澄清】二级市场（AMM 流动性池与 C2C 订单簿）为全平台统一的公共市场，所有资产在同一个市场中流通、撮合，不按发行方/渠道/客户做任何分区；此前版本提出的 market_scope（TENANT_ONLY/GLOBAL）字段与撮合层隔离方案自本次澄清起不再采用。
  - 【已确认，本次澄清，替代原 14.5 待确认项】不需要在产品层面限制"某些资产只能在其发行方所在的市场流通"——因为本平台从设计上就只有一个市场，不存在"多个租户市场"需要限制互通的问题。PRD-03 14.6 提出的"版税可规避性"风险独立存在（与是否强制转账经过市场合约有关），与本条无关，已在 PRD-03 中单独处理，不再要求合并评审。
  - 白标/纯 API 客户获得的核心商业价值是"品牌化/自主化的发行与获客入口"，其带来的投资者可直接享受全平台的资产池与流动性深度——这对客户实际是优势（无需自建冷启动流动性），但需要在商务合作协议中明确说明，避免客户误以为能获得排他性的独立资金池。
- 成功结果：全平台流动性与资产池保持统一，避免因隔离导致的流动性碎片化，投资者体验一致。
- 异常情况：无（该规则本身不产生运行时异常，属于产品边界澄清）。

模块八：白标交付
功能 8.1 主题与域名配置
- 功能描述：白标租户可配置自己的品牌主题（复用 PRD-01 提及的 Design Token 体系）与独立域名，无需修改代码即可上线。
- 操作流程：Admin 为租户创建主题配置 → 设置颜色/Logo/字体等 Token 值 → 绑定客户提供的域名 → 域名解析生效后即可通过该域名访问已换肤的平台前端。
- 页面元素：主题配置表单（Design Token 各项）、域名绑定与解析状态检测、预览页面。
- 业务规则：
  - 【已确认】白标只做"主题 + 域名 + 权限 + 配额"，不做租户级功能定制；有定制需求的客户引导走纯 API 自研前端。
  - 【已确认，本次澄清】换肤后的前端中，Issuer Console 部分展示的资产/认购数据按发行方归属过滤（只看自己的）；投资端（Marketplace、二级市场）部分展示全平台统一数据，与自营前端完全一致，不因白标身份而收窄或隔离。
  - 主题配置的可定制范围边界【待确认】——是否仅限视觉层（颜色/Logo/字体），还是也允许调整页面模块的展示/隐藏（如某租户不想展示二级市场入口）。
- 成功结果：客户在自己域名下看到符合自身品牌调性的平台前端，功能与自营前端完全一致。
- 异常情况：域名解析失败、主题配置项缺失导致页面显示异常时的默认兜底样式。

模块九：租户与计费管理（Admin）
功能 9.1 租户生命周期管理
- 功能描述：Admin 管理租户从申请、开通、配置、暂停到注销的全生命周期。
- 操作流程：审核租户申请 → 创建租户记录并配置配额/交付形态 → （白标）配置主题域名 → 租户运营中 → 如需暂停/注销，执行对应操作并处理该租户下数据的后续归属【待确认，见14.3】。
- 页面元素：租户列表（状态、交付形态、创建时间）、租户详情（配额、用量、计费方式）、暂停/注销操作与二次确认。
- 业务规则：目标"新租户开通可在1个工作日内完成"（承接原方案里程碑要求）。
- 成功结果：租户开通流程标准化、自动化，不依赖大量人工部署工作。
- 异常情况：租户注销时若仍有未完成的链上业务（未到期的 Offering、未领取的收益）如何处理【待确认，见14.3】。
功能 9.2 用量计量与计费方式配置
- 功能描述：记录每个租户的 API 调用量、资产规模（AUM）等计量指标，为计费提供数据基础。
- 业务规则：
  - 【待确认，见14.1】计费模式：按租户订阅费 / 按发行规模（AUM）抽成 / 按 API 调用量 / 按交易手续费分成，四种如何组合，纯 API 与白标形态是否差异定价。
  - 【已确认，架构约束】无论最终计费模式如何，用量计量埋点必须与 API Gateway 同期建设，避免后补导致历史数据无法回溯。
- 成功结果：即使计费模式尚未最终确定，用量数据已被完整记录，未来可随时启用计费。
- 异常情况：计量数据丢失或不准确将直接影响未来计费的可信度，需要计量本身具备高可靠性（不因业务服务故障而丢失计量记录）。

模块十：API 版本管理与 Dogfooding 门禁
功能 10.1 API 版本化与弃用策略
- 功能描述：接口以 /v1 路径版本化，破坏性变更需新增版本号并提供并行期。
- 业务规则：
  - 破坏性变更定义【待确认，需要一份明确的清单，如"删除字段""改变字段类型""改变必填性"均视为破坏性，"新增可选字段"不视为破坏性】。
  - 并行期时长【待确认】，并行期内旧版本继续可用，到期前通过开发者门户与 Webhook 多次提前通知。
- 成功结果：客户前端上线后，平台仍能持续迭代而不造成客户生产事故。
- 异常情况：紧急安全修复是否可以跳过并行期直接下线旧版本【产品建议：安全类修复可缩短但不应完全跳过通知流程，除非旧版本本身存在活跃被利用的漏洞】。
功能 10.2 Dogfooding 门禁
- 功能描述：强制自营前端从设计上只能调用公开 API，作为保证"API 覆盖面 = 产品覆盖面"的核心机制。
- 业务规则：
  - 【已确认】CI 层面禁止自营前端引用任何非公开接口（工程流程要求，产品侧的验收标准是"自营前端 100% 可以用文档里公开的接口复现"）。
  - 若自营前端需要一个当前不存在的能力，必须先补齐为公开 API，再由自营前端调用，不允许开临时私有接口"抄近道"。
- 成功结果：外部客户能用 API 做到的事情，与自营前端能做到的事情始终保持一致。
- 异常情况：发现自营前端存在私有接口依赖时，视为架构违规，需要排期补齐并下线私有接口。

- 【已确认】白标不做租户级功能定制。

8.6 计算规则

11.1 需要的数据能力

- Admin相关：租户创建/配置/生命周期管理、计费方式配置、用量与错误率监控查询。
- 【已确认，架构约束】PRD-01/02 中定义的全部投资者侧与发行方侧接口均通过本文档定义的 API Gateway 对外统一开放，本文档不重复定义这些接口的业务语义。

13. 验收标准
正常场景
- 外部开发者可在沙箱环境仅凭文档与SDK、无人工支持完成"发行→认购→Claim"联调全流程。
- 白标客户可通过仅配置主题与域名的方式上线，无需编写代码，功能与自营前端一致。
- 自营前端的全部功能均可用公开API复现，不存在私有接口依赖。
- 新租户开通可在1个工作日内完成。
异常场景
- 跨发行方越权访问后台管理数据的自动化测试用例（每个核心资源至少一条"A发行方访问B发行方后台数据"用例）应被正确拒绝。
- API Key吊销后立即失效，不存在延迟窗口内仍可调用的情况。
- 超出配额的请求被正确限流而不影响其他接入方。
边界场景
- 同一自然人作为不同发行方/接入方渠道带来的投资者时，KYC只需完成一次，且能在任意入口投资任意发行方发布的资产。
- 任意两个接入方（如白标客户A、纯API客户B）的投资端/二级市场前端应展示完全一致的全平台资产池与市场深度（验证"不隔离"这一核心结论）。
- API版本并行期内，新旧版本同时被不同客户调用时均能正确响应。
- 接入方注销时若存在未完成业务（未到期Offering、未领取收益），流程应有明确的拦截或处理方案而非允许"裸注销"。

14. 风险与待确认事项
14.1 产品风险（计费模式）
- 计费模式（订阅费/AUM抽成/API调用量/交易分成，及其组合）尚未确定，直接影响用量计量埋点的设计颗粒度与开发者门户看板展示内容。建议尽快明确，避免后续为了补计费口径而重新采集历史数据。
14.2 业务风险（版本弃用与客户生产事故）
- 一旦首个纯API客户上线，任何未经充分通知的破坏性变更都可能造成客户生产环境事故，进而损害平台的SaaS商誉。API版本与弃用策略必须在首个外部客户接入前就完整落地并经过演练。
14.3 待确认问题（租户生命周期）
- 租户暂停/注销时，若存在未完成的链上业务（未到期Offering、未领取收益、进行中的二级市场挂单），应如何处理？由于身份与资产均是全局/链上对象，"注销租户"不能理解为"清空用户资产"，需要明确注销的准确含义（是否仅指"停止该租户前端与API访问权限，但已存在的链上资产与身份不受影响"）。
14.4 待确认问题（配额与权限颗粒度）
- 租户配额的具体档位（不同交付形态是否有差异化默认配额）。
- API Key的权限范围是否需要精细化到能力域级别的授权审核，还是默认全量权限。
14.5 已确认（原"多租户市场隔离边界"问题，本次澄清后关闭）
- 【已确认】不存在"多个租户市场"的产品形态，一级市场与二级市场均为全平台统一公开市场，不做任何按发行方/客户/渠道的隔离，详见模块七。PRD-03 14.6 提出的"版税可规避性"风险与本条无关，作为独立议题在 PRD-03 中处理，不再要求合并评审。
- 【产品建议】既然投资端全局统一、白标客户无法获得排他性资金池，建议尽早与商务/法务团队对齐白标合作的定价逻辑与对外话术（价值点应聚焦"品牌化入口 + 免自建流动性冷启动"，而非"专属市场"），避免后续客户预期错位引发纠纷。
14.6 待确认问题（白标定制边界与展示排序）
- 白标主题的可定制范围是否仅限视觉层，还是也允许调整页面模块的展示/隐藏。
- 【新增待确认】既然投资端数据全局统一，白标客户的品牌前端是否允许对"自己名下发行的资产"做优先展示/置顶（如推荐位），还是必须与其他发行方的资产完全平等地按统一规则排序（如按发布时间/热度）——这属于产品层面的展示策略问题，不影响底层数据是否隔离。

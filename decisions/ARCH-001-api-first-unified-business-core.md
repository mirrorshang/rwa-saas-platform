# ARCH-001｜统一业务核心的 API-First / Contract-First 架构原则

> **状态：Approved — 产品与技术架构原则（不是最终技术设计、V1 研发授权或商业 Open API 上线批准）**
>
> 决策日期：2026-10-22｜产品负责人明确确认“同意你的建议，确认”。
>
> 关联：SCOPE-060（本次确认修订后的架构部分）；22 模块 M01～M22，重点 M04～M12、M16～M22；SCOPE-053～058 的最小实现原则。此决策是后续新增架构原则，不追溯改写已经冻结的第 02/03/04 份文件或 DEC-001～011。

## 1. 已批准的决策

1. **Issuer SaaS 首期即 API-First/Contract-First。** 发行机构 Web 前端通过清晰定义的应用 API 调用后端业务服务；核心业务规则不能散落于前端组件或专属接口控制器。
2. **统一业务核心可复用。** Issuer SaaS、未来 White-label 和商业 Open API/SDK 共用业务能力、统一状态机和风控规则；可按所需建立不同接口/BFF/网关适配层，但不可为新渠道复制第二套发行、KYC 资格、认购、额度、稳定币对账、配售、登记或 Token 业务系统。
3. **内部与对外接口安全边界不同。** Issuer SaaS 内部应用 API 可以按页面需要设计；外部 API 必须经独立暴露审查、凭证与权限模型、租户/资源/字段鉴权、用量限制、数据隔离和审计。**内部接口不因存在就自动允许对外公开。**
4. **契约从首期开始。** 对 API 定义请求/响应、业务 ID、权限范围、状态/错误语义、幂等要求、审计关联和事件/Webhook 契约（适用时），维护可版本化的契约文档；具体使用 OpenAPI 等标准、数据协议或 BFF 技术选型留待第 07 份技术规格决定。
5. **重要交易只能进入同一受控业务层。** 无论通过 Web、白标还是外部 API，必须经过同样的 KYC/Eligibility、Offering 守卫、M12 唯一额度、M11 付款与对账、审批/受权自动配售、法定登记、链上执行、退款权限、审计与幂等规则。事件重放/HTTP 超时不可引发重复付款、配售、Mint 或退款。
6. **不要求首期微服务。** 可以使用有明确模块/领域服务边界的模块化单体，未来视规模和独立部署需求拆分。API-First 不等于强制多微服务或先建庞大 API 网关平台。
7. **API-Ready 与 API-as-a-Product 两阶段。** Issuer SaaS V1 必须具备“规范接口调用同一核心业务能力”的架构条件；M16 完整商业 Open API/SDK（客户应用、开发者门户、外部凭证授权、Sandbox、公开版本、商业限流/配额、开发者文档/SDK、对外 Webhook 等）的**实际交付批次依然待定**，不得因本原则判定与 Issuer V1 同期上线或自动延至 V2。

## 2. 推荐的逻辑层次（非最终工程拓扑）

```text
Issuer SaaS Web       White-label Web         Third-party/API Client
        |                    |                         |
 Internal App API / BFF   White-label API          Public API Gateway
        \____________________|_________________________/
                             |
             Shared application/domain business services
             (M01–M22, Guards, RBAC, audit, idempotency)
                             |
                 Persistence + approved integrations
        (identity/KYC, payment, chain, legal register, signatures)
```

说明：BFF、独立网关、多服务进程、最终部署拓扑可按技术取舍选择，不强制物理多层。对外接口可通过有意设计的适配层重用相同的业务服务；**不能直接把内部管理 API 整包公开**。

## 3. 模块级影响与详细 PRD 追加约束

| 模块/领域 | 必须规划的 API-First 复用边界 |
|---|---|
| M01～M03 SaaS 客户、组织与平台 | tenant_id、organization_id、环境与能力许可、角色/资源级鉴权；平台运维权限与客户金融业务权限隔离 |
| M04～M06 Asset/Instrument/Offering/文件 | 创建/修改/审核/发布业务命令、版本与文件证据，不能绕过审批和生效条件 |
| M07 链上 Token | 获授权执行意图、密钥/签名责任、链上 Tx 状态、Unknown 查询；不能暴露无条件 Mint/销毁接口 |
| M08～M10 投资者/准入/购买 | 用户或第三方调用者的身份关联、Offering 可见性、KYC 合法复用、资格/认购规则、订单与报价快照、幂等请求 |
| M11～M12 付款/配售/登记 | 支付指令和实收区分；M12 统一额度权威；自动配售需事先批准和逐笔 Guard；法律登记与 Token 独立权威结果 |
| M13 发行后 | 权益和存续期查询、披露与适用收益/赎回责任，不通过接口调用自动改变法定权利 |
| M15 白标 | 同业务核心但独立运营商/发行方授权、域名/品牌隔离、跨机构数据和分发权限严格校验 |
| M16 Open API/SDK | 商业网关与开发者产品的交付时间待定；首期业务核心/API 契约可复用，内部 API ≠ 获准外部公开 |
| M17～M22 共性 | 审批与例外、通知事件、配置版本、租户安全、审计、查询、三方适配与回调签名/去重统一实施 |

从此以后，模块详细功能 PRD 的适用章节应补充：**可复用业务命令/查询、必要数据字段与对象 ID、权限与身份/租户作用域、业务 Guard、幂等与错误状态、事件/Webhook（适用时）、内部/外部暴露边界**。不必在产品 PRD 冻结数据库表、HTTP URL 或 SDK 具体实现。

- **SCOPE-059、SCOPE-061、SCOPE-062 未因本次 ARCH-001 自动批准。** White-label 是否与 Issuer SaaS 同期交付、集中募集是否完整纳入 V1、首发金融工具何时固定等，继续独立评审。
- 具体框架、编程语言、OpenAPI 版本、微服务与否的最终方案、BFF/网关部署、API 路由、数据库架构、服务商与安全实施，留第 07 份架构文档详细设计。

- 不批准任何法律许可、真实资金出款、生产合约操作或正式研发；PR #6 继续 **Draft / Open / Unmerged**。

## 5. 变更与验收约束

后续设计若建议某一渠道绕过共享服务/Guard，或形成重复的发行/认购/Token 规则实现，必须在独立架构评审中解释差异与风险并获得产品负责人重新批准。本架构原则的落地验收重点为：同一业务规则跨渠道一致、独立鉴权与最小权限、外部公开清单可审查、重复/乱序事件不引发重复交易、每项不可逆执行可追踪、环境隔离和版本契约可追溯。

## 二、解释与强制核验点

1. **只简化界面，不简化安全与权威事实**：M10 订单不能充当资金到账，M11 支付/对账不能充当配售，M12 配售不能充当法律登记，法定登记不能自动等于 Token 链上交付。
2. **API-First 约束所有首期模块**：统一服务端业务核心，从 Issuer Web 的有契约 API 复用，未来 White-label 和对外 Open API 不能另起一套发行规则；内部接口不得无审查公开。
3. **持续购买为完整 V1 目标**：Offering 资格、额度预留、指定链 USDT/USDC 到账确认、自动配售、安全授权和真实 Token 交付均要闭环；集中募集并非默认首期全量，但若首发金融工具强制则补充必要最小功能。
4. **M15/M16 商业产品按独立交付里程碑规划**：White-label 不强制首期同期（SCOPE-059）；Open API 的 API-Ready 首期、商业产品另行排期（ARCH-001/SCOPE-060）。这里只建议不计入 Issuer 基础首期开发承诺，不写具体 V2 日期。
5. **冻结真实 V1 清单前必须选择 1～2 类参考 Instrument**：验证特殊收益、还本/赎回、转让限制、法律登记、投资者资格/资金法律责任，并把需要升级的条件性 P1 另行批准。

## 二点五、已确认的核心/界面分类审计约束（SCOPE-063～070）

**产品负责人已明确批准 SCOPE-063～070 的跨模块业务主责/页面合并/ARCH-001 复用原则**。参见[决策记录](../../decisions/SCOPE-063-070-core-ui-cross-module-simplification.md)与[115 项审核报告](RWA-SaaS-Issuer-V1-Core-and-Shared-UI-Audit-v0.1.md)。此处**仅更新分类解释，不改变 187 项既有 P0/P1/P2/V2/待定，也不把全部功能实际交付方案判为 Approved**：

- **73 项“共享业务核心需实现”**：确立服务端受权领域能力与 API 契约复用方向，不要求 73 个独立微服务/路由；共享服务可用模块化单体，具体技术选型另审。
- **42 项“共享界面/简化实现”**：它们也都是 P0 核心业务候选。简化只适用于表单、界面及操作编排；Tenant 生命周期、组织/资源权限、Instrument/Offering 版本、批准/签署证据、审计与安全恢复仍须有服务端能力。
- **三个使用界面、15 个逻辑页面群**是已批准的 UI 分组方向；不决定实际 URL、页面数、导航层级或视觉风格。
- **跨模块权威**：M01/M03 同 Tenant 业务核心；M05 配置/M19 版本/M09 资格/M10 Guard；M06 签署与 M17 任务/M18 通知分离；M10 订单、M11 资金、M12 额度配售/登记、M07 Token、M21 只读报表各自保留不同责任。
- **10 项外部执行和 16 项条件性 P1**仍需下一轮单独审核；外部执行者合法身份、回执与控制机制不因本次审计自动批准。真实 V1 必交清单仍 Draft。

## 二点六、已批准 10 项外部执行与核验原则（SCOPE-071～077）

已明确确认 **SCOPE-071～077 全部同意**，参见 [外部执行/核验正式决策](../../decisions/SCOPE-071-077-external-execution-authority-controls.md) 和 [10 项专项审核](RWA-SaaS-Issuer-V1-External-Execution-and-Authority-Audit-v0.1.md)。

- 对分类为**“受权外部执行 + SaaS 核验”**的 M07-F002/F004/F005/F008、M11-F004/F005/F009、M12-F006、M22-F004/F005，批准**强制业务能力和安全责任边界**，不是批准实际外部供应商或默认由 SaaS 控制资金/生产私钥/法定登记。
- 合约部署、Mint、退款、电子签和登记的实际执行责任须依法授权；付款监测与链上确认更多是外部链上事实观察，SaaS 保留**独立状态/对账/可信核验**。外部结果 Unknown 时优先查询原操作，避免不可逆重复执行；重复回调不得吞掉不同真实入账。
- M22 只是技术集成，M07 Token、M11 资金/退款、M12 配售与登记保持独立权威；ARCH-001 内部 API 也不能让商业 Open API 绕过权限、规则 Guard 和法定批准。
- **接下来 16 项“条件性必需（需参考工具裁决）”仍未逐项批准完整交付深度**；当前五类原分类及 187 项原始等级维持原样。

## 二点七、已批准的 16 项条件性 P1 审查原则（SCOPE-078～SCOPE-085）

产品负责人已确认 **SCOPE-078～085 全部同意**（[正式决策](../../decisions/SCOPE-078-085-conditional-p1-v1-baseline-principles.md)、[16 项专项审核](RWA-SaaS-Issuer-V1-Conditional-P1-Assessment-v0.1.md)）。批准的是 16 项 P1 的**触发条件与最低必需业务控制**，不是已经选择首发 Instrument 或认定全部 V1 必交：

- M05-F011/M12-F010 集中募集、M10-F009/M12-F009 部分认购和配售以 Offering/首发工具规则判定；V1 连续购买优先，但法定或合同必要的业务闭环不得丢失。
- M07-F009/M13-F004～F006 赎回、销毁、收益、还本、兑付须在首发工具触发时形成最小必需的业务处理与独立权威事实核验。
- M08-F009/M18-F004～F005/M21-F005 必要披露、法定通知/失败恢复和基本存续信息按工具及送达要求提供。
- M11-F010 的**基本资金异常人工调查**、M19-F006 的**底层强制配置优先级**、M20-F007/M21-F006 的**必要数据交接/受控导出**不得因增强 UI 原分级为 P1 而被删除。
- **还有另外 5 个 P1**（M03-F003/F004、M04-F008、M06-F007、M17-F006）处在 46 项非默认 Issuer 首期候选中，需另外审核。原 187 项功能 ID 与范围分级/五类统计均保持不变，实际 V1 清单仍 Draft。

## 二点八、已批准 46 项非默认交付与独立商业产品边界（SCOPE-086～095）

产品负责人已明确确认 **SCOPE-086～095 全部同意**：[正式决策](../../decisions/SCOPE-086-095-nondefault-issuer-v1-scope-and-product-milestones.md)、[46 项审核](RWA-SaaS-Issuer-V1-Nondefault-46-Item-Exclusion-and-Roadmap-Audit-v0.1.md)。

- P1 的基础客户交付、金融工具权利、专业意见、异常升级路径仍需通过相关 P0/共享能力满足；增强 UI 可后置。M14 转让 V2 不影响 M07 必要合约级转让限制。

- **五类审查原则已覆盖 187 项**：核心 73 + 界面简化 42 + 外部受权执行 10 + 条件性 P1 16 + 非默认 Issuer 首期 46 = 187；**真实开发交付深度、条件性 P1 触发、参考 Instrument、法域及资金/登记/Token 责任尚未冻结**。
- 本节不改变既有 187 行的范围等级（P0 125 / P1 21 / P2 21 / V2 6 / 待定 14）及五类分类建议，只把跨模块审核结论的**原则**更新为已批准。

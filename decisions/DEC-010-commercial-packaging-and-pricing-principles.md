# DEC-010｜商业套餐与定价原则（提案）

- 提案日期：2026-10-19
- 状态：**Proposed（待产品负责人确认；尚未批准）**
- 关联决策：DEC-002（客户层级与交付模式）、DEC-003（多资产与初始范围）、DEC-004（受监管活动责任边界）、DEC-005（目标客户优先级）、DEC-008（认购资金、结算与退款原则）、DEC-009（V1 二级转让能力边界）
- 关联文档：[第 02 份《产品战略与商业模式》](../docs/02-product-strategy/RWA-SaaS-Product-Strategy-Business-Model-v01.md)
- 本提案只确定商业包装与定价的产品原则，不设定最终价格、收入预测或任何未经验证的客户支付意愿。

## 1. 需要决策的问题

RWA SaaS 同时包含 Issuer SaaS、White-label 和 Open API/SDK 三条商业交付线。若所有客户使用同一套餐或完全按交易量收费，可能无法反映不同客户的购买动机、部署复杂度和服务成本；若一开始设计过多维度、复杂计费和大规模企业定制，又会增加销售阻力与交付成本。

需要先确定商业套餐应遵循哪些可复用原则，再通过客户访谈、竞品证据、成本测算和试点报价确定具体档位及价格。

## 2. 建议的商业原则（等待确认）

1. **三条商业交付线分别包装。** Issuer SaaS、White-label、Open API/SDK 共享统一业务核心，但分别呈现适合各自买方的套餐、合同和计费方式；不能强行套用完全相同的套餐结构。
2. **以可理解的订阅/许可为基础。** 初始商业模型优先考虑周期性 SaaS 订阅、White-label 年度/周期许可、API 平台订阅或用量包，并可加实施/集成费和企业支持费。
3. **套餐价值与真实客户任务挂钩。** 档位差异优先围绕可感知的产品能力、运营规模、组织/席位、发行活动数量、品牌/域名、API 使用量、支持等级与部署要求设计，而非堆叠难以理解的技术限制。
4. **先控制计费维度数量。** V1 不应同时对大量变量收费。每条产品线优先选取少数能解释成本或客户价值、易于计量且不容易产生争议的主要计费维度；其余作为合理使用限制或升级条件。
5. **价格点必须由证据决定。** 具体月费/年费、免费试用、实施费、额度和超额价格，在客户访谈、竞争方案、服务成本、支付意愿及试点反馈后确定；不能把假设写成市场事实。
6. **明确区分软件费与第三方费用。** KYC/KYB、AML、支付、托管、登记、链上 Gas、合约审计等第三方成本应透明说明由谁采购、谁承担、是否转付及是否包含额度；不得把投资者资金或资产发行募集资金当作平台收入。
7. **谨慎处理按交易额/资产规模抽成。** AUM、募集额、认购金额、转让成交额或收益分成可作为后续研究选项，但不作为未经验证的默认计价方式；必须先分析客户接受度、成本归因、合同透明度及可能涉及的金融监管/佣金限制。
8. **企业定制必须有边界。** 专属部署、特殊 SLA、定制集成、额外环境和非标准功能应单独评估报价，避免基础套餐包含无法规模化交付的无限服务。
9. **套餐权限应可审计。** 套餐、额度、超额、降级、暂停、续费和合同到期行为应有明确规则及通知；不能因套餐状态变化破坏客户依法必须保存的记录或未结业务处理。
10. **商业计费不得绕过 DEC-004/008/009。** 收取软件费不自动授权平台开展受监管金融活动；任何与介绍、分销、交易、资金处理或成交挂钩的收费，必须在具体业务和法域中单独法律审查。

## 3. 建议的三条产品线包装方向

### A. Issuer SaaS

面向单一发行机构或资产管理机构，优先按周期订阅。可研究的套餐区分维度：

- 组织/机构与管理员席位数量；
- 同时管理的资产、Instrument 或活跃 Offering 数量；
- 投资者/合规工作流、认购、配售、登记及存续期模块；
- 报告、审计导出、权限和自动化能力；
- 标准集成额度、支持等级与 SLA。

**建议方向：** 先设计清晰的基础版、成长版、机构版作为研究框架，不在本提案中确定具体功能表或价格。不要简单按每个投资者或每条记录收费，以免抑制正常业务使用；若确需限制，应以可解释的额度和成本依据为基础。

### B. White-label

面向需要以自有品牌运营、多家发行机构或客户门户的服务商/运营商。可研究的计价维度：

- White-label 运营商许可；
- 纳入的发行机构/组织数；
- 品牌门户、域名或环境数量；
- 运营管理、权限、资产授权分发和报告能力；
- 实施/迁移/品牌配置费用；
- 专属环境、支持 SLA 与额外集成。

**建议方向：** 采用周期性许可 + 一次性实施/集成费用作为基础模型；多发行机构规模、专属部署和高级支持作为升级依据。V1 不因 White-label 交付而默认支持多级代理/转售（DEC-002）。

### C. Open API / SDK

面向金融科技、机构和已有业务系统的集成客户。可研究的计价维度：

- 平台基础订阅或开发者/企业许可；
- API 请求量、事件/Webhook、环境或项目额度；
- Sandbox、生产环境、版本支持与 SLA；
- SDK、专属支持、认证/安全要求和集成服务。

**建议方向：** 基础订阅 + 明确的用量包/超额规则；先验证客户的调用模式和可接受计量单位。不得以调用量作为唯一维度而忽略支持与集成成本，也不应在无成本依据时设置惩罚性超额价格。

## 4. 费用组成与合同透明度

后续报价模型应清晰区分：

| 费用类型 | 建议处理原则 |
|---|---|
| SaaS 订阅 / White-label 许可 / API 许可 | 明确计费周期、包含范围、额度和续费规则 |
| 实施、迁移、集成与定制 | 根据范围单独报价，写明交付物、验收和变更机制 |
| 企业支持与 SLA | 明确响应时间、服务时段、升级流程和排除项 |
| 第三方 KYC/KYB、AML、支付、托管、登记服务 | 明确供应方、采购/合同关系、计价方式、转付规则与责任边界 |
| 链上 Gas、节点、存储等可变基础设施成本 | 明确是否包含额度、超额计算和成本变化处理 |
| 金融介绍、分销、交易或成交相关费用 | 不默认采用；须单独审查具体法域的法律、许可和合同条件 |
| 投资者认购资金、发行募集款及资产本身资金 | 与平台营收、客户订阅款及第三方费用严格区分，不作为 SaaS 收入记载 |

## 5. 暂不建议在当前阶段定死的事项

- 具体价格点、币种、月付/年付折扣和涨价机制；
- 免费试用时长、免费层是否存在及其限制；
- 每个套餐的精确功能矩阵、资产数/发行数/席位/API 额度；
- 是否按 AUM、募集额、认购/转让交易额或成功发行收费；
- 各地区税费、发票、付款方式和汇率规则；
- 合作方费用的加价、转付或收入分成；
- 企业级专属部署、定制 SLA 与支持团队的最低合同额；
- 渠道佣金、转介绍费用和白标运营商的转售定价。

这些事项应结合客户发现、竞品证据、成本模型和法律审查另行决定。

## 6. 需要收集的商业证据

每类客户至少应验证：

1. 购买决策人、预算归属、采购周期和合同签署流程；
2. 客户目前使用的替代方案及总成本；
3. 典型项目数量、发行频率、管理组织数、投资者规模和 API 使用模式；
4. 客户更偏好固定订阅、按量、实施费还是混合计费，并说明原因；
5. 对功能分档、额度、超额、年付、SLA 和专属部署的实际接受度；
6. 第三方服务费用由客户直签、平台统一采购还是按实际用量转付；
7. 客户愿意为减少哪些人工、合规协调、系统建设或运营成本付费；
8. 试点报价、客户反馈、拒绝原因及可能成交条件。

证据记录应包含日期、客户类型、受访角色、具体业务情境、报价/价格区间（若有）、可信度与后续验证项；不能用单个客户的意见直接代表整个市场。

## 7. 建议的验收标准

若本提案获原则性确认，后续商业方案应满足：

- 三条产品线有清晰区分的包装逻辑，但共享一致的产品核心与合同边界；
- 每条产品线优先采用少量、易理解、可核验的计费维度；
- 具体价格与额度有客户证据、竞品证据或成本依据，而非臆测；
- 软件费、实施费、第三方费用和客户/投资者资金明确分离；
- 按交易额、资产规模或金融活动收费前完成法律审查；
- 套餐额度、超额、暂停、降级、续费与到期行为可解释、可审计；
- 定制服务、SLA 和专属部署有明确范围与成本边界；
- 不将未经验证的收入预测、市场价格或客户支付意愿写成已确认事实。

## 8. 决策请求

请产品负责人确认以下方向：

- **A｜原则上同意本提案**：先确立三条产品线分别包装、订阅/许可为基础、计费维度保持精简、价格由证据决定的原则；具体价格与额度后续验证；
- **B｜同意基本方向，但需修改部分原则**；
- **C｜暂不确认，先补充客户/竞品/成本证据。**

在确认前，本文件仅为讨论提案，不应被视为已批准的商业定价策略或最终价目表。

## 1. R2-04-01：Project 管理与对象关系（R01–R08 全部 A）

用户明确批准 R01–R08，补充意见无。

| 决策 | 已批准内容 |
|---|---|
| R01 | Project 是资产发行生命周期的轻量管理容器，不是发行参数配置对象 |
| R02 | 首次从资产与权益结构发起发行方案时，系统自动创建 Project，不要求用户手动建立 |
| R03 | V1 每个 Project 关联一个主要 Asset；企业可以管理多个 Project |
| R04 | 一个 Project 可包含多轮 Offering，每轮独立配置、记录、管理 |
| R05 | 一个 Offering 关联一个 Project、一个主要 Asset 和一个明确的 Instrument Version，不做多资产组合发行 |
| R06 | Project 页面只提供项目总览、对象关联、轮次及进度，不复制 Offering 参数表单 |
| R07 | 同一 Project 同时仅允许一轮尚未关闭认购的当前 Offering；不做多轮并行销售 |
| R08 | 已创建 Offering 的 Project 不可直接删除；只有不存在未完成发行和存续义务时才可归档 |

此处 Project 关联一个 Asset，不妨碍其下多轮 Offering 分别使用该 Asset 对应的不同、有效 Instrument 版本。单个 Offering 始终仅使用一个权益结构版本。不得从“一个Project多个Offering”推断多资产、多权益组合发行。

**延后候选**：多资产 Project、单轮多资产/多权益组合、并行销售、多轮间复杂额度调拨及优先级；涉及正式V3功能的复杂资产组合仍维持原版号，不能仅靠此文件提前迁入V2。

## 2. R2-04-02：Offering 基础发行参数（R01–R10 全部 A）

用户明确“确认”了本批推荐 R01–R10，包括 U 与 USDT 固定 1:1。

| 决策 | 已批准内容 |
|---|---|
| R01 | Offering 是单轮发行配置，承载权益数量、Token 数量、单价和募集规模 |
| R02 | 从权益结构详情或项目管理发起；没有Project则自动创建，有Project自动关联 |
| R03 | 一个Offering仅对应一个Asset、一个权益结构的固定版本；同一Asset的Project可关联多种权益结构的不同轮次 |
| R04 | Offering轮次编号系统自动生成；发行名称可自定义 |
| R05 | 本轮最大发行权益数量由企业填写、自动继承权益单位，不允许更换单位 |
| R06 | Token数量根据R2-03固定映射规则自动计算，不可在Offering重定义映射 |
| R07 | 一轮只配置一个固定Token单价（U），不做动态定价或价格分层 |
| R08 | V1投资者认购支付仅OP Mainnet USDT |
| R09 | 保存草稿不占用权益池；确认发行方案后才建立权益容量预留 |
| R10 | 已确认核心参数版本化保护；未认购前撤销确认可按规则释放预留并重新配置，有下游业务记录时保留历史版本及影响检查 |

金额口径：**1 U = 1 USDT，MVP不做汇率换算**；价格、募集金额和认购金额均使用U表示，实际投资者支付为OP Mainnet USDT。价格、Token数量、权益单位、权益容量及最大募集额相互关联但不可合并成单一字段。

“确认发行方案”仅代表参数/版本已确认和额度预留，**不等于发行准备通过、不等于对外发布、不等于开放认购、不等于真实收款或Mint**。发行准备仍在R2-05独立设计。

## 3. R2-04-03：认购资格与基本限额（修订版已确认）

用户明确要求：**“MVP版本，用户只要完成KYC，就有认购资格，企业不再进行发行的独立资格配置了，这些相关的功能，移入2.0。”**

### 3.1 已批准的产品收敛

1. 在本产品 MVP 语境下，“完成KYC”须理解为 **KYC核验通过且仍有效**，不是仅填写/上传资料或提交KYC申请。
2. 通过KYC的投资者自动取得MVP的**基础认购资格**，无须针对每轮Offering另外填写资格申请或等待发行企业人工审核。
3. Issuer SaaS 的 Offering 配置表单中**不建设独立投资者资格配置区域**，不提供：
   - 自然人/机构类别的Offering单独准入配置；
   - Issuer自定义认购国家/地区白名单及资格分层；
   - Offering级白名单、邀请名单或定向资格审批；
   - 企业逐个审核、手动授予或撤销投资者认购资格；
   - Offering-specific Eligibility二次人工批准或灵活资格规则引擎。
4. 不再把旧Master PRD I-32中“企业配置各类Offering资格及限制”的旧详细页面设计当作本轮MVP开发必做事项；旧文档保留历史追溯。
5. “是否可以查看Offering”仍是合法披露与访问控制问题；“是否现在可以创建有效订单”还需要同时满足KYC有效、强制AML/制裁/法律禁止规则、发行可售状态、必要签署/确认、容量与订单守卫。这些**不是企业可配置的第二套资格审批**。
6. 平台系统与依法有权第三方仍应执行强制风险、制裁、适用地区及法律生产准入检查。若某法域/金融工具要求MVP尚不支持的额外适当性、分类、销售限制或认购资格，**该笔真实Offering必须Fail-Closed，不得以KYC代替法定资格**；可继续在Free Sandbox演练模拟流程。
7. 在可用的合法MVP路径中，投资者完成KYC后无需额外资格步骤，依次确认有效报价/条款、必要签署、申请额度预留、按授权支付、等待配售/登记/Token独立结果。

**重要术语**：KYC核验通过 ≠ 仅提交资料；基本资格自动授予 ≠ 所有Offering在所有法域必然可卖；不建设Offering级Issuer资格配置 ≠ 停止AML/制裁或绕过法律要求。

### 3.2 对R2-04-03第一稿的影响

| 第一稿项目 | 新版处理 |
|---|---|
| R01 “展示与资格分离” | 保留披露与实际下单条件的区分，但MVP不设置额外Offering资格申请/配置 |
| R02 “公开/受限披露” | 只保留必要的合法披露及文件可见性控制，不引入Offering级企业资格配置、名单管理或复杂披露策略 |
| R03 “企业选择自然人/机构资格” | **删除MVP配置，归V2候选** |
| R04 “企业选择合法销售地区” | **删除Issuer任意地区配置**；必要的地区/法域合法性以平台受控规则和生产Gate守卫，不能由KYC自动覆盖 |
| R05～R07 基础认购上下限与总发行上限 | **已确认**：企业可设单笔最低认购金额（U）；单投资者在本轮Offering累计最高认购金额为可选项；总上限直接引用已确认发行数量与自动计算募集额，不另设第二套募集额度 |
| R08～R09 单一认购窗口与到期/售罄 | **已确认**：仅一个开始/结束时间明确时区的连续认购窗口；到期或额度售罄停止新认购，已有订单按原状态继续处理 |
| R10 发布后规则及版本保护 | **已确认**：发布后规则变更保留版本和原报价、条款、签署、订单及支付记录；重大变化不得静默覆盖既有业务 |

### 3.3 后续确认及核算要点（已批准）

用户在R2-04-03修订方案后再次明确“确认”，因此本批按以下最终MVP口径收口：

- **投资者资格**：KYC核验通过且有效即自动具备基础认购资格；无企业Offering专属资格设置或二次审批。强制AML/制裁、法域适用、生产Gate、必要签署和可售状态仍单独执行。
- **金额限额**：单笔最低认购金额由企业配置；单个投资者的本轮Offering累计最高认购金额可选；不做复杂分层、关联账户合并限额。
- **累计额度**：有效订单预留、已付款未完成分配及已确认分配计入同一投资者累计使用；仅在取消、过期或退款等权威业务事实确定后释放可复用额度；Unknown不得提前释放。订单预留不得对Instrument容量重复扣减。
- **募集上限**：复用R2-04-02的本轮最大发行权益数量、映射Token数量及固定Token单价推导最大募集金额；不另建一套软上限或额外募集金额字段。
- **认购窗口**：一轮只保留一个有明确时区的开始/结束窗口；到期或售罄时关闭新订单入口，但在途订单独立结算/处理，不自动视作失败。
- **披露与版本**：依法允许的公开/受限资料披露和资产文件可见性继续受控，不以披露配置变相建设第二套资格审核；发行规则发布后变更应保留原条款/报价/订单/支付及快照。
- **不推定法律许可**：若具体金融工具/法域法定适格要求超出本MVP能力，则真实Offering必须Fail-Closed，不能用“KYC已通过”代替必需法律资格审查。

**审核结果：R2-04-03 修订版已确认，不再把本批基础限额、窗口或版本规则标为待审核。**

## 4. R2-04-04：Offering 生命周期与状态机（R01–R10 全部 A）

用户明确批准本批R01–R10全部推荐方案A，补充意见无。

### 4.1 MVP正常状态

`Draft → Confirmed → Published → Active → Ended → Settling → Completed`

| 状态 | 进入条件与业务含义 |
|---|---|
| Draft | 企业配置发行方案；尚未确认，不占用权益容量 |
| Confirmed | 企业确认核心参数和版本，系统预留对应权益容量；不代表已通过发行准备、已发布或可认购 |
| Published | R2-05发行准备检查通过且企业明确执行发布；投资者可按披露规则查看，但尚未到认购开始时间时不能下单 |
| Active | 到达认购开始时间且所有强制条件仍满足；系统开放新认购 |
| Ended | 到达认购结束时间或本轮有效容量已售罄；停止新订单，既有订单继续处理 |
| Settling | 对在途订单、付款确认、配售、Token分配和必要对账进行收尾 |
| Completed | 本轮发行所需的订单/支付/配售/分配结果均已处理或按规则关闭；不表示资产或投资者存续义务结束 |

### 4.2 暂停、恢复、撤回与终止

- 企业可主动暂停新认购，必须填写原因；已存在订单和容量占用保留。符合恢复条件后企业可恢复，系统重新检查窗口、容量及强制守卫。
- 平台/受控服务因资产、权益、合规、制裁、法域、Provider/Signer/链或其他生产风险触发强制暂停时，形成系统风险阻断记录。企业不能仅靠普通“恢复”按钮解除；必须由对应受控检查/服务恢复并重新通过守卫。
- 发布后、未产生有效认购时可按规则撤回；已产生认购/资金/Token记录后不得直接撤回或删除，必须进入受控终止与收尾处理，保护投资者权益。
- 暂停不等于订单取消；结束不等于所有在途订单失败；Completed不等于资产生命周期终结。
- 重要操作记录操作者、时间、原因、触发来源及前后状态，不引入企业内部多级审批人员。

### 4.3 自动转换、Unknown与幂等

- 认购开始时间到达时，只有Published且必要守卫全部满足，才自动进入Active；否则保持阻断/暂停并显示可读原因。
- 认购结束时间到达或剩余可售容量归零时，自动停止新订单并进入Ended；不得删除或重写已存在订单。
- 支付、链上交易、Token分配等外部操作若结果Unknown，必须先按原业务标识查询、核对权威结果；禁止盲目重试导致重复扣款、重复配售、重复Mint或提前释放权益容量。
- 各状态转换、外部命令和事件处理必须幂等；重复点击/回调不得重复产生业务事实。

### 4.4 MVP明确不做

- 多阶段/多个认购窗口、预售/优先认购阶段；
- 同一Project多轮Offering并行开放及复杂优先级；
- 多级审批、企业角色审批、人工例外工作流；
- 高级暂停策略、复杂终止补偿/清算瀑布和规则引擎；
- 自动处理法律争议或替企业决定资产、资金、Token权利。

以上高级能力作为V2候选记录于V2.0需求池；正式V3/TBD能力继续保持原版本归属。

## 5. R2-04-05：Token身份、配置与合约关系（R01–R10 全部A）

用户明确回复“R2-04-05 R01～R10 全部同意 A，无补充意见。”

| 决策 | 已批准产品规则 |
|---|---|
| R01 | 首次配置Offering时，系统自动创建逻辑Token身份；后续轮次复用，不重复创建 |
| R02 | 一个Instrument关联一个逻辑Token；同一Instrument的多轮Offering共享Token身份，但每轮额度、订单、已分配与Mint记录独立 |
| R03 | Token是业务身份，Contract是链上部署实例；V1产品目标为一个生产主合约，技术可行性、具体标准和部署仍受独立技术Gate约束 |
| R04 | Token名称默认继承权益结构名称，Symbol由系统生成；首次确认前允许调整，确认后锁定，不因后续Offering再次更名 |
| R05 | 本轮Token数量由Offering权益数量×Instrument已批准固定映射自动计算，不允许企业直接改写 |
| R06 | Token最大供应量由Instrument总授权权益容量和固定映射计算，多轮累计不得突破总授权及供应上限 |
| R07 | Token精度由获准合约技术配置控制，不提供企业任意配置；不允许静默四舍五入造成实际权利差异 |
| R08 | Issuer不自行选择Token发行网络、合约标准或部署参数；由平台在生产技术准入后确定受控配置 |
| R09 | 只有R2-05发行准备通过且独立生产技术Gate全部满足，才允许执行真实合约部署；Free Sandbox仅模拟 |
| R10 | 资金及权益分配权威事实满足执行守卫后才可触发Mint；Burn需要独立授权和真实业务依据，默认不自动恢复权益容量 |

### 5.1 数据及展示约束

- Instrument → 1个逻辑Token；Offering → 引用Instrument对应的Token身份并分别记录发行轮次、目标Token数量、分配数量、实际Mint数量及技术异常。
- Token最大供应量与每轮Offering最大Token量、已确认分配Token量、已Mint量是**四种不同口径**，不得混同或重复扣减。
- 已确认分配≠链上Mint成功；Mint失败或结果Unknown必须保留已确认业务分配并核对，不盲目重新Mint。
- Token精度、最小可表达权益单位、映射比例与固定单价需共同满足完整可表示性校验；发生不可准确表示的零碎权益/Token数量时阻止提交并提示，不自动损失权益。
- 投资者支付网络固定为OP Mainnet USDT，并不直接决定Token发行网络；Token合约网络、标准、Provider、Signer、主合约是否能安全承载多个逻辑Token均保持Draft技术决策门。
- 单生产主合约是用户批准的**产品架构目标**，不得误写为已完成合约方案、已批准ERC标准或部署权限。

### 5.2 已批准的V2延后边界

- 企业自选合约及Token精度、任意合约部署参数；
- 多逻辑Token/复合Token和企业定制复杂映射；
- 多链Token同步发行、跨链桥、复杂合约升级治理；
- 高级Burn、赎回、权益转换及自定义转让限制策略。

正式归属已在V3/TBD的能力继续保持原归属；上述条目作为补充候选，不自动纳入DEC-017正式V2的22项。

## 6. R2-04 跨模块一致性审核（Audit Draft，尚未批准）

此表为对已确认五批设计与R2-02/R2-03之间进行的业务交叉核验。表内建议不等于已经获得用户批准，需在后续审核中单独确认。

| 审核项 | 当前一致性检查结论 | 仍需审核的MVP收口建议 |
|---|---|---|
| C01 业务对象关系 | Asset可关联多个Instrument，Project对应一个Asset；Offering只引用一个Instrument版本；逻辑Token按Instrument复用 | 同一Asset首次Offering创建一个默认Project，后续轮次优先复用，不引入多个同资产Project管理与选择流程 |
| C02 同轮排他 | 同一Project不支持多轮并行认购，但Draft、Confirmed、Published、Active的重叠规则尚不够明确 | 同一Project在同一时刻最多有一轮处于可发布/已发布/认购中或暂停后可恢复的当前发行；其他后续轮次可建Draft但不得抢占开放位置 |
| C03 容量与Token账本 | R2-03权益池、R2-04 Offering预留、Token已分配/Mint是不同事实 | 确认Offering只预留一次；订单子预留不重复扣权益池；已承诺与预留转换、结算释放、Burn不自动回充皆按已有规则 |

| C06 生产技术Gate | 一生产主合约、OP Mainnet USDT支付、真实Token网络/标准未冻结 | 将“单生产主合约支持多逻辑Token”标为架构验证门，先通过独立技术和法律审查；Sandbox不得触发真实部署/Mint/Burn |

| C08 发行闭环 | Offering完成与Asset/Instrument存续不能等同 | Completed只代表本轮订单及资金/Token处理结果收口，收益、持仓、赎回、法定登记和资产运营继续由对应模块独立承接 |

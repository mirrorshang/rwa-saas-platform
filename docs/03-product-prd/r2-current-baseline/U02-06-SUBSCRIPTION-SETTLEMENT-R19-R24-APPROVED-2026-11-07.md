## 1. 本批 R19～R24 Approved 内容

| 决策 | 已批准的业务要求 | 适用范围和未决边界 |
|---|---|---|
| **R19｜认购资金路径** | **优先研究并在条件满足时采用同链原子 DvP**（认购支付与 Token 交付原子联动）；若法律资格/签署、合约能力或业务条件不能同步完成，则采用**受控收款→后续配售→退款/恢复**的保护性路径。具体模式由**独立准入**决定，企业不能在 Offering 中自由切换技术收款模式。 | 产品业务路径与优先顺序 Approved；**具体合约/资金保管与控制人/原子交易结构/升级权限/发行与法域适配均未批准**。不得把「合约收款」理解为 SaaS 平台获授权直接托管用户资金。 |
| **R20｜订单与付款** | 投资者输入认购 **Token 份数**，系统依本期固定价格计算 **应付 U**；完成身份、地区/KYC、单笔最低认购、钱包余额/支付能力和可用份数校验后，形成**唯一订单**，再进行 OP Mainnet USDT 支付授权/支付。 | 订单创建本身不是付款成功；须校验同一订单幂等及本期额度。订单级临时额度锁与过期释放的细节待审。支付授权不等于实际已转账；余额不足/授权拒绝应明确提示和恢复。 |
| **R21｜Token 交付与订单完成** | 原子模式下，**获授权的** Token Mint 或已有 Token 交付与 USDT 支付在同笔原子事务；非原子模式下，在法律/业务/支付确认条件满足后另行交付。**只有真实支付和 Token 交付都得到确认，认购订单才显示「已完成」。** | 实际到账 USDT、链上确认、Mint/transfer 事件与最终持有人主账应相互核验；异步收款但 Mint 失败不能称「已完成」；预先 Mint 还是按单 Mint、交易最终性、安全确认阈值、转让限制等仍 Open。 |
| **R22｜企业结算与费用** | 结算目标为**Offering 发布时固定快照的企业绑定收款钱包**；只有 Token 交付及相关准入/结算条件满足后才能结算。发布后变更受控审查并留审计轨迹。**不预设平台费率或分账比例。** | 原子模式可能在同一链上事务中完成支付、交付与允许的资金结算；异步模式需阻止「未交付就先把资金结算到企业」的默认路径。不能把企业收款地址与投资者支付合约地址混为一谈；资金是否法定托管、分账主体/手续费承担、变更需何种签署仍 Open。 |
| **R23｜异常、失败与退款** | 区分**交易失败、付款超时、Mint 失败、配售失败**等状态。原子交易失败应按事务规则回滚链上业务动作；非原子路径提供**可核验的退款或受控恢复**流程，禁止重复扣款、重复 Mint 或重复退款。 | 交易失败时 Gas 费未必退还；退款资格、退款来源/时限/金额、自动和人工处理边界、支付成功但订单超时、链回滚、冻结代币和交易失败幂等策略均另审。不能假设退款一定立刻到账。 |
| **R24｜容量、订单与对账** | Offering **成功发布时预留本期总 Token 份数**；具体订单的待支付/已支付/待交付占用属于本期**预留内部细分**，不能从 Instrument 共享容量中重复扣减。真实交付后相应份数转为「已发行/已交付」，关闭后仅释放没有待处理义务的剩余预留。**订单、资金和 Token 三类业务事实必须可对账。** | 容量主账不能用前端演示值作为生产权威；不能因订单创建/支付失败/关闭造成二次扣减或释放已交付 Token。订单过期/申诉/退款待定期间的冻结时点、并发下原子更新、账本精度与复核程序仍 Open。 |

## 2. 最小用户流程和状态可见性（Approved 原则的 UI 解释）

```text
企业端：资产 → 权益结构 → Offering 单页 → 选择企业最终收款钱包
       → 发布前检查与最终投资者预览 → 受控发布（成功时预留本期额度）

投资者端：
身份/地区/KYC/认购资格检查
  → 输入 Token 份数（最低单笔金额与本期可用额度校验）
  → 页面自动计算应付 U（OP Mainnet USDT）
  → 唯一订单 → 钱包授权/支付（支付状态须真实确认）
  → 若适用原子模式：同一链上交易完成可交付 Token 与符合条件的资金结算
    若适用非原子模式：合约/受控收款 → 必要签署/分配门 → Token 交付 → 受控结算
  → 「已完成」仅在支付与 Token 实际交付均已确认后显示

异常：拒绝授权/余额不足/链上失败/超时/资格失效/分配失败
  → 显示该订单真实阶段、阻断原因与允许的下一步
  → 非原子已收款订单应支持合规退款/受控恢复，不虚构完成

发行结束：在途义务先闭环 → 已交付保留 → 无待处理义务未分配预留释放
```
- 对用户只呈现与动作相关的必要状态和清晰的下一步，复杂合同/交易细节留在详情与审计记录，不增加无用多步表单。
- 「授权 USDT」≠「扣款成功」；「支付交易链上成功」≠「投资者 Token 交付成功」；「认购完成」≠「企业已结算到账」的同义词。各对象归属主账独立可核验。
- 认购费用、Gas、链上失败耗费、平台服务费等须独立可解释；未定金额不得预填固定比例。

## 3. 不可混淆的共享容量口径
例：Instrument 可发行 10,000 Token，Offering 第一期**发布预留** 3,000 Token；本期已交付 1,800、待处理订单 200、未认购 1,000。
- **权益池总占用**不是 3,000 + 1,800 + 200；其中 1,800 从发布预留转为确认已发行，200 与 1,000 属于本期剩余预留的不同子集。
- 关闭后：确认已发行 1,800 继续占用权益；待支付/待交付/退款等待中的 200 继续依规则保留或结清；1,000 在无其他法律/业务义务条件下释放，后续期可用。
- 必须防止同一 Instrument 通过新 Offering/新 InstrumentVersion 增加同一授权权利总数；同一时间最多一轮可开放认购。

2. R20 订单可支付期限、重复钱包签署、订单幂等键、订单临时锁/异步结算重试、转账后交易重组、网络确认数、支付手续费与滑点等技术和精度。
3. R21 的 Mint-by-order / 预铸交付、资格链上证明、Token 合法身份及权利关系、转让限制和异步交付的最大周期。
4. R22 费用比例、链/应用手续费、资金合约实际控制人/法律资金保管主体、钱包受益人变更、平台是否触及受监管活动、对账和提现协议。
5. R23 的退款申请/自动资格、冻结与黑名单、代付 Gas、异常超时处置、链上回滚及异步资金安全责任。
6. R24 的服务端金额与份额主账事务、幂等、并发、关闭中冻结/解除时点和独立审计/数据对账方法。
7. Offering 完整生命周期及发布条件、投资者预览/展示字段、合同版本与签署、法律/资格责任；需后续 UI-Ready/状态机审核。

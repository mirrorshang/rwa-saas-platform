## 1. 文档目的与阅读规则

本文件定义平台总体产品边界、产品线、用户与组织关系、核心业务对象、端到端业务阶段、权限与数据隔离要求、核心模块、非功能要求及后续规格拆分。后续第 04 份业务流程、第 05 份合规与资格规格、第 06 份 UI/UX、第 07 份架构、第 08 份法律研究、第 09 份商业规划应在本文件框架下细化；若发现冲突，应回到对应决策记录，不得自行覆盖。

### 1.1 需求状态标记

- **已确认原则**：已有 DEC-001 至 DEC-010 支持，必须遵循对应决策的具体范围。
- **建议纳入 V1**：总体产品方案建议，需经产品负责人评审后才能成为正式需求。
- **待决策门**：需要独立证据、法律/合作方核验或明确产品决策；本 PRD 不代替决策。
- **后续研究**：保留为扩展方向，不代表 V1 承诺。

### 1.2 本版的决策约束

以下事项明确不在本版中擅自定案：
1. 首批正式开放的国家/地区及运营主体；
2. 首发的 1–2 类资产/金融工具及其具体法律权利结构；
3. 三条商业产品线的具体价格、额度、套餐边界与 SLA；
4. 任一法域下发行安排、招揽/分销、资金收付、托管、法定登记、交易执行及收益/赎回支付等活动的具体责任主体、许可路径与合作安排；
5. 真实资金业务的具体执行方式、实际资金责任主体与正式商业上线授权；链上 Token 发行属于平台目标核心能力，但具体资产类别、合约/协议选择、部署方式及生产启用条件仍须按后续决策与设计确定。

## 1.3 产品负责人逐条确认记录

以下记录总体 PRD 评审过程中由产品负责人明确选择的原则。记录仅代表对应条目已确认，不代表整份 PRD 已冻结或授权开发。

1. **产品线关系：已确认选择 C（2026-10-19）**：统一核心业务能力与必要规则；Issuer SaaS、White-label、Open API/SDK 可根据各自客户需求独立演进其后台功能、产品模块、接口版本、授权与服务等级。统一核心不代表所有页面、功能或交付架构必须相同；共享能力不改变租户隔离和授权边界。
2. **V1 产品建设优先级：已确认选择 A（2026-10-19）**：优先打磨发行机构工作台与核心发行流程，在此基础上扩展白标运营管理能力和 API 产品。此项是建设顺序与产品设计重心，不代表取消另外两条产品线，也不改变 DEC-005 已确认的目标客户优先级。具体 V1 功能仍须结合首发市场、资产类别、客户验证和其他决策门裁剪。
3. **发行项目工作台组织方式：已确认采用推荐方案（2026-10-19）**：发行机构工作台以发行项目为主要日常工作入口，资产档案、文件、专业服务、审核、投资者准入、认购、登记和存续期事项围绕项目组织。资产档案仍作为可独立管理、可被适当项目引用的业务对象；此原则决定主要工作体验，不限定底层技术实现或完整数据模型。
4. **投资者获取与平台职责：已确认采纳推荐原则（2026-10-19）**：V1 默认由发行方负责其项目的投资者拓展与商业关系；在白标模式下，可由具备适当授权的运营商按具体业务安排开展相关工作。平台提供投资者门户、资料收集、身份核验集成、项目级资格判断、认购流程和投资者状态管理能力，但不默认经营统一投资者流量平台，也不默认承担发行、招揽、分销或资金处理责任。具体职责须按适用法域、业务模式、合同与许可安排确定。
5. **Issuer SaaS 基础投资者门户：已确认采纳推荐方案（2026-10-19）**：Issuer SaaS 默认包含基础投资者门户能力，支持展示发行方获准发布的项目、投资者注册/登录、资料提交与身份核验流程接入、项目级资格状态、认购状态、相关文件和通知。门户能力不等于平台提供投资者流量或代替客户拓展投资者。高级品牌定制、独立域名、丰富门户配置，以及白标运营商的多发行机构统一运营能力，可作为后续可选模块或独立套餐评估；具体套餐与收费未定。
6. **商业收费结构：已确认原则（2026-10-19）**：建议采用基础订阅费作为基线，结合有限且易理解的使用额度与可选增值服务。Issuer SaaS 可评估活跃发行项目数、组织席位、模块与支持等级等维度；白标可评估运营商许可、发行机构数量、品牌/域名/环境和实施支持；API/SDK 可评估基础订阅、接口用量、环境、版本/SLA 与集成支持。第三方 KYC/KYB、AML、支付、托管、登记、链上 gas、审计等成本按实际安排单列。投资者认购资金及发行所得不是平台收入；不将按 AUM、募资额、交易量或成功费抽成设为默认收费模式。具体价格、额度、套餐组合和 SLA 仍待市场、成本、法律与客户验证。
7. **真实资金与链上 Token 发行原则：已确认（2026-10-19）**：真实资金业务按完整业务流程进行产品规划，具体资金路径、实际处理主体、服务商和集成方案留待后续设计，并按业务模式与适用要求确定。链上 Token 发行是平台核心业务目标，产品不能仅停留于后台发行记录或模拟 Token；平台应规划从发行准备、规则配置与审批，到适配的链上 Token 创建/部署、铸造、分配、状态与存续期管理的业务能力。具体 Token 标准、合约模板、协议、链与执行方式，应根据资产类别、权利结构、转让限制、存续期规则及适用要求选择，不预设所有资产使用同一技术方案。技术选型与接口实现留待后续架构和开发阶段；真实资金执行、生产环境链上操作及正式商业上线仍需完成适用的法律、合作方、安全和运营条件。
8. **资产存续期管理：已确认（2026-10-19）**：资产存续期管理属于平台核心产品能力规划。除发行准备、链上 Token 创建/部署、铸造和分配外，平台还应规划发行后持有人与权利记录、信息披露/报告、通知、约定收益或利息事件、本金偿还、到期、赎回、违约/异常事件及退出等适用业务。具体事件、计算规则、责任主体和执行方式按获批资产类别、产品条款、适用要求与合作安排细化；平台记录和工作流能力不等于平台当然承担实际支付或法定登记责任。
9. **资产档案与发行项目分离：已确认（2026-10-19）**：资产档案与发行项目是独立业务对象。一个资产档案可在权限与业务规则允许的情况下被不同发行项目引用；每个发行项目独立管理其发行条款、审核、投资者、认购与发行状态，避免把资产本身与某次发行混为一体，并支持后续再次发行场景。
10. **多链适配原则：已确认（2026-10-19）**：产品规划应支持按资产类别、权利结构和业务要求适配不同区块链及 Token 协议；首发链、支持范围、跨链能力与优先级另行决策，不预设所有资产使用同一条链或要求 V1 支持所有链。
11. **合约/协议模板与发行规则管理：已确认（2026-10-19）**：产品应支持受控管理合约/协议适配、发行参数、转让限制及关键规则的配置与版本。生产环境的合约部署、升级或更换应具备明确权限、审批、测试和审计机制；不得允许未经受控审核的关键合约逻辑修改直接进入生产。
12. **关键业务工作流与人工审批：已确认（2026-10-19）**：发行审核、投资者资格例外处理、配售、退款、Token 铸造/分配及存续期关键操作，应支持角色权限、审批节点、异常处理与审计记录。自动化可辅助判断与执行，但不得擅自替代依法或按业务安排应由责任主体作出的最终决定。
13. **全生命周期审计与报告：已确认（2026-10-19）**：平台应对重要业务状态变化、用户操作、审批决定、规则版本、资金对账结果和链上交易结果保留可追溯记录，并按权限提供查询、报告和导出。审计记录需保护完整性，并明确敏感数据的访问与保留规则。
14. **国际化基础能力：已确认（2026-10-19）**：产品设计应考虑多语言界面、日期/时区/数字与货币格式等国际化基础能力；首发语言、翻译内容、当地文件模板及实际开放地区另行确定。
15. **多租户数据严格隔离：已确认（2026-10-19）**：每家发行机构仅可访问其有权访问的资产、项目、投资者与业务数据；白标运营商仅可访问其被授权管理的机构和项目。跨租户访问、资产展示或数据复用必须有明确授权和适用的权限、投资者资格及法域限制，不得因平台共享核心能力而默认共享客户数据。
16. **组织内多角色与细粒度权限：已确认（2026-10-19）**：平台应支持组织管理员、项目负责人、合规审核、财务/运营、只读审计等不同职责角色；权限应可按组织、项目、数据范围和操作类型进行控制，具体角色模板可配置与扩展。
17. **关键操作职责分离：已确认（2026-10-19）**：高风险操作应支持配置由不同人员发起、审核和执行；必须复核的操作范围与审批规则按业务风险、资产类别、发行条款和适用要求细化，避免单人越权或误操作，同时不过度阻塞一般操作。
18. **投资者身份与项目资格分开：已确认（2026-10-19）**：身份核验事实或结果在具备合法依据并满足告知/同意、目的限制、最少数据、权限、有效期、撤销及跨境规则等条件时，可按受控机制复用；每个发行项目仍独立判断投资者资格。默认不跨租户共享原始身份材料。
19. **外部服务可替换：已确认（2026-10-19）**：KYC/KYB、AML、支付、托管、登记、区块链等外部能力应通过清晰的集成边界进行管理，避免产品在总体设计上不必要地绑定单一供应商；具体供应商、集成和替换条件按市场、资产、商业及合规要求确定。
20. **平台运营与客户业务数据分离：已确认（2026-10-19）**：平台运营人员可按职责开展租户开通、服务支持与故障排查，但对客户业务数据的访问应遵循最小必要、授权、权限控制和审计要求，并保护客户机密及投资者数据。

21. **发行项目生命周期状态机（对应评审项 20）：已确认（2026-10-19）**：发行项目应采用明确、可解释的生命周期状态机，覆盖草稿、准备、审核、待发行、发行中、发行完成、存续期、结束/终止等主要阶段，并根据实际流程支持补件、拒绝、暂停和异常等分支状态。每个状态须定义进入条件、允许操作、转换条件、责任角色与审计要求；具体状态名称和转换细节在第 04 份业务流程与状态机文档中细化。
22. **资产、Offering 与 Token 分层建模（对应评审项 21）：已确认（2026-10-19）**：资产代表基础资产或权利对象；Offering 代表一次具体发行安排及其条款、资格与发行状态；Token 代表链上数字凭证及其技术实例。三者需要建立明确关联，但不得混为同一对象或以 Token 的链上存在自动证明底层资产权利、Offering 获批或法定登记完成。
23. **文件与证据作为独立业务能力（对应评审项 22）：已确认（2026-10-19）**：文件与证据应作为可独立管理和关联的业务能力，支持分类、版本、所属对象、提交人、审核状态、权限与审计，并可关联资产、Offering、投资者及存续期事件。文件的上传或存在本身不代表其真实性、充分性或法律效力已获确认。
24. **专业服务协作纳入发行工作流（对应评审项 23）：已确认（2026-10-19）**：平台应规划律师、评估机构等专业服务方参与发行项目的协作流程，支持任务分配、材料提交、补件沟通、成果交付和客户确认。专业服务方仅能访问被明确授权的项目、任务和材料；平台提供协作工具不等于平台替代专业服务方的独立判断或承担其法定/合同责任。
25. **发行审核、配售与链上执行分离（对应评审项 24）：已确认（2026-10-19）**：项目审核、投资者资格、资金到账、配售批准、Token 铸造/分配及权威登记完成应分别建模、分别记录状态和依据，并通过明确关联形成可追溯流程。任一阶段完成不得自动视为其他阶段已完成；链上执行结果不得自动替代资金确认、配售批准或权威登记事实。
26. **异常处理与人工纠正作为标准能力（对应评审项 25）：已确认（2026-10-19）**：平台应将失败重试、人工复核、异常升级、补充证据和受控纠正纳入标准能力。人工纠正须记录原状态、新状态、原因、证据、操作人、时间及必要复核；不得无痕覆盖历史记录，也不得以人工修改内部状态伪造外部资金、服务方、法定登记或链上事实。


27. **通知与待办分离管理（对应评审项 26）：已确认（2026-10-19）**：平台应规划统一的通知与待办能力。通知用于传达状态变化、补件要求、审核结果和其他业务信息；待办用于要求特定角色采取审核、补件、确认或异常处理等行动。应记录通知状态与时间，但通知已发送或已送达不代表用户已阅读，也不自动构成法律或合同意义上的正式送达。
28. **基础运营报表与数据分析（对应评审项 27）：已确认（2026-10-19）**：V1 优先规划支持日常运营所需的基础报表，包括发行进度、认购状态、资金对账差异、配售与登记状态、存续期事件、投资者资格、待办和异常事项。报表查询与导出须遵循角色、组织、项目和数据授权范围；应说明统计口径、数据来源与更新时间，不得将内部统计冒充外部权威事实。复杂分析能力后续评估。
29. **关键配置与规则版本管理（对应评审项 28）：已确认（2026-10-19）**：资格规则、发行参数、转让限制、审批流程、服务商状态映射等重要配置应保留版本、变更人、时间、原因、生效时间及必要审批。历史业务应保留当时适用的规则版本和决策依据；若配置变更可能影响在途业务，应进行影响评估或进入人工复核，不得默认静默覆盖。
30. **客户开通、暂停、恢复与退出（对应评审项 29）：已确认（2026-10-19）**：客户服务生命周期应覆盖申请、审核、合同/产品授权、开通、暂停、恢复、终止与退出。客户账号可用不代表所有市场、资产类别、资金操作或链上生产能力均获准使用。暂停或终止时应明确新业务限制、在途业务处理、数据导出、凭证撤销、记录留存及责任移交；具体处理依据合同、适用规则和业务责任安排确定。
31. **API、Webhook 与事件一致性（对应评审项 30）：已确认（2026-10-19）**：API 与 Webhook 必须遵循与产品界面一致的租户权限、业务资格、审批和审计规则，不得成为绕过控制的旁路。Webhook 应规划签名验证、事件标识、幂等、重试和失败追踪；明确区分事件产生、发送、接收和业务处理完成。接口版本、凭证撤销、环境隔离及用量监测应纳入后续 API/SDK 规格。

## 2. 产品愿景与目标

### 2.1 产品愿景

建设面向全球机构客户的标准化、可配置、多资产 Tokenization SaaS 基础设施，以共享的核心业务对象、生命周期工作流、权限与审计能力为基础，通过可验证的法域配置和第三方服务集成支持不同客户的发行及存续期管理需求。

### 2.2 产品目标

1. **缩短机构搭建时间**：让发行机构使用标准化后台配置资产/金融工具、Offering、投资者准入和发行后管理流程，减少从零建设系统的需要。
2. **覆盖核心生命周期**：从组织开通、资产建档、发行准备、投资者准入、认购状态、配售/登记到存续期事件、报告、转让申请和退出处理，建立可追溯的流程链。
3. **隔离客户并支持授权运营**：Issuer SaaS 客户独立管理自身资产；White-label V1 支持运营商管理多家发行机构，但以严格的租户、组织、资产授权和投资者资格边界为前提。
4. **共享核心、区分交付**：Issuer SaaS、White-label、Open API/SDK 共享通用能力，同时分别配置用户体验、授权范围、品牌、集成、支持和商业合同。
5. **为合规判断提供可配置和可审计工具**：支持规则版本、资格判断、人工覆核、证据引用、操作审计和状态追踪；不宣称软件本身替代法律意见、许可或责任主体判断。
6. **支持后续多资产扩展**：数据模型从一开始考虑不同资产/金融工具的差异；V1 真实交付聚焦经后续决策批准的 1–2 类，而不是同时实现所有候选类别。
7. **支持真实链上 Token 发行**：将链上 Token 创建、部署/铸造、分配及后续管理纳入平台核心产品能力规划；按获批的首发资产类别与业务要求选择适配的合约/协议，不把单一技术标准强加给所有资产。
8. **覆盖资产存续期**：围绕已发行资产的持有人/权利记录、报告通知、约定收益与偿还、到期、赎回、异常事件和退出等场景提供可配置的管理能力，具体范围按资产类别和发行条款裁剪。
9. **支持资产与发行解耦**：资产档案与单次发行项目独立管理，并在授权和业务规则允许时支持复用资产档案。
10. **支持多链与受控合约适配**：按获批资产类型和业务要求选择适配的链、Token 标准/协议及合约模板，并提供发行规则版本、审批、测试和审计控制。
11. **支持关键流程治理**：关键业务流程具备权限、审批、异常处理和审计能力，自动化不得越过必要的责任主体决定。
12. **提供全生命周期审计与报告**：关键操作、状态、规则和外部执行结果可追溯，并支持受控查询、报告与导出。
13. **具备国际化基础**：支持多语言、时区及数字/货币格式的扩展能力，具体语言与地区按后续决策确定。
14. **保障多租户隔离与组织权限**：对客户数据、组织、项目和操作实施细粒度授权；对关键操作支持职责分离和可配置复核。
15. **保护投资者与客户数据**：身份核验复用与项目资格独立判断分离，外部服务采用可管理的集成边界，平台运营访问受最小必要与审计约束。
16. **管理发行项目生命周期**：以明确的状态机、转换条件、责任角色与异常分支管理发行项目从草稿、准备、审核到发行及存续期的阶段。
17. **清晰区分核心业务对象**：分别管理资产/权利对象、具体 Offering 与链上 Token 实例，并通过可追溯关联保持一致性而不混同其含义。
18. **管理文件、证据与专业协作**：支持文件证据的版本、权限、审核与审计，并将律师、评估机构等服务方的任务、补件、成果交付和确认纳入受控工作流。
19. **分离关键业务决定与执行状态**：项目审核、投资者资格、资金到账、配售批准、Token 铸造/分配及权威登记分别记录状态、依据和结果。
20. **提供可审计的异常与纠正机制**：支持重试、人工复核、异常升级、补证和受控纠正，保留完整历史与责任轨迹。


21. **建立通知与待办机制**：区分信息通知和需要责任角色采取行动的业务任务，并保留必要状态与时间记录。
22. **提供基础运营报表**：支持查看发行、认购、对账、配售/登记、存续期、待办与异常情况，并标明数据来源、统计口径和更新时间。
23. **保证关键配置可追溯**：重要规则与配置变更可版本化，识别对在途业务的影响并保留历史决策依据。
24. **管理客户服务生命周期**：对客户开通、暂停、恢复、终止与退出进行受控管理，并区分服务授权与具体受监管业务的启用条件。
25. **保障接口与数据可治理**：API/Webhook 遵循统一权限与事件一致性要求，并提供受控数据导出、迁移和留存/删除处理能力。


26. **建立安全事件响应机制**：对安全事件进行分级、处置、升级和审计，必要时受控撤销凭证或暂停高风险操作。
27. **保障业务可恢复性**：规划备份、灾难恢复与演练，恢复后核对外部事实与业务状态，避免重复执行。
28. **控制产品与生产变更风险**：关键产品、接口、规则、配置和数据结构变更应可追溯，并具备适当测试、审批、兼容与补偿方案。
29. **提供权限继承的搜索能力**：统一搜索不能绕过租户、组织、项目和字段级授权。
30. **保护文件与敏感材料**：对文件上传、访问、下载、审核和留存实施与风险相称的安全控制。
31. **规范客户支持与问题升级**：提供受控工单、内部升级与必要客户沟通，同时限制支持人员对敏感数据的访问。
32. **治理数据生命周期**：按数据类别管理保留、删除、限制处理和合法留存，避免不必要的敏感数据留存。
33. **保护审计记录完整性**：关键审计记录采用只追加和受控更正原则，避免无痕修改或删除。
34. **落实敏感字段权限**：字段级访问控制适用于界面、搜索、报表、导出和 API，并按风险采用脱敏及额外授权。
35. **统一金融数据表达规则**：明确金额单位、精度、舍入、时间基准、时区及汇率/估值来源，保留历史计算依据。
36. **管理数据来源与质量**：标识关键数据来源和权威性，处理冲突、缺失、过期与无法验证的数据。
37. **保证关键计算可复核**：对重要计算保留输入、规则版本、参数与时间信息，支持受控复核和更正。
38. **明确标准产品与服务交付边界**：区分标准产品、实施服务和定制开发，控制交付范围与维护责任。
39. **建立分层配置治理**：明确平台、产品线、租户和项目配置的适用范围、优先级与修改权限。
40. **隔离演示、测试与生产环境**：防止测试数据、凭证或操作误入生产业务，尤其避免真实资金与不可逆链上操作被意外触发。
41. **准确呈现能力启用状态**：区分产品支持、配置完成、业务授权、运行就绪和实际运行状态。
42. **建立上线就绪检查**：在启用约定的真实业务能力前，核验适用条件并保留审批与证据。
43. **规范客户交付验收与责任移交**：根据合同范围记录交付、测试、培训、未解决事项和持续运营责任。

### 2.3 非目标

本版不把以下事项作为默认 V1 目标：
- 平台自营统一全球资产池或公开零售 Marketplace；
- 默认由 SaaS 平台为客户寻找投资者、经营统一投资者流量或撮合跨发行方项目；
- 将高级品牌定制、独立域名或白标多机构运营能力一概视为所有 Issuer SaaS 套餐的默认包含项；
- 在缺少市场、成本、客户和法律验证前，将具体价格、额度、SLA 或募资额抽成方式定为既定方案；
- 公开二级交易市场、公开订单簿、自动撮合或平台自营流动性；
- 平台默认收取、保管、转移或控制投资者资金；
- 无条件建立跨租户共享的投资者身份/KYC 数据库；
- 白标运营商之下的多级代理、经销或转售层级；
- 通过软件开关规避许可或将受监管活动自动认定为可外包；
- 同时上线全部资产类别、全部国家/地区或所有第三方服务；
- 在本阶段直接启动正式业务代码开发或真实资金/链上生产流程。

## 3. 产品线与交付形态

### 3.1 Issuer SaaS

**目标用户**：有持续发行需求的资产管理机构与发行企业（DEC-005 的 A 类优先客户）。

**建议能力**：
- 机构注册/申请、组织资料、管理员与成员；
- 资产与金融工具档案、底层资产证据、权利结构和文件；
- Offering 创建、条款版本、发行准备清单及审批；
- 投资者邀请/申请、身份核验服务接入、项目级资格检查；
- 认购意向、付款指令状态、资金确认/对账状态、配售与登记流程；
- 持有人记录、Token/链上记录关联、发行后报告；
- 利息/收益/分配、到期、赎回、公司行动、违约等已支持生命周期事件；
- 受控转让申请与必要审批；
- 审计、数据导出、服务商连接和客户配置。

以上为候选能力集合；具体 V1 功能须依据首发资产类别与市场决策裁剪。

### 3.2 White-label

**已确认（DEC-002）**：V1 一个白标运营商可管理多家发行机构并运营自有品牌门户；资产仅可在运营商自有或明确获授权范围内展示；不支持多级代理/转售层级。

**交付顺序说明（与已确认评审项 2 一致）**：上述内容定义白标产品线的 V1 目标能力，不表示白标多机构运营必须与 Issuer SaaS 核心发行工作台同期交付。建设顺序优先完成发行机构工作台与核心发行流程，再分阶段扩展白标运营管理能力和 API 产品；具体版本切分仍须在后续迭代计划中评审，不据此自动授权开发。

**建议能力**：
- 运营商品牌、域名和门户配置；
- 发行机构邀请、审核、启用、暂停及退出；
- 发行机构与资产授权关系管理；
- 运营商与发行机构分层的组织、角色和权限；
- 门户资产目录、访问规则和投资者准入配置；
- 运营审查队列、异常处理、服务商配置与审计；
- 合同终止、授权撤回、资产下架、数据导出和未完成业务移交。

白标管理权限不意味着运营商可随意读取所有原始 KYC 材料、改变发行方依法承担的业务决定或绕过资产授权与投资者资格限制。

### 3.3 Open API / SDK

**已确认（DEC-002）**：作为独立商业交付线。

**建议能力**：
- API 凭证、应用/环境管理和权限范围；
- Asset / Instrument / Offering / Investor Reference / Eligibility / Subscription / Payment Status / Allocation / Register Reference / Lifecycle Event 等资源接口；
- Webhook 订阅、签名验证、重试、幂等键和事件追踪；
- 版本管理、速率/用量观测、错误文档、Sandbox 与示例；
- API 调用审计、密钥轮换、撤销与环境隔离。

API 不是绕过 UI 权限、合规规则、客户隔离或业务审批的旁路。原始敏感数据默认不因 API 接入而开放。

### 3.4 配套产品层

- **投资者门户**：发行方或白标客户面向终端投资者的品牌化入口，显示经授权且满足资格规则的资产/Offering。
- **平台运营管理端**：管理 SaaS 客户、产品线开通、系统级配置、服务商连接状态、运营异常和审计；平台运营人员不得因此默认获得客户敏感业务数据的无限访问权。
- **开发者门户**：API 文档、凭证、Sandbox、Webhook 调试与用量信息。
- **商业管理能力**：合同、套餐授权、用量、账单和续费等后续模块；具体商业规则依 DEC-010 及第 09 份文档确认。

## 4. 用户、角色与组织模型

### 4.1 核心主体定义

| 主体 | 定义 | 核心边界 |
|---|---|---|
| SaaS Customer / Tenant | 购买软件或签订服务合同的客户 | 默认独立数据与管理边界 |
| Issuer Organization | 实际发行或负责项目的机构 | 仅管理获授权的组织、资产及 Offering |
| White-label Operator | 使用自有品牌运营门户并管理多家发行机构的客户 | 只在授权范围内管理发行机构和资产 |
| Investor | 申请、查看或参与具体 Offering 的个人/机构 | 资格按项目、工具、法域与时间独立判断 |
| Platform Operator | SaaS 提供方的内部运营角色 | 按职责最小授权，不默认可查看所有敏感资料 |
| Service Provider | KYC/KYB、支付、托管、登记、审计等外部服务方 | 按合同、集成权限和明确责任范围提供服务 |
| API Client | 经授权调用平台 API 的客户应用 | 权限不超过其所属客户及被授权资源范围 |

实际合同主体、法定发行主体、数据控制/处理角色、资金责任主体和登记责任主体可能不同，须在具体业务场景中明确，不能仅凭系统中的组织类型推断法律责任。

### 4.2 角色建议

- Tenant Owner / Customer Admin：客户组织设置、成员与授权管理；
- Issuance Manager：资产档案、Offering、发行准备和发行后运营；
- Compliance Reviewer：在被授权范围内查看核验状态、资格结果并进行覆核；
- Finance / Reconciliation Operator：处理付款状态、对账异常、退款流程及相关记录；
- Register / Lifecycle Operator：持有人记录、事件及经授权的更新流程；
- White-label Operator Admin：管理运营商门户、获授权发行机构和运营配置；
- Issuer Admin：管理单一发行机构的资产和业务；
- Investor：管理自身资料、查看可访问 Offering、提交申请/认购意向并查看状态；
- API Developer：管理 API 应用、密钥、Webhook 和 Sandbox；
- Platform Support / Operations：处理客户支持与系统异常，敏感数据访问需有明确权限、目的和审计；
- Auditor / Read-only Reviewer：只读访问获授权范围内的记录。

角色名称是产品模型建议，不代表最终权限矩阵已冻结。最终权限应按租户、组织、资源、操作、业务状态、数据敏感级别及授权关系共同判定，而不只依赖角色名称。

### 4.3 多租户与授权规则（已确认原则）

1. 默认以 Tenant 作为数据隔离边界；同一 Tenant 内仍需按 Organization、项目、资产和角色进一步授权。
2. Issuer SaaS 默认服务单一发行机构；White-label 允许一个运营商管理多家发行机构，但各发行机构间不默认共享数据或投资者资料。
3. 门户资产可见性必须同时检查资产/Offering 状态、门户授权、发行方授权、投资者资格及适用市场配置。
4. 跨发行方展示/分发须存在可审计的明确授权及其有效期、范围、撤销状态。
5. SaaS 厂商内部支持访问应最小化、限时/限目的（如适用）并留痕；系统管理员身份本身不等于业务数据所有权。
6. API、导出、报表、搜索、通知和后台任务必须应用同等隔离规则，防止只保护页面而泄露数据。
7. 客户终止、白标授权撤销或成员离职后，应撤销相关访问，并按适用留存要求处理数据、未完成业务和导出。

## 5. 核心业务对象

下表为总体逻辑模型，不指定数据库结构、服务边界或技术实现。

| 对象 | 目的与主要关系 | 关键约束 |
|---|---|---|
| Tenant | SaaS 客户/合同与隔离根 | 资源必须可归属并受租户边界保护 |
| Organization / Legal Entity | 发行机构、运营商、服务方等组织主体 | 组织类型不自动决定法律责任 |
| User / Membership / Role | 用户、组织成员资格、角色与授权 | 支持撤销、审计与最小权限 |
| Asset | 底层资产及其证据资料 | 底层资产不等于投资者实际取得的法律权利 |
| Instrument / Legal Right | 投资者取得的金融工具或合同权利结构 | 需明确权利、义务、限制、登记与退出方式 |
| Offering | 某次发行/募集/认购安排与条款版本 | 具有明确所属方、状态、资格规则和适用条件 |
| Offering Document | 条款、披露、合同及相关版本文件 | 版本与批准记录可追溯 |
| Investor Profile | 投资者基础账户及必要资料 | 按敏感度、目的与授权控制访问 |
| Verification Event | 身份/核验服务方返回的事实、时间、有效期与引用 | 不等同于项目资格或业务批准 |
| Due Diligence Result | KYC/AML 或其他尽调结果 | 责任主体、可见范围及复用依据待具体化 |
| Eligibility Decision | 某投资者对特定 Offering 的资格判断 | 关联规则版本、时间、结果、原因与覆核 |
| Subscription Intent | 投资者表达参与意向/提交申请 | 不代表资金已到账或配售已完成 |
| Payment Instruction / Payment Status | 外部支付指令及权威状态引用 | 来源、时间、外部参考号与状态需可追踪 |
| Reconciliation Record | 预期与实际资金/交易状态的核对结果 | 支持差异、未知、人工复核与纠错 |
| Allocation | 配售/分配结果与批准记录 | 收款不自动等于配售批准 |
| Register Entry / Register Update | 持有人及权利记录或其权威登记引用 | 法定权威来源需按场景确定 |
| Token / Chain Transaction | 链上凭证、交易及链上状态 | 链上记录不自动取代法律权威登记 |
| Distribution / Repayment Event | 利息、收益、还本、赎回或其他现金流事件 | 真实付款责任和执行方需独立确定 |
| Transfer Request | 受控转让申请、资格、同意与处理状态 | 申请、对价结算、登记及链上执行分开建模 |
| Lifecycle Event | 到期、违约、公司行动、估值更新等事件 | 事件类型由首发工具范围决定 |
| Service Provider Connection | 服务方配置、凭证引用、状态和权限 | 不将集成成功视为服务方责任已确认 |
| Audit Event | 关键访问、状态变化、授权、导出与人工操作 | 不可由普通业务角色随意修改或删除 |
| Commercial Entitlement | 产品线、合同授权、套餐和用量 | 具体价格、额度与规则待商业决策 |

## 6. 核心业务生命周期（总体层）

以下是建议的业务阶段框架，不代表所有阶段必须在一个线性状态机内，也不代表每个资产类别均有相同步骤。

### 6.1 客户开通与治理

客户申请/创建 → 组织资料收集与审核（如适用）→ 合同与产品线授权 → 管理员与角色配置 → 服务商/法域配置 → 可用能力开通 → 持续复核、暂停、终止或退出。

关键要求：
- 客户账号可用不等于其所有业务、资产或市场均获批准；
- 产品线授权、组织审核、法域准入与具体业务权限分开记录；
- 暂停或终止时区分登录/新业务限制、在途业务处理、数据导出和法定留存。

### 6.2 资产与 Offering 准备

资产/权利结构建档 → 上传/引用证明与文件 → 指定负责组织与服务方 → 配置适用市场、投资者资格和限制 → 创建 Offering 与条款版本 → 内部审核/外部专业审查（按场景）→ 满足发布前置条件 → 发布或保持草稿/暂停。

不得将资产档案已创建等同于法律权利已验证、发行已获批准或已取得必要许可。具体发布门槛须在首发资产和市场确定后进一步细化。

### 6.3 投资者准入与资格

投资者访问门户 → 必要资料收集 → 身份核验/尽调服务流程（如适用）→ 形成核验事实与结果 → 对特定 Offering 执行资格判断 → 通过、拒绝、待补充、过期或人工覆核 → 授权查看或提交认购意向。

关键要求：
- 核验完成不等于满足某个 Offering 的资格；
- 资格判断须关联适用规则版本、时间、结果和原因；
- 原始敏感材料不默认跨租户共享；
- 规则或投资者状态变化后，应能识别受影响的在途业务并进入适当复核流程。

### 6.4 认购、资金状态、配售与登记

认购意向/申请 → 必要审核与资格复核 → 外部付款指令（如适用）→ 外部权威来源确认资金状态 → 对账与异常处理 → 配售决定 → 权威持有人记录更新 → Token/链上记录更新（如适用）→ 向相关方显示状态。

强制区分以下概念：
- 认购意向 ≠ 付款指令；
- 付款指令已创建 ≠ 资金到账；
- 资金到账 ≠ 对账完成；
- 资金到账 ≠ 配售批准；
- 配售批准 ≠ 权威登记更新完成；
- 链上交易成功 ≠ 所有法律登记/结算义务均已完成。

状态须有权威来源、更新时间、外部引用和异常路径。未知/处理中不得自动转换为成功或失败。

### 6.5 退款与异常

退款申请/触发条件 → 权限与原因检查 → 必要审批 → 向责任支付/资金机构发起指令 → 外部状态跟踪 → 对账确认 → 成功、失败、未知、退回或人工处理。

发起退款不代表退款完成。必须支持幂等、重复回调处理、超时/未知状态、人工纠错与审计。平台是否可发起或控制真实资金操作须由具体业务、法律与合作安排确认。

### 6.6 存续期管理

按工具类别启用相应事件，例如利息、收益分配、估值/NAV、报告、公司行动、到期、还本、赎回、违约、清算和投资者通知。

每类事件至少需要明确：触发来源、负责主体、规则/计算依据、审核权限、预期记录、外部执行方、状态来源、失败处理、投资者通知和审计。未经首发资产范围确认，不把上述所有事件均视为 V1 必做功能。

### 6.7 受控转让（DEC-009 边界）

投资者/授权方提出转让申请 → 识别工具与限制 → 资格检查 → 必要的发行方同意/优先购买权/其他审批 → 对价结算路径确认（如适用）→ 权威登记更新 → 链上更新（如适用）→ 通知与审计。

V1 默认不提供公开订单簿、自动撮合、平台自营流动性或未经批准的交易执行。转让申请、批准、对价交割、权威登记和链上操作是不同阶段；具体能否支持真实转让由资产、法域、合作方与责任分工决定。

### 6.8 客户退出与数据治理

合同/授权终止或客户迁移 → 限制新增操作 → 列出未完成 Offering、认购、资金、退款、登记和存续期义务 → 数据导出与接收方确认 → 权威记录/责任迁移（如适用）→ 按要求保留、删除或限制处理数据 → 撤销凭证/访问 → 留存审计证明。

不能因 SaaS 合同结束而删除仍需依法保存的记录，也不能以“法定留存”为由无限制保留所有资料；具体规则由适用法律、合同和责任主体确定。

### 6.9 客户实施、上线与交付验收

对包含实施、迁移、定制或集成的客户，按合同约定管理实施范围、配置、测试、培训、验收和责任移交。标准自助开通可采用精简流程，但不得省略适用的客户授权、安全与业务上线条件。

上线就绪检查应按拟启用的产品线、市场、资产类别和真实业务能力裁剪，并记录检查项、责任人、证据、未解决风险、批准结果和生效范围。产品能力支持、配置完成、客户服务开通、业务授权与生产运行就绪应分别判断；任何一项必要条件未满足时，相关能力不得被视为可正式运行。

演示、测试与生产环境须保持清晰隔离。测试场景应明确标识模拟数据与外部服务状态；生产环境中的真实资金、正式投资者沟通、Token 铸造或其他高风险/不可逆动作须有单独的授权和控制。具体环境架构、部署数量及技术实现由后续架构文档确定。

客户交付验收应以合同约定的范围和可验证证据为依据，记录已交付内容、测试结果、限制与未完成事项、培训文档、后续责任和客户确认。验收不能替代监管批准、法律意见或第三方授权，也不能把平台交付验收等同于客户真实业务已获准上线。

## 8. 跨模块通用业务规则

1. **状态与事实分离**：内部工作流状态不得冒充外部权威事实；所有外部状态记录来源、时间和引用。
2. **状态可解释**：每个重要状态应定义进入条件、允许操作、退出条件、失败/未知状态、人工处理和审计。
3. **关键动作有权限**：发布 Offering、修改条款、确认配售、修正登记、发起退款、批准转让、授权跨租户共享等操作须具备独立权限及必要的审批/复核。
4. **关键记录版本化**：条款、资格规则、业务配置、服务商状态映射和重要批准应保留版本与生效时间。
5. **避免隐式自动执行**：不能因一个上游状态成功就自动完成资金、配售、登记或链上执行，除非该场景经过明确产品、法律和运营审批。
6. **人工纠错可审计**：允许授权人员处理异常，但应记录原状态、新状态、原因、证据、操作人、时间和必要复核。
7. **幂等与重复事件**：付款回调、Webhook、链上事件和后台任务须处理重复、乱序、超时和重试。
8. **通知不等于法律送达**：通知的发送/送达状态与合同或法律要求的正式通知效果分开；具体要求待法律研究。
9. **数据导出受控**：导出应校验范围、目的和权限，记录操作者、时间、对象范围及结果。
10. **配置不得替代批准**：未完成相应法律、合作方和产品上线门槛时，不得仅通过配置开启真实市场、资金、托管、登记或交易能力。
11. **数据保留与删除按类别治理**：删除请求、客户退出和合同终止均须结合数据类别、适用依据、在途业务及依法留存要求判断，并保留处理记录。
12. **敏感字段权限贯穿所有出口**：界面、搜索、报表、文件下载、导出和 API 均须执行适用字段权限；不得通过其他入口绕过脱敏或授权控制。
13. **金融数据与计算可追溯**：重要金额、时间、汇率/估值和计算结果应保留单位、来源、适用时间、规则版本及必要输入；来源冲突或计算错误须进入受控复核与更正流程。
14. **产品支持不等于获准启用**：产品版本支持、配置完成、业务授权、运行就绪和实际运行状态分别记录；不得将其中单一状态冒充整体上线批准。
15. **测试与生产严格区分**：演示/测试数据、凭证、服务配置与生产操作须隔离；不得由测试流程意外触发真实资金、正式通知或生产链上不可逆操作。
16. **交付与上线分别验收**：客户实施交付验收、平台内部上线检查、外部法律/监管/合作方授权是不同事项，不得互相替代。
17. **配置遵守分层优先级**：客户或项目级配置不得覆盖平台强制安全底线、已批准的业务边界或适用要求；关键变更须可追溯。

## 9. 非功能要求（总体基线）

本节提出后续架构与验收需要量化的质量属性；具体数值目标须在架构、成本和服务等级评审后确定。

### 9.1 安全与访问控制
- 默认拒绝未授权访问；所有资源访问均需服务端验证租户、组织、角色、资源范围和业务状态。
- 对敏感数据采用最小收集、最小暴露和分级授权；密钥与凭证不得以明文暴露于普通日志。
- 支持关键凭证轮换、撤销、会话失效及异常访问调查。
- 管理员与支持人员的敏感操作应可审计，并根据风险采用额外确认/复核。

### 9.2 隐私与数据治理
- 区分身份资料、核验事实、尽调结果、资格决定、业务决定和审计记录。
- 支持数据来源、处理目的、访问/共享范围、有效期、导出、更正、限制处理、删除与留存策略的可配置治理。
- 跨境、数据驻留、保留期限、删除权及数据控制/处理角色须按实际市场和合同验证，不预设全球统一规则。
- 数据保留、删除和限制处理应按数据类别、目的、适用依据及责任主体管理；无法按请求删除时，应记录具体依据和后续复核条件。
- 敏感字段权限应一致应用于界面、搜索索引、报表、导出、文件访问及 API 响应。

### 9.3 审计与可追溯性
- 关键状态转换、授权变更、条款版本、资格判断、资金状态、配售/登记、退款、转让、数据导出及人工修正均可追溯。
- 审计事件包含足够的主体、时间、上下文、结果和引用信息；避免在审计日志中复制不必要的原始敏感资料。
- 具体防篡改级别、保存周期和审计导出格式待架构与合规设计。
- 关键审计记录应采用只追加、受控更正的原则；技术实现和保留周期按风险、适用要求与成本确定。

### 9.4 可靠性与数据一致性
- 关键工作流支持重试、幂等、超时、未知状态、补偿和人工处理。
- 区分外部系统最终状态与本平台记录状态；外部服务不可用时不得虚构成功。
- 对数据修正、对账差异和事件重放定义权限与操作记录。
- 重要金融计算应保留必要输入、规则版本、关键参数、计算时间与复核/更正轨迹；金额单位、精度和舍入规则应明确。

### 9.5 可配置性与多资产扩展
- 共享通用对象和生命周期能力，同时允许资产/金融工具定义专属字段、事件和约束。
- 不将所有法律权利强行映射为同一套不可区分的“Token”字段。
- 市场、资产、资格规则、服务商和流程配置应具备版本、生效时间和审计；哪些配置允许客户自助修改仍待权限设计。

### 9.6 集成与可观测性
- 外部集成需明确接口契约、状态映射、超时、重试、幂等、告警与人工处理机制。
- 记录必要的请求关联标识、服务方引用和错误类别，避免记录不必要的敏感载荷。
- API 应有版本兼容、凭证管理、用量观测和安全限制；精确 SLO、速率限制与 SLA 待定。

### 9.7 可用性、国际化与可访问性
- 支持响应式布局与主要业务场景的清晰错误、空状态、加载、处理中和失败反馈。
- 国际化架构应预留语言、时区、日期/数字/币种格式及区域化文案；首发语言、币种和无障碍目标待市场证据确定。
- 不能因为产品定位全球化而默认首版必须完成所有语言、所有币种或所有地区格式。

### 9.8 备份、恢复与运营连续性
- 明确备份、恢复、灾难恢复、服务方故障和业务连续性方案。
- RPO/RTO、可用性目标、日志保留和恢复演练频率由架构及商业 SLA 决策确定，不在本版虚构数值。

### 9.9 环境隔离、交付与上线就绪

- 演示、测试和生产环境的边界、凭证、数据与外部服务配置应明确；具体环境数量和部署形式由架构阶段确定。
- 真实资金、生产 Token 操作、正式投资者通知及其他高风险操作须具备独立的生产授权与必要保护措施。
- 上线就绪清单应按实际产品线、市场、资产类别和启用能力裁剪，并保留检查结果、责任人、证据与批准记录。
- 客户交付验收应关联合同范围、测试证据、已知限制、未完成事项、培训与责任移交；不得用页面可访问或内部检查通过代替外部授权。
- 产品支持、配置完成、业务授权、运行就绪和实际运行状态应分别表达，避免误导客户或运营人员。

## 10. 建议的验收原则

本 PRD 的总体验收应以可验证行为而非仅以页面存在为准。至少包括：

1. 租户 A 的普通用户无法读取、搜索、导出或通过 API 获取租户 B 未授权的资产、投资者资料和业务记录。
2. White-label 运营商只能管理被其授权管理的发行机构；子发行机构不能因同属一个运营商而默认互相访问敏感数据。
3. 未经明确授权的资产不会出现在其他客户门户或可被其 API 访问；撤销授权后，系统按定义停止新增可见/访问并处理缓存、通知和在途业务。
4. KYC/身份核验状态不能自动替代具体 Offering 的资格判断；资格判断可追溯到规则版本、时间、结果和原因。
5. 认购意向、付款指令、实际资金状态、对账、配售、权威登记和链上交易在数据与状态上可以区分。
6. 未知/处理中资金状态不能自动作为成功或失败；重复回调和重试不会重复创建配售、退款或登记动作。
7. 退款发起、外部处理和确认结果可区分；失败、未知和退回状态有可审计处理路径。
8. 受控转让流程能区分申请、资格、发行方同意、对价结算、权威登记和链上更新；不出现默认公开订单簿或自动撮合。
9. 关键条款、权限、资格、资金、配售、登记、退款、转让、数据导出和人工纠错操作可审计。
10. 客户退出流程能处理访问撤销、数据导出、未完成业务、权威记录迁移及按适用要求留存/删除。
11. 真实市场、资金、托管、法定登记、交易执行或收益支付能力在对应市场/工具未完成法律和合作方确认前，不得仅凭产品配置被视为获准上线。
12. 所有正式验收项均应关联测试场景、预期结果、责任角色和证据；具体数值型性能与可用性目标在架构阶段补充。
13. 标准产品、实施服务和定制开发范围可区分，客户交付内容与合同/约定范围相符；超出范围的需求有单独评估记录。
14. 平台级、产品线级、租户级和项目级配置遵循定义的权限与优先级，客户配置无法覆盖强制安全规则或已批准边界。
15. 演示/测试与生产环境的凭证、数据和服务配置按约定隔离；测试不得触发真实资金、正式投资者通知或生产链上操作。
16. 关键业务能力可分别展示产品支持、配置、授权、运行就绪和实际状态；缺少必要条件时能说明限制原因，且不会误报为已获准上线。
17. 正式上线就绪检查可提供与实际产品线/市场/资产/能力相符的检查记录、证据、责任人和批准结果；内部检查不冒充外部法律或监管授权。
18. 客户交付验收可追溯交付范围、测试证据、已知问题、未完成事项、培训与责任移交；验收结论与正式业务上线批准分别记录。

## 12. 后续文档拆分与工作顺序

建议按以下顺序推进，不将本 PRD 直接视为开发任务：

1. **第 03 份 PRD 评审**：确认总体范围、角色/对象、生命周期和非目标；记录修改与产品负责人批准。
2. **客户发现与决策门研究**：并行收集市场、首发资产、客户需求/支付信号、合作方及法律可行性证据。

## 一、产品流程分批策略

按**客户购买 SaaS 并进入真实发行流程**的顺序，而非单纯按模块编号。跨模块守卫必须在每批出现其首次业务触发位置，不允许将安全/权限留到最后补。

| 审核批次 | 主要业务问题/用户成果 | 主责模块与依赖 | 本轮要审核的详细交付规格 | 冻结/法律阻断条件 |
|---|---|---|---|---|
| **Batch 01｜商业开通与组织权限** | 客户购买/签约后如何获得可使用的独立 Issuer 工作台，谁能操作、暂停/退租如何处理 | **M01/M02/M03**；M17/M19/M20 安全依赖 | 在线入口、机构/合同/套餐记录、Tenant 与 Role、业务状态/暂停、异常/审计、必要客服路径；不默认开发在线自动收款/CRM | 合同/商业授权≠发行法定许可；管理员不能绕过隔离和双人复核 |
| **Batch 02｜资产/Instrument 与文件** | 机构如何声明资产、权利/义务主体、A/B 法律文件、专业复核和版本 | **M04/M06**；M19/M22 | Asset 与 Instrument 分离、权利片段/版本、证明/审查/签署证据、A/B 条件字段及最小表单 | 文件/专业审查与法律生效/合法发行权限仍需真实权威 |
| **Batch 03｜Project/Offering 与发行前置** | 如何建立项目、设定 Offering 参数/持续一级认购、批准发布、暂停/关闭 | **M05/M19**；M04/M06/M09/M11/M12/M07 接口 | 项目/发行轮次、价格/币种、发行额度、资格、条款冻结/变更、发布前 Guard、A1/B1/B2 条件模式 | 真实法域、发行工具/资本授权、收款/Token 法定先后未确定不可开放生产 |
| **Batch 04｜投资者/认购/真实资金与配售** | 机构提供投资者门户后，投资者如何准入、签约、支付、占额和获配 | **M08/M09/M10/M11/M12**；M06/M17/M19/M22 | Offering 资格、钱包/签署、报价、预留、真实 USDT/USDC 支付回执、对账/退款、配售与法定登记证据、错误恢复 | 法定登记、资金控制/退款、资格与外部最终性须各自受权 |
| **Batch 05｜真实 Token、交付及外部执行** | 合约如何受权部署/Mint，交付何时合法完成，第三方失败怎样恢复 | **M07/M22**；M12/M19/M20 | Token 版本/链、签名/合约、转让限制、最终性、法律登记与链事实不同步处理、审计与复核 | 不默认 SaaS 控制私钥/法定登记或可自行创造法律权利 |
| **Batch 06｜存续期、法定通知、报表与全程验收** | A 的票息/还本及 B 的合法可选分红/回购如何登记、真实出款、异常/退出 | **M13/M17/M18/M20/M21**，横贯 M01～M22 | 现金流与权利快照、出款及对账、逾期/公司行动适用性、受控通知/导出、退租与责任移交、完整 E2E 设计 | 真实法域与债务/公司权威、外部资金、合约事件及正式验收证据 |

**非默认首期边界**：M14 受控二级转让仍 V2；M15 White-label 与 M16 商业 Open API 是独立产品发布批次。Issuer V1 内部必须满足 ARCH-001 的统一业务 API-First/Contract-First，**不等于对外发售商业 API**。C/D/E 十八条 GAP 保持长期参考，不能因为设置 Instrument 家族字段就宣称生产支持 NAV/版税/储备仓单。

## 二、每批必须交付的最小审核表（建议模板）

对每个正式 Mxx-Fxxx：
1. **用户目标与入口/状态展示**：机构/运营/投资者端谁可进入，入口在哪个逻辑页面组，最小信息是否足够，不强制一功能一页。
2. **可执行领域命令/API-First**：create/update/approve/pause/observe/reconcile/close 哪些是真实受权动作，哪些只读；给出输入、前置 Guard、响应/错误及幂等边界，不必提前指定接口 URL。
3. **权威事实/字段/版本**：哪个模块写入、哪个第三方回执或法律文书决定生效；Quote/Offering/Instrument 等关键快照不可静默覆盖。
4. **角色授权和审计**：最小角色、Tenant/Project/Offering 隔离、审批分权、撤权、敏感数据最小可见。
5. **正常状态与异常/Unknown**：必要状态转换、在途/暂停/撤销/失败/恢复及不能产生的副作用；不得将用户 UI 的成功动画当资金/权利/链成功。
6. **交付定位**：受批 P0 最低能力、可复用 UI、受权外部执行、条件性 P1 或增强后置；对真实法域未知时明确独立决策门。
7. **验收设计和证据**：至少成功/拒绝/越权/并发或重复请求/异常恢复的测试断言、法律/外部证据引用及 Not Executed 标签；只有真正运行测试后才可更新 PASS。

**术语**：建议先采用三态“必做最低能力 / 按实际 Instrument 触发 / 当前不做增强”，另将“真实法域/受权服务商待确定”作为**依赖/阻断标签**，不要误将未获法律准入的生产动作纳入已交付。接口和数据库具体技术形式依后续架构评审。

## 三、G-01～G-06 的并行决策门，不应被六批页面设计取代

| 门 | 审核材料/责任 | 与交付深度的关系 |
|---|---|---|
| **G-01** 真实首发 Instrument / 法域 | 产品、发行/法律责任方确认具体权利及合规资格 | 可先做通用草案，但真实发行“生产可用”不能冻结 |
| **G-02** 外部主体及执行权限 | 发行人/公司机关/收款退款/分红还本/登记/电子签/密钥责任人 | 涉及真正资金和合法权利的 API 必须受控不可用 |
| **G-03** 合法发行/募集模式 | A1 同权增发与晚入报价，B1 公司授权资本、必要 B2 集中配售 | 若 ContinuousPurchase 不适用，条件性 P1 Batch 不能隐性丢失 |
| **G-04** 16 项 P1 最低能力 | 对 A/B 逐条审查实际条件、资金/法定安全底线、增强 UI | 不能把 P1 无条件视为全部忽略或全量开发 |
| **G-05** 187 项实现深度 | 每批逐 ID 绑定事件/API、页面、权限、异常、责任和验收 | 只此门完成后才可形成真实产品详细交付清单 |
| **G-06** 证据与独立签收 | 产品/法律/受权执行方/工程测试，按阶段不同职责签收 | 文档级规则 Approved 不等于沙盒/测试链 E2E 或合规 PASS |

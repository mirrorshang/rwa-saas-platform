# RWA SaaS Platform｜产品战略与商业模式

文档编号：02 / 10｜版本：**Draft v0.1**｜日期：2026-10-16
状态：**讨论稿，未冻结**；适用于从零新建项目，与任何既有 WDEX 产品和代码无复用假设。

## 1. 执行摘要

建立面向全球客户的**标准化、可配置、多资产 Tokenization SaaS 基础设施**，服务资产发行方、基金/资产管理机构、金融科技公司及 RWA 服务商。产品设计从一开始面向跨市场复用：以统一核心数据模型、工作流和产品能力为基础，通过法域、资产/金融工具、投资者资格、服务商和业务流程配置适配不同市场，而不是为单一国家定制整个平台。

已确认客户拓展优先级为：**A 类有持续发行需求的资产管理机构与发行企业优先；B 类 RWA 服务商/区域平台运营商重点跟进；C 类金融科技公司及机构 API 客户独立拓展**（DEC-005）。主要售卖标准化发行与存续期软件、客户自有品牌 White-label 平台及 Open API/SDK 接入能力。

**市场策略：全球客户发现 + 有证据的首批市场选择。** 日本和阿联酋仅作为候选研究市场，不是已确认的优先市场，也不构成排他范围。首批市场顺序须结合可触达客户与试点证据、实际需求和付费信号、法律可行性、合作方可用性、竞争情况、交付成本及商业可行性综合评估后决定（DEC-006）。

**收入以 SaaS 订阅、白标授权、API/用量和企业增值服务为主**；不以自行买卖 RWA 资产、吸收资金、自营投资平台流动性或承诺收益作为基本商业模式。

核心原则：技术基础设施尽可能标准化，市场适配通过配置与可验证的集成实现；不同金融工具的法律权利、投资者资格、资金路径、登记及转让规则必须按资产和法域单独评估。全球化产品定位不代表所有法域或所有金融活动均可直接上线。

## 2. 战略基线（已确认）

1. 对标 Brickken 的产品类别、商业交付方式和核心生命周期，但不照搬其 UI 或未经实测的内部实现。
2. 完全从零搭建独立项目；不沿用既有项目作为产品基线。
3. **【已确认｜DEC-002】** 商业产品线包括 Issuer SaaS、White-label 与 Open API/SDK；标准 SaaS 面向单一发行机构，White-label V1 支持一个运营商管理多家发行机构并运营自有品牌门户，Open API/SDK 是独立交付产品线。投资者门户、平台管理和开发者服务为配套产品层。
4. 优先 ToB 发行及运营基础设施，不预设自营统一的全球零售资产聚合市场。
5. **【已确认｜DEC-004】平台首要提供软件、流程管理、合规配置及第三方服务集成。** 涉及证券发行安排、投资者招揽/分销、资金收取与转移、托管、法定登记、交易执行及收益/赎回支付等受监管活动时，不预设由平台自行承担或一定可以外包；必须根据拟服务法域的具体法律意见、实际业务模式与合作机构安排逐项确定责任主体和上线前置条件。软件配置、合同措辞或第三方 API 不能替代许可要求。详细约束见 [DEC-004](../../decisions/DEC-004-regulated-activity-responsibility-boundaries.md)。
6. **【已确认｜DEC-006】全球化产品设计、全球客户发现、证据驱动的首批市场选择。** 不预先把日本、阿联酋或其他任何单一国家定为唯一/优先市场；市场选择与产品定位分开决策，并保留逐市场法律可行性门槛。详见 [DEC-006](../../decisions/DEC-006-global-product-and-market-selection.md)。
7. 当前阶段先做竞品、产品、UI/UX 与业务规则文档，正式业务研发另行授权。

以下其他表述均属于**战略建议/待决策**，未因写入本文件而自动冻结。

## 3. 目标客户与价值主张

**【已确认｜DEC-005】客户拓展优先级：A 优先、B 重点跟进、C 独立拓展。** 该排序用于安排首阶段产品发现、客户访谈和需求验证，不代表市场规模、付费意愿或具体获客假设已得到验证。详见 [DEC-005](../../decisions/DEC-005-target-customer-priorities.md)。

| 客户 | 核心问题 | SaaS 价值 | 购买产品 |
|---|---|---|---|
| 资产持有人/发行企业 | 不想从零建设资产登记、发行、投资者与收益系统 | 自助创建合规可配置的发行/管理流程 | Issuer SaaS |
| 私募基金与资产管理机构 | 不同资产、份额、投资者资格、募集/存续管理复杂 | 金融工具模板、权限、申赎/分配与对账 | SaaS/Enterprise |
| RWA 服务商 / 区域平台运营商 | 需要以自有品牌服务多个发行客户 | 品牌、门户、机构角色及授权运营 | White-label |
| 银行/Fintech/开发型机构 | 已有客户或业务系统，希望嵌入代币化能力 | API、SDK、Sandbox、Webhook 与集成支持 | API/Enterprise |

**对投资者的产品关系**：投资者一般作为发行方或白标客户的终端用户访问客户拥有的投资者门户，而不是默认成为 SaaS 厂商自营市场的交易用户。

### 3.1 客户优先级对产品策略的影响

1. **A 类｜首要目标客户：** 有持续发行需求的资产管理机构与发行企业。优先验证重复发行、资产/金融工具配置、投资者管理、认购与配售状态、持有人记录、发行后报告及收益/利息/到期等存续期流程。Issuer SaaS 的核心工作流应优先围绕经访谈证实的高频问题设计。
2. **B 类｜重点战略客户：** RWA 服务商与区域平台运营商。重点验证 White-label 的多发行机构管理、品牌/域名、门户配置、资产分发授权、组织权限和运营支持需求。B 类的重要性不改变 A 类的首要优先级，并继续受 DEC-001、DEC-002 的客户隔离和明确授权原则约束。
3. **C 类｜独立拓展路线：** 金融科技公司及机构 API 客户。单独验证 API/SDK 集成场景、Sandbox、Webhook、版本治理、开发者体验、支持 SLA 与用量计费，不要求其销售路径与 Issuer SaaS 完全一致。

**仍待验证：** 各类客户在日本与阿联酋的细分行业、采购决策人、项目频率/规模、采购周期、预算与付费意愿、可触达性及获客成本。客户优先级不是首发资产类别、监管辖区、定价或收入目标的替代决策。

## 4. 产品形态与边界

### 4.1 产品 A：Issuer SaaS

企业注册/验证、组织及权限、资产/金融工具定义、发行法律文件、发行轮次与价格、准入/KYC 接入、投资者及白名单、认购支付状态、份额登记/Token、报告、收益/利息/赎回及存续期事件。客户使用统一品牌的标准后台，并可配置资产专属投资入口。

### 4.2 产品 B：White-label（V1 边界已确认）

客户自有品牌/域名、资产发行方及投资者门户、运营配置、角色权限、客户/渠道归属、资产展示范围、区域合规和服务商配置。

**【已确认｜DEC-002】** 一个白标运营商可管理多家发行机构并运营自有品牌门户；门户仅展示运营商自有或获得明确分发授权的资产，并受客户权限、投资者资格及适用法域约束。V1 不支持白标运营商之下的多级代理、经销或转售层级。

独立部署/专属基础设施、外部服务转售及更深层渠道模式不属于本次已确认范围，需另行评估。

### 4.3 产品 C：Open API / SDK

标准化 Asset/Instrument/Offering/Investor/Compliance/Subscription/Payment Status/Register/Distribution/Wallet/Event APIs；API Key/OAuth、Webhook、版本化、SDK、CLI、Sandbox、审计及用量计费。前端与第三方共享相同业务核心，避免形成仅自用的私有业务逻辑，但敏感/管理接口需分级授权。

### 4.4 支撑产品

平台总管理 Admin、开发者门户、商业官网、客户投资者门户、客户计费/合同管理、服务商集成及协作工作流。专业服务商开放撮合商城可作为后续增值服务，不是首批必须条件。

## 5. 关键业务模型

核心层次采用：
- Tenant / SaaS Customer：购买软件及承担合同的一方；
- Organization / Legal Entity：实际发行人、资产 SPV、受监管服务提供者；
- Underlying Asset：底层真实资产及验证文件；
- Instrument / Legal Right：投资人实际受让的金融权利、登记及退出方式；
- Offering：一轮发行/募资/分配条款；
- Token / Register：数字凭证及权威法律持有人记录；
- Investor / Eligibility：个人或机构投资者，按法域、工具、发行人和计划配置准入；
- Subscription / Payment / Allocation：认购意图、真实结算、确认配售三者独立；
- Lifecycle Event：收益、利息、NAV、申赎、报告、违约、回购、到期和清算。

**规则**：同一 Token 的转让不自动代表权利登记的法律最终变更。真实数据及状态的权威来源必须由当地法律/登记机制与合作金融机构规定。

## 6. 全球客户发现与首批市场选择

### 6.1 已确认的市场战略原则（DEC-006）
- **产品定位全球化：** 建设一套标准化、可配置、多资产的 Tokenization SaaS；通用核心能力尽量跨市场复用，法域差异通过明确的配置边界、模块化集成和逐项验证处理。
- **客户发现全球化：** 不把客户发现局限于日本或阿联酋。围绕 DEC-005 的 A/B/C 客户群建立候选市场与潜在客户池，优先寻找有真实发行计划、可接触决策人、可验证采购流程及试点可能性的客户。
- **首批市场证据驱动：** 不先验指定国家排名。基于客户痛点与可触达性、试点意向、支付/采购信号、适用法律路径、合格服务商生态、竞争替代方案、实施和持续运营成本，比较候选市场并记录证据与不确定性。
- **分开判断产品范围与市场准入：** 全球化产品设计不等于所有国家/地区都已开放，也不等于可在所有法域开展全部金融活动。任何具体市场与功能组合均须先完成相应法律定性、许可/注册分析、合作方责任确认和上线条件审查。

### 6.2 候选研究市场（非优先级承诺）

**日本（候选研究市场）**
- 可研究证券型 Token、电子记录转让权利及相关发行、销售、管理规则；
- 评估潜在客户、可接触试点、合资格法律/金融服务商及实际商业需求；
- 如有证据支持，再研究日语/英语、JPY、身份资料格式、隐私及跨境数据处理等产品适配要求；
- 相关许可路径、受监管活动责任和商业可行性均未确定。

**阿联酋（候选研究市场）**
- 将适用监管区域与经营制度分别评估，不把 UAE 或“中东”视为单一牌照市场；例如 DIFC、ADGM 与 Dubai 其他区域须分别定性；
- 研究客户、合作机构、法律服务、KYC/KYB、支付、托管及登记资源的实际可获得性；
- 如客户证据支持，再评估英语/阿拉伯语 RTL、币种、数据驻留和投资者分类需求；
- 具体许可路径、服务边界和商业可行性均未确定。

日本和阿联酋与其他候选市场处于同一证据评估框架中；此处列出不构成优先顺序或排他范围。首批正式开通市场、经营主体和可商用工具均须经独立法律可行性评估与客户/合作方证据支持，不能由软件开关代替牌照。

## 7. 资产类别与分期策略（已确认原则；具体首发类别待评估）

平台架构一开始按多资产设计，但首批真实交付**只选择合规路径、客户需求和服务商能力均可验证的 1–2 类**，避免把“架构支持多资产”误解为 V1 同时实现所有资产业务。

### 首期候选评估顺序（战略建议，非最终选择）

1. **企业股权 / 私募证券**：评估标准化发行、持有人登记、投资者准入与企业融资生命周期的复用价值。
2. **债权 / 私募信贷**：评估利息、还本、到期、逾期、违约及债权转让等生命周期能力。
3. **房地产相关权益、基金份额、收益权等**：先保留为后续候选，须分别分析实际法律权利和运营模型，不将其视为同一资产模板。

### 首发选择的评估标准

每个候选类别均需在第 02 份文档冻结前做评分和证据说明：

- **客户需求与可获得性**：目标客户是否有明确发行需求、可接触的试点客户和可验证的支付意愿。
- **候选市场法律可行性**：对有证据支持的候选市场逐一判断实际法律工具、发行、分销、托管/登记、投资者资格及运营职责；日本和阿联酋只是候选研究市场之一，不能用“技术平台”标签替代法律意见。
- **合作方可用性**：是否可接入合格的法律、KYC/KYB、支付/托管、登记及审计服务方。
- **业务生命周期复杂度**：认购、配售、登记、利息/收益、赎回/到期、违约、转让及纠错是否可被清晰建模。
- **产品复用度**：该类别沉淀的能力能否被其他客户与资产复用，而非大量一次性定制。
- **实现与运营成本**：合约、账务、对账、审计、客服和持续运营成本是否可控。
- **商业可售性**：是否能形成清晰的 SaaS 套餐、实施服务和续费价值。

### 当前已确认与未确认

- **已确认：** 平台从架构上按多资产扩展；首批真实交付只聚焦 1–2 类。
- **已确认：** 企业股权/私募证券、债权/私募信贷作为优先评估候选；房地产相关权益、基金份额、收益权等暂列后续候选。
- **未确认：** 首批究竟选择哪 1–2 类；不能仅凭本节候选顺序视为最终决定。
- **未确认：** 日本和阿联酋各自首批可以实际商用的法律工具及许可路径；须由当地法律顾问和合作方验证。
## 8. 商业模式与计费

### 三种收入主线
1. **SaaS 订阅**：按基础版、成长版、机构版划分功能、资产数、机构席位、额度与 SLA；
2. **White-label 许可**：品牌/域名、运营商管理、部署等级、多组织管理、扩展组件与支持级别；
3. **API 订阅/按量**：API 调用、发行活动、资产或服务额度、专属环境、技术支持。

### 增值收入
实施费、集成费、企业定制服务、额外支持、外部供应商通道费等。任何涉及金融介绍、分销或佣金的服务收费必须经法律审查。

### 成本模型
KYC/KYB、AML、节点/基础设施、链上 Gas、支付/托管/登记、合约审计、SRE、安全、客服/机构实施、商务与法务。第三方代收费用、平台技术费和投资资产资金不得混记。

### 必需的商业后台
套餐/功能授权、合同、试用/开通、计量、账单/发票、收款、暂停与续费、客户成功与审计。具体价格点和成本比例**待市场研究与经营地明确后决策**。

## 9. 多租户、客户层级与开放分发原则（DEC-001、DEC-002 已确认）

- 每个付费客户拥有独立管理权限、品牌设置及保密数据域，发行人仅能管理其有权限的资产；
- 投资者的资格与查看范围按发行项目、客户授权、监管区域配置；不是任一入口自动显示全球所有资产；
- **【已确认｜DEC-001】客户独立资产门户与授权分发**：Issuer SaaS/White-label 客户独立管理自身资产及投资者门户；门户不默认接入全平台统一资产池。跨发行方分发必须有明确授权，并符合渠道、投资者资格和法域要求。
- **【已确认｜DEC-002】客户层级与交付模式**：标准 SaaS 服务单一发行机构；White-label V1 支持一个运营商管理多家发行机构，但不支持多级代理/转售；Open API/SDK 是独立商业交付产品线。
- 【待细化】私有门户/邀请制/获授权合作渠道的页面交互、授权生命周期、资产可见性及投资者身份关联，留待第 03/05 份文档落地；
- 身份核验的事实可评估重用，但 KYC 结果不等同对任何项目的投资资格，不能在无合法依据时跨客户共享原始身份数据；
- 合同到期、白标撤销或 SaaS 客户退出时，必须有数据导出、法定持有人/资金责任迁移和未完成义务处理机制。

除已明确标注为 DEC-001、DEC-002、DEC-003、DEC-004 的原则外，其余为**我方建议设计或待验证事项**；不等于 Brickken 当前实际实现已经全部证实。

## 10. 原则上暂不做的能力

- SaaS 厂商自营一级全球资产聚合市场；
- 统一公开 AMM、公开 C2C 专业二级交易所、K 线交易终端；
- 平台自行担任证券承销商、托管银行或无许可的证券交易场所；
- 使用型 Token 的实际消费履约/仲裁平台；
- 默认跨链实时资金结算、无条件全球通用 KYC 或永不允许纠错的收益发放机制。

受限二级 P2P/ROFR、机构分发连接可独立研究，但不得在未明确法律责任前设计为可直接正式上线的金融市场。

## 11. 首批产品设计顺序

1. 设计租户/客户/机构/发行人/投资者/法域的基础模型，以及产品和数据访问边界；
2. Issuer SaaS 的 Onboarding、资产、Instrument、Offering、投资者、认购与生命周期；
3. Investor Portal 的注册/合规/资产展示/签署/认购/持仓/收益；
4. Platform Admin 的企业、资产、规则、权限、计费、审计；
5. White-label 的品牌、域名、运营商权限与门户；
6. API/开发者门户的自助接入、Sandbox 和用量；
7. P2P/高级资产模板和专业服务商生态。

这是设计文档顺序，不代表真实业务后端必须串行开发。后端、法律和服务商依赖需同步验证。

## 12. 成功指标与验收门槛

商业指标：已签约企业数、成功上线租户数、每个租户从签约到发行的时间、付费转化、续费、MRR/ARR、毛利、客户支持工单量。

产品指标：完成发行配置时间、合规审核成功率、认购到最终结算成功率、账本与登记对账准确度、收益差错率、API 自助集成成功率、白标开通时间、跨租户权限测试覆盖率。

安全与合规门槛：业务定性、合作机构责任、数据保护、智能合约审计、支付与法定登记一致性、异常补偿、隐私及灾备。**前端功能完成不等于允许真实金融业务上线**。

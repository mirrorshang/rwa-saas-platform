RWA 平台 V2 产品需求文档（三）
合约功能规范（Token 层 / 业务层 / 治理层 / 二级市场层）
文档状态：草稿 v1.0
PRD 系列共 4 份：① 身份认证与一级市场 ② 二级市场 ③ 合约功能（本文档） ④ Open API / SaaS / 白标 PRD
文档性质说明：本文档不同于常规面向终端用户的功能 PRD，目标读者是合约研发团队与架构评审方，用于把 PRD-01、PRD-02 中"由合约保证、后端不可绕过"的业务规则收敛为一份统一的合约功能规范，同时对 PRD-01/02 中标注"需在合约功能PRD中重新确认"的开放问题给出正式的功能性需求与推荐方案。
编写原则：本文档只描述合约需要具备的业务能力、约束条件与不可篡改的规则，不涉及具体的 Solidity 实现、存储布局或代码结构，工程可行性与具体实现方式由合约团队评审确认。
标注说明：【已确认】PRD-01/02 或原升级方案中已明确、直接作为合约必须满足的约束；【待确认】需要合约工程可行性评审或业务进一步拍板的问题；【产品建议】非正式需求，仅供参考

---
1. 需求背景
1.1 为什么做
PRD-01、PRD-02 中反复出现"该规则必须由合约强制执行、后端不可绕过"的表述（如 Capacity 超发约束、合规实时校验、资金分账、Merkle 收益分配、二级市场手续费与版税等），且多处明确标注"需要在《合约功能PRD》中与技术团队重新确认"。这些要求分散在两份面向前端体验的 PRD 中，缺少一份统一、聚焦合约能力边界的规范，容易在实现阶段出现遗漏或前后矛盾。
1.2 当前存在的问题
- V1 权限过度集中（单一主权限合约管控全部业务合约），单点失效风险高。
- V1 购买等业务逻辑写入 Token 合约，导致业务迭代必须触碰资产凭证合约，升级风险高、审计成本高。
- V1 合规校验依赖后端拦截，前端直连合约后这一防线自动失效。
- V1 没有 Capacity 概念，超发缺乏硬约束。
- PRD-01/02 中新提出的多项能力（N 方自定义资金分账、单选认购/收益币种、Usage Token 标准化销毁、AMM+C2C 双市场、版税分账、订单过期与撤单）在原技术方案中缺少或需要调整对应的合约设计。
1.3 解决什么问题
明确合约在资产凭证（Token）、一级发行业务、治理与权限、二级市场撮合结算四个层面必须具备的功能与约束，作为 PRD-01/02 业务规则的可信执行层，并为 PRD-01/02 中遗留的合约相关待确认问题给出正式的功能性需求与推荐方案，供合约团队评审工程可行性。

2. 产品目标
2.1 业务目标
- 建立"链下产品规则、链上强制约束"的双层防线，使前端直连合约后依然满足合规、防超发、资金安全三项底线。
- 通过合约三层收敛（Token / 业务 / 治理）与权限分域，降低升级风险、满足机构与审计准入门槛。
- 使资金分账、收益分配、二级市场结算三类涉及资金安全的能力具备"任何人可在链上自行核验"的可信度，不依赖对平台的信任。
2.2 用户目标（间接，通过 PRD-01/02 承载体验）
- 投资者：认购、Claim、二级交易的关键规则（限购、Capacity、分账比例、手续费、版税）都可在链上验证，不依赖平台单方陈述。
- 发行方：自己配置的资金分配方案、版税比例创建后不可被平台后台静默修改。
- 平台运营：拥有分级权限（而非单一超级管理员），关键参数变更有 Timelock 缓冲期。

4. 需求范围
4.1 本期做什么
1. Token 层功能规范：ERC-20/721/1155 三类模板的合规钩子、干净原则、版税信息承载。
2. 一级资产业务合约功能规范：OfferingConfig 参数与不可变性、Capacity 硬约束、认购执行与资金分账、认购/收益币种白名单。
3. 收益分配（Merkle Distributor）功能规范。
4. Usage Token 标准化销毁能力规范。
5. 二级市场合约功能规范：AMM、C2C（Seaport 风格）订单结算、版税执行、订单过期与撤单（nonce）机制。
6. 治理与权限功能规范：权限分域、多签国库、Timelock、熔断开关的链上落地。
7. 跨资产通用能力：Currency Registry、Exit Rule 触发接口（框架级）。
8. 对 PRD-01/02 中标注"需合约功能PRD确认"的问题给出正式功能性需求与推荐方案。
4.2 本期不做
- 具体合约代码结构、存储布局、Gas 优化方案（工程实现细节，由合约团队自行设计）。
- 跨链 Supply Control 的具体实现（本期默认单链，见 PRD-01/02 范围声明）。
- 拍卖类订单（荷兰拍/英式拍）、期权期货等衍生品合约能力。
- 具体的安全审计与漏洞赏金执行计划（属于实施阶段工作，非功能需求）。

5. 产品流程
5.1 认购执行时序（合约视角）
```Plaintext
前端构造待签交易（calldata，含 Offering 地址、认购数量、认购币种）
  → 用户钱包签名并广播
  → 合约按序执行（同一笔交易内，任一步失败则整体回滚）：
       1. 合规校验（KYC/Eligibility/持仓上限/锁仓/发售状态/时间窗口，来自 Compliance 层）
       2. Capacity 校验（本次认购后 Tokenized 是否超过 maxSupply）
       3. 扣款（按 Offering 配置的认购币种）
       4. 资金按分配方案拆分转出至各接收地址（含平台手续费固定项）
       5. 铸造/转移对应数量 Token 至投资者地址
  → 交易确认后，Indexer 解析事件更新平台展示数据```
5.2 收益分配与 Claim 时序
```Plaintext
平台侧（Admin 后台）确认 Distributable 净额与 Record Date
  → 生成持仓快照（链下计算）→ 生成 Merkle Root
  → 治理层权限（Issuer Agent 或专用 Distribution Agent）将 Merkle Root 与对应资金提交上链
  → 合约记录该期 Root 与资金托管，无平台侧回收接口
  → 用户提交 Merkle Proof → 合约校验 Proof 有效性与未重复领取 → 转出用户应得金额```
5.3 二级市场吃单结算时序（C2C）
```Plaintext
Maker 已通过 EIP-712 离线签名生成 Listing/Offer（含价格、数量、过期时间戳、nonce）
Taker 选择一个或多个订单 → 前端/撮合服务对订单做链下有效性预检查
  → 组装批量结算 calldata → Taker 钱包签名并广播（或经由撮合服务代为广播，签名仍为原始 Maker/Taker，见14.5）
  → 合约按序对每笔订单执行：
       1. 校验订单未过期（当前时间 ≤ 订单中的过期时间戳）
       2. 校验订单未被撤销（nonce 校验）
       3. 校验 Maker 资产余额/授权充足
       4. 若任一笔校验失败 → 该笔订单从本次批量结算中剔除，其余订单继续结算（不整体回滚）
       5. 有效订单执行资金结算：成交金额 → 扣平台手续费 → 扣版税（如已配置）→ 剩余转给卖方
       6. 执行资产转移
  → 交易确认后返回本次实际成交清单（含被剔除订单列表）```
5.4 使用型 Token 销毁时序
```Plaintext
第三方生态在自身应用内完成一次消费
  → 触发销毁操作（发起方与授权模型见14.4待确认）
  → 合约校验销毁数量不超过持仓、调用方具备销毁权限
  → 执行销毁（Burn）→ 触发事件供 Indexer 解析
  → 平台侧同步扣减该 Right 的 Capacity Consumed 账（链下账本，通过事件驱动更新）```

6. 功能需求
模块一：身份与合规层（Identity & Compliance）
功能 1.1 链上身份承载
- 功能描述：承载 ONCHAINID 身份与 KYC Claim，支持一个身份绑定多个钱包地址。
- 业务规则：
  - 【已确认】身份为全局对象，不按业务合约或租户区分实例。
  - 【已确认】平台不提供任何"客户/第三方自行上报 KYC 结论"的写入口，Claim 签发方仅限平台对接的 KYC 供应商与平台自身审核结果。
  - 新增/解绑钱包（对应 PRD-01 功能1.4）需要在身份合约层面同步维护绑定关系，供 Compliance 校验时识别"同一身份多地址"的合并持仓/限额口径。
- 成功结果：任意业务合约在执行 Transfer/认购前均可查询到统一的身份与 KYC 状态。
- 异常情况：地址已绑定其他身份时拒绝重复绑定（呼应 PRD-01 功能1.4 业务规则）。
功能 1.2 合规实时校验（Compliance / Eligibility）
- 功能描述：对每一笔涉及 Token 持仓变化的操作（认购发币、二级成交转移、赎回、销毁）执行实时合规校验，校验不通过则该笔操作失败。
- 业务规则：
  - 【已确认】校验项至少包括：KYC 状态、辖区限制、投资者类型、单户持仓上限、锁仓期、发售状态与时间窗口、地址是否被冻结/加入黑名单。
  - 【已确认】合规规则的维护（新增白名单、调整上限、冻结地址）由 Compliance Agent 权限执行，不需要业务合约升级即可生效（规则参数化）。
  - 合规规则变更本身是否需要 Timelock 延迟见 14.3。
- 成功结果：任何不满足合规条件的资产变动都会在链上被拒绝，无法通过绕过前端来规避。
- 异常情况：规则误配导致合法用户被拒绝——需要 Compliance Agent 权限可及时修正，同时配合 Timelock 权衡"及时止损"与"防误操作"。

模块二：Token 层（资产凭证）
功能 2.1 三类 Token 模板
- 功能描述：提供 ERC-20（收益份额型）、ERC-721（单一权属型）、ERC-1155（批次型，收益或使用型）三类资产凭证模板，由 Token Factory 按 Offering 配置选择部署。
- 业务规则：
  - 【已确认】Token 合约保持"干净"：只负责余额记账与合规钩子（每次 transfer/mint/burn 前调用 Compliance 校验），不包含认购、交易、分账等业务逻辑。
  - 业务逻辑（认购、二级交易、收益分配）由独立的业务层/市场层合约调用 Token 合约完成，Token 合约本身不主动发起这些动作。
  - 【产品建议】Token 元数据中应包含指向 Offering/Right 的关联标识，便于链上直接追溯"这个 Token 对应哪个资产、哪期发行、什么权益类型"。
- 成功结果：升级业务逻辑（如调整认购流程）无需重新部署或迁移 Token 合约。
- 异常情况：Compliance 钩子调用失败时，对应的 mint/burn/transfer 操作必须整体失败，不可出现"钩子报错但转账仍完成"的情况。
功能 2.2 Usage Token 标准化销毁能力
- 功能描述：为 ERC-1155/721 类使用型 Token 提供标准化的销毁（Burn）函数，供第三方生态在获得授权后调用。
- 业务规则：
  - 【待确认，见14.4】销毁权限模型：
    - 方案A：仅持有人自己签名发起销毁（平台/生态方均不能代为操作，与"平台不代签"原则完全一致，但要求终端用户在第三方生态消费时也需要额外唤起钱包签名，可能影响生态方的产品体验）。
    - 方案B：持有人在获得平台准入的生态方处，一次性签名授权（Approve 类似机制）给该生态方合约地址销毁权限，之后生态方可在授权额度内代为发起销毁，无需持有人逐笔签名。
  - 销毁数量不可超过当前持仓，销毁后触发事件供 Capacity Consumed 账同步。
- 成功结果：第三方生态可以稳定调用销毁能力完成核销，销毁记录可在链上核验。
- 异常情况：超授权额度或超持仓的销毁请求被拒绝。
功能 2.3 版税信息承载
- 功能描述：ERC-721/1155 合约层记录版税比例与接收地址，供二级市场结算合约在成交时读取并执行分账。
- 业务规则：
  - 【已确认】版税信息由发行方配置（见 PRD-02 功能2.5），本期不要求写死在 Token 部署时不可变，允许发行方后续调整（具体是否允许修改、修改生效范围见 PRD-02 14.6，本文档承接该待确认，需合约支持"读取最新版税配置"的能力以便支持未来可能的调整）。
  - 版税信息仅供 C2C 市场结算合约读取执行；AMM 合约不读取、不执行版税逻辑。
- 成功结果：任何在平台市场合约内完成的 721/1155 成交均能正确执行版税分账。
- 异常情况：版税比例为异常值（如负数或超过 100%）时应在配置阶段被拒绝，不应等到成交时才失败。

模块三：一级资产业务合约（发行 · 认购 · 分账）
功能 3.1 OfferingConfig 参数与不可变性
- 功能描述：将 Offering 的发售规则以链上参数形式固化，作为认购执行的唯一依据。
- 业务规则：
  - 【已确认】OfferingConfig 至少包含：起止时间、单笔最小/最大限购、总量上限（对应 Capacity 预占）、认购币种（单一）、资金分配方案（接收方列表+比例，含平台手续费固定项）、发行状态。
  - 【已确认，承接 PRD-01】Offering 发布后，仅"结束时间"与"发行状态"两项参数允许变更，其余参数（含资金分配方案、认购币种、限购规则）创建生效后不可修改，需要合约层面通过权限控制或字段级不可变设计强制保证，而非仅依赖后台流程约束。
  - 【待确认】结束时间的可延长范围是否需要设置上限（避免无限期延长导致 Capacity 长期被占用）。
- 成功结果：任何后台操作都无法绕过合约直接改变已发布 Offering 的核心规则，投资者可自行核验。
- 异常情况：尝试修改不可变参数的调用应被合约直接拒绝（而非依赖后台不提供入口这种弱约束）。
功能 3.2 资金分配方案的链上执行（N 方动态分账）
- 功能描述：支持发行方在 OfferingConfig 中配置任意数量的分账接收方与比例，并在认购发生时于同一笔交易内完成拆分转账。
- 业务规则：
  - 【已确认，本次收敛】这是相对原技术方案"固定两方（发行方66.7% / 国库33.3%）分账"的实质性变更——本文档正式将其确立为功能需求：合约需支持可变数量的分账接收方列表（而非硬编码两个地址），且列表中固定包含一项由治理层（而非发行方）写入的"平台手续费"，比例创建时锁定快照（呼应 PRD-01 功能2.5 产品建议）。
  - 分配方案中所有接收方比例（含平台手续费）之和必须等于 100%，该校验应在 Offering 创建/审核环节的链上提交时执行，而非留到认购时才发现配置错误。
  - 【待确认，见14.1】分账接收方数量是否需要设置上限（避免单笔认购交易因分账接收方过多导致 Gas 成本过高甚至超出区块 Gas Limit）；建议合约团队评估一个合理上限（如≤10个接收方）并反馈给产品用于前端表单限制。
- 成功结果：认购资金在链上按方案自动拆分，任何人可核验实际到账地址与比例。
- 异常情况：比例之和不等于100%时创建阶段即拒绝；分账接收方数量超过合约设定上限时创建阶段拒绝并提示。
功能 3.3 Capacity 硬约束
- 功能描述：链上维护 maxSupply，作为 Capacity 账本之外的最后一道硬约束。
- 业务规则：
  - 【已确认】maxSupply 只可下调、不可上调（关闭发行只能收紧，不能放宽）。
  - 认购执行时校验"当前已发行量 + 本次认购量 ≤ maxSupply"，超出则整笔交易回滚。
  - 使用型资产的销毁（Consume）不增加可认购的剩余额度（销毁与发行是两个独立方向，不循环利用 maxSupply）。
- 成功结果：即使平台后台数据被误改，链上供应量也不可能超过 maxSupply。
- 异常情况：并发认购导致临界竞态——由合约的原子性保证不会出现超发，只会出现"后到达的交易失败"。
功能 3.4 认购/收益币种白名单
- 功能描述：合约校验认购支付币种与收益发放币种是否为该 Offering/该次分配所配置的唯一币种。
- 业务规则：【已确认，承接 PRD-01】认购币种、收益发放币种均为单选，合约层应直接以"该币种地址"作为唯一合法输入，而非维护一个可多选的白名单集合（相比原技术方案的多币种白名单设计有所简化）。
- 成功结果：非配置币种的认购请求直接被拒绝。
- 异常情况：币种未在 Currency Registry 中启用时，Offering 创建阶段即应被拒绝。

---
模块四：收益分配合约（Merkle Distributor）
功能 4.1 Merkle Root 提交与资金托管
- 功能描述：接收链下计算好的 Merkle Root 与对应分配资金，托管至用户可自助领取。
- 业务规则：
  - 【已确认】资金一次性注入分发合约，合约不提供任何平台侧回收接口，保证"收益不设过期"的承诺在合约层面可信。
  - 每期、每种发放币种对应独立的 Merkle Root。
  - 提交 Root 的权限归属【待确认，见14.5】——是否需要独立的 Distribution Agent 角色，还是复用 Issuer Agent。
- 成功结果：Root 与资金一经上链即不可被平台单方撤回。
- 异常情况：资金注入金额与 Merkle Root 计算的总应发金额不一致时，创建阶段应校验拦截（防止资金不足导致部分用户无法 Claim）。
功能 4.2 用户 Claim 与防重复领取
- 功能描述：用户提交 Merkle Proof 证明自己在快照中的应得份额，合约校验后转出对应金额。
- 业务规则：
  - 每个 Proof 对应的领取名额只能被核销一次（防止重复领取）。
  - 支持批量 Claim（一笔交易同时核销跨期、跨 Offering 的多个 Proof），降低用户 Gas 成本。
- 成功结果：用户按实际应得金额领取，不多不少，且不可重复。
- 异常情况：伪造或错误的 Proof 应被拒绝且不消耗目标资金。

模块五：二级市场合约
功能 5.1 AMM 合约（仅 ERC-20）
- 功能描述：承载发行方注入的流动性池，提供实时报价与兑换执行。
- 业务规则：
  - 【已确认】流动性仅由发行方注入，本期不开放公众 LP。
  - 兑换执行时校验合规（买卖双方 KYC/Eligibility）、滑点保护（用户设定的最小可接受数量）。
  - 手续费在兑换时从成交额中扣除并转入国库（比例由治理层配置，见模块六）。
  - 【待确认】流动性撤出规则（见 PRD-02 14.5），若允许发行方撤出，合约需支持相应的撤出函数与限制条件（如锁定期、最低保留比例）。
- 成功结果：满足条件的兑换在一笔交易内完成扣款、分账、发币。
- 异常情况：滑点超出容忍度、流动性不足以完成兑换时整笔交易回滚。
功能 5.2 C2C 订单结算合约（Seaport 协议风格）
- 功能描述：校验链下签名订单（Listing/Offer）并执行批量结算，支持多资产标准（ERC-20/721/1155）与多收款方分账。
- 业务规则：
  - 【已确认】订单结构中必须包含过期时间戳，合约在结算时必须校验当前区块时间未超过该时间戳，超过则该笔订单结算失败（呼应 PRD-02"挂单必须设置过期时间"）。
  - 【已确认】订单撤销通过 nonce 机制实现：合约维护每个用户的 nonce，签名订单中包含用户当时的 nonce 值，用户撤单时可递增自己的 nonce 使包含旧 nonce 的所有未使用签名失效。具体是"全局递增（一次撤单使该用户全部旧订单失效）"还是"按订单粒度独立标记撤销"，是本文档需要合约团队评审给出推荐方案的问题（见14.2）——从产品角度更希望是"按订单粒度撤销"，避免用户撤销一笔订单时意外让其他有效挂单失效，若工程上"按订单粒度"成本过高，需要向产品说明并共同评估折中方案（如"分组 nonce"）。
  - 支持同一笔批量结算交易中包含多笔订单，部分订单校验失败时不影响其余有效订单的结算（局部失败、非整体回滚，呼应 PRD-02 功能2.4）。
  - 结算时的资金分配顺序：成交金额 → 平台手续费（转入国库）→ 版税（如 Token 已配置，转入版税接收方）→ 剩余转给卖方（或 Offer 场景下的原持有人）。
  - 支持 Listing（卖方发起）与 Offer（买方发起）两种方向的订单结构。
  - ERC-1155 订单支持部分数量成交（剩余数量的订单在链下订单簿中更新，链上只需确认本次实际成交数量不超过订单声明的剩余可成交数量，通过 nonce 或已成交数量映射防止超额重复成交）。
- 成功结果：批量结算一次性完成资产与资金的原子交换，任何一笔子订单的失败不影响其他子订单。
- 异常情况：订单已过期、Maker余额不足、Taker资格不满足——对应订单从本次结算中剔除。
功能 5.3 熔断开关的链上落地
- 功能描述：将 PRD-01/02 中定义的资产/Offering 级别熔断开关（新认购/交易/收益分配/使用/赎回）落地为合约层的状态位，业务合约在执行对应操作前检查开关状态。
- 业务规则：
  - 五个开关独立存储、独立校验，互不影响。
  - 【已确认】Pauser 权限可触发暂停类开关，但不能执行资金转移类操作（权限最小化原则）。
- 成功结果：Admin 后台的熔断操作能实时、可靠地反映为合约执行结果的变化。
- 异常情况：暂停生效与用户已广播未确认的交易存在竞态——按照"合约状态在交易执行时刻的最新值"为准，可能导致用户交易在暂停生效后被拒绝，属预期行为需前端提示。

模块六：治理与权限
功能 6.1 权限分域
- 功能描述：按业务域拆分权限主体（Issuer Agent / Compliance Agent / Treasury Signer / Pauser 等），替代 V1 单一主权限合约管控全部业务合约的模式。
- 业务规则：每个权限主体的可执行操作范围应严格限定在其业务域内，不可越权调用其他域的功能（如 Pauser 不能修改合规规则，Compliance Agent 不能转移资金）。
- 成功结果：单个权限私钥泄露的影响范围被限制在其对应业务域，不会导致全平台失陷。
功能 6.2 国库多签
- 功能描述：国库资金出口采用多签钱包（如 Gnosis Safe），替代 V1 单签出口。
- 业务规则：达到预设签署阈值（如 M-of-N）才能执行国库资金的转出类操作。
- 成功结果：单个签署人私钥泄露不足以转移国库资金。
功能 6.3 关键参数 Timelock
- 功能描述：对影响资金安全或合规规则的关键参数变更引入时间锁延迟。
- 业务规则：
  - 【待确认，见14.3】哪些参数变更需要纳入 Timelock（候选：平台手续费比例、Compliance 规则、Currency Registry 启用状态、版税比例上限），需要与合约团队共同划定清单，在"及时止损能力"与"防误操作/防作恶"之间做取舍。
- 成功结果：关键参数变更前有可观察的缓冲期，供审计与用户预警。

模块七：跨资产通用能力
功能 7.1 Currency Registry
- 功能描述：统一注册与管理平台支持的币种（含链、合约地址、精度、是否启用）。
- 业务规则：Offering 创建时的认购币种、收益分配时的发放币种均必须从已启用的 Currency Registry 中选取。
- 异常情况：币种被临时禁用后，已发布但未开始的 Offering 如何处理【待确认】。
功能 7.2 Exit Rule 触发接口（框架级）
- 功能描述：为 PRD-01 中定义的 Exit Rule（二级转让/现金赎回/资产清算/权益到期/使用型销毁）预留合约层触发入口。
- 业务规则：本期仅要求合约具备"识别到期时间并允许被外部调用触发对应流程"的框架能力，具体每类 Exit Rule 的资金来源与执行细节延续 PRD-01 14.7 的待确认状态，本文档不重复展开，待后续专项设计明确后再补充对应的合约功能需求。

8. 业务规则
8.1 金额与数量
- 分账接收方比例合计=100%；分账接收方数量存在合约层上限【待确认】。
- Capacity：已发行量 ≤ maxSupply，且 maxSupply 只可下调。
- 手续费与版税均以成交总额为独立计算基数，不叠加计算。
8.2 时间
- OfferingConfig 的起止时间为强约束，认购必须在时间窗口内。
- C2C 订单必须包含过期时间戳，超过即结算失败。
- 关键参数变更的 Timelock 延迟期【待确认具体时长】。
8.3 权限
- 权限分域：Issuer Agent / Compliance Agent / Treasury Signer / Pauser 各自权限边界不可越权。
- 平台不代签：所有资金/资产变动类操作的最终签名者必须是资产所有者本人（或其明确授权的合约地址，如 Usage Token 销毁的授权模型）。
8.4 状态
- Offering 状态、熔断开关状态、订单状态均以链上状态为唯一真相源（对应 PRD-01 E2 已确认决策）。
8.5 限制条件
- Token 合约不得包含业务逻辑；业务逻辑合约不得直接持有用户私钥相关操作。
- AMM 不执行版税逻辑；版税仅在 C2C 结算合约中生效。
8.6 计算规则
- 认购分账：应付金额 × 各接收方比例（含平台手续费）。
- 二级成交分账：成交金额 × 手续费比例、成交金额 × 版税比例，卖方到账为剩余部分。

13. 验收标准
正常场景
- 认购、Claim、AMM兑换、C2C成交均能在满足条件时于一笔交易内正确完成全部子操作（合规校验、资金分账、资产转移）。
- 分账接收方数量为2个以上（非固定两方）时，认购交易仍能正确按比例拆分到全部接收方。
- OfferingConfig 除结束时间/发行状态外的参数在合约层面确实不可被修改（非仅后台不提供入口，需合约本身拒绝相关调用）。
- C2C 批量结算中部分订单过期/失效时，其余有效订单仍能正确结算。
异常场景
- 任一环节合规校验失败时，整笔认购/转移交易应完整回滚，不产生部分状态（如扣款但未发币）。
- 尝试超过 maxSupply 的认购请求必须被拒绝，即使并发场景下也不产生超发。
- 权限主体尝试越权操作时应被拒绝并有明确的错误反馈。
边界场景
- 分账接收方比例精度处理（如无法整除的比例）应有明确的取整规则且不产生"多退少补"的资金差额悬空。
- Merkle Root 对应资金与理论应发总额恰好相等时，最后一位用户仍能完整领取。
- C2C 订单在最后一个区块内同时被过期判定与被吃单尝试时的优先级判定一致、可预期。

14. 风险与待确认事项
14.1 产品风险（分账接收方数量上限）
- N 方动态分账相比固定两方分账会显著增加单笔认购交易的 Gas 成本与复杂度，需要合约团队评估一个合理的接收方数量上限并反馈，产品据此在前端表单中做限制，避免发行方配置过多分账项导致交易失败或 Gas 成本过高。
14.2 业务风险（nonce 撤单粒度）
- "全局 nonce 撤单"实现简单但会误伤用户其他有效挂单，"按订单粒度撤单"体验更好但可能增加实现与 Gas 成本，需要合约团队给出推荐方案，产品倾向于按订单粒度撤单。
14.3 技术依赖（Timelock 参数清单与延迟时长）
- 哪些参数变更需要纳入 Timelock、延迟时长设置多久，需要合约团队结合审计与运营应急响应能力共同评审，本文档暂不给出具体数值。
14.4 待确认问题（Usage Token 销毁权限模型）
- 沿用 PRD-01 14.9 的待确认项，本文档给出两个候选方案（用户自签 vs 授权代销毁），需要产品与合约团队共同选定，这将直接决定 Usage Token 合约的接口设计方向。
14.5 待确认问题（撮合结算的广播主体）
- C2C 批量结算交易的最终广播者是 Taker 自己的钱包，还是允许平台侧撮合服务代为广播（签名内容不变，仅 gas payer/sender 不同）？这不违反"平台不代签"原则（签名仍是用户自己的），但涉及"谁支付 Gas""失败由谁重试"等产品体验问题，需要明确。
- Merkle Root 提交权限归属哪个角色（独立 Distribution Agent 还是复用 Issuer Agent）。
14.6 待确认问题（版税可规避性，承接 PRD-02 14.2）
- 若 Compliance/Transfer Rule 不强制"仅允许通过平台市场合约完成的转账"，用户可绕过市场合约直接点对点转账从而规避手续费与版税。是否需要在 Transfer Rule 中增加"仅白名单市场合约可发起转账"的限制？此举会牺牲资产的自由转让性（与"用户完全自持、自由控制资产"的平台底线存在一定张力），需要业务、法务与合约团队共同权衡取舍，并如实向发行方披露版税的实际可执行边界。

### 2.2 MVP 企业账号与权限

- MVP 每家企业先采用一个操作账号。
- MVP 不建设企业内部多成员、角色分权、审核人员、内部审批流或职责分离配置。
- 因为 MVP 只有一个企业操作账号，不设置企业内部的提交人与审核人双角色流程。
- 企业成员、角色、细粒度权限、审批人员配置及职责分离放入 V2.0。
- 上述简化不代表删除平台后台自身的商业运营、安全管理或法定生产准入责任，也不代表平台可以代替发行方作实质法律判断。

### 2.3 资产类型模板

- 不同资产类型必须采用独立模板，不能用一套通用字段表强行覆盖房产、债权、股票/股权、实物资产、衍生品等不同资产特征。
- MVP 当前优先建设房地产资产管理及其权益结构。
- 债权、股权/股票、实物资产等独立模板暂缓至后续版本；底层产品模型保留多资产扩展能力。
- 衍生品等其他类别仅作为长期扩展候选，本文件不承诺其必然进入 V2.0，也不将其列为 MVP 可用模板。
- 资产类别是底层标的与资料模板的分类，不等同于 Instrument 的法律权利家族。具体投资者取得的法律/经济权利必须由权益结构及其有效法律文件表达。

### 2.4 项目管理与发行准备

- Project 保留为系统内部的业务项目对象和企业侧项目管理视图。
- 企业不需要为了进入发行流程而重复手动创建一个 Project；系统根据业务流程自动创建或关联项目。
- 项目管理负责汇总关联资产、权益结构、发行安排、当前进度及后续业务状态，不重复承担发行参数配置。
- 发行准备保留为发行前最终准备、检查和确认入口。该页面汇总资产、权益结构、发行参数、投资者展示页、法律文件、认购规则及适用的生产条件；企业确认后，才进入相应的模拟发布或正式发行流程。
- 发行准备的完整检查项、阻断条件、确认文案及发布状态仍需按后续 UI-Ready 设计逐项展开，不得仅凭页面名称推断全部检查规则已经冻结。

### 2.5 文件及法律资料

- 法律文件、权属证明、估值/运营资料等应在其所属业务对象和业务流程中上传、查看、更新及引用。
- MVP 不把独立「文件中心」设置为资产与发行流程的必经一级或二级入口。
- 文件仍需具备真实文件上传、版本留存、业务对象关联及相应可见性控制；不得把仅填写文件名称或粘贴 URL 当成已完成真实文件上传。
- 平台产品页面负责提示必要资料是否填写、上传及关联完整；不因页面存在文件字段就宣称平台已实质核验文件真实性、法律效力或资产权属。发行企业对其提交资料及声明承担相应责任，平台自身依法应承担的责任与生产准入门仍单独处理。

## 3. 业务对象定义与关系

### 3.1 核心对象

| 对象 | 产品定义 | 企业侧使用方式 |
|---|---|---|
| Asset（资产） | 被登记、描述和关联证据的底层现实资产或标的。资产模板由资产类别决定。 | 企业创建、维护资产档案，并在资产详情中补充权属、法律及运营资料。 |
| Instrument（权益结构） | 基于资产及有效法律安排定义投资者能够取得的法律/经济权利、权利范围、限制、期限及相关容量。中文名称统一为「权益结构」。 | 企业在资产基础上创建和维护一个或多个权益结构；权益结构可按明确的权利范围拆分，并在发行配置时被独立引用。 |
| Project（项目） | 组织一项发行相关业务资料、对象关联、发行安排和进度的管理容器。 | 由系统自动创建或关联；企业主要查看和管理项目，不重复手动创建空项目。 |
| Offering（发行方案/具体发行轮次） | 一次具体发行或一轮发行安排，承载发行数量、Token 数量及映射、价格、币种、认购窗口、限额、参与条件和披露等配置。 | 企业通过「发行方案」配置具体一轮发行；每个发行方案应关联明确的项目、资产及适用权益结构。 |
| Token（链上凭证） | 按适用法律安排及已批准映射规则承载或表征权益的链上凭证。 | 在发行方案中明确 Token 数量、计量单位及与权益结构的映射关系；链上成功不自动等同于法定权利生效、资金到账或登记完成。 |
| Document / Evidence（文件与证据） | 证明资产、主体、权利、估值、运营及披露事项的文件或记录。 | 在对应资产、权益结构、项目、发行方案或发行准备页面中上传、版本化和引用。 |

### 3.2 对象关系原则

1. Asset 与 Instrument 必须分开建模：资产说明「是什么标的」，权益结构说明「投资者取得什么权利」。
2. 一个 Asset 可以关联多个 Instrument；不同权益结构不得因引用同一 Asset 而自动合并成同一种权利。
3. 权益结构可以按清晰的权利范围拆分，并可在发行方案中独立引用；具体拆分单位、互斥规则及冲突检查应在权益结构详细设计中明确。
4. Project 是系统生成/关联的业务管理容器，不要求企业为每个发行步骤重复创建项目。
5. Offering 是具体发行轮次及其参数配置，不等同于 Project。一个 Project 可以组织相关发行安排；具体一对多数量限制及自动生成触发点以 R2 后续详细设计为准。
6. Token 数量、Token 单价、权益容量及其映射比例是相关但不同的业务数据，不得用其中一个字段替代其他字段。
7. 文件应关联具体业务对象和版本；文件版本更新不能静默覆盖历史发行时点实际引用的文件版本。

### 3.3 关系示意

Asset（底层资产）
→ 一个或多个 Instrument（权益结构）
→ 系统自动创建/关联 Project（项目管理容器）
→ 一个或多个 Offering（具体发行方案/发行轮次）
→ 按明确映射规则生成或分配 Token（链上凭证）

上述关系是产品对象关系说明，不等于已冻结数据库表结构、API、合约标准或所有对象的最终基数约束。

## 4. Issuer SaaS MVP 导航

### 4.1 导航结构

一级导航：**资产与发行**

二级导航按以下顺序直接展示，不增加第三级导航：

1. 资产管理（承接原资产列表）
2. 权益结构
3. 项目管理（承接原发行项目）
4. 发行方案
5. 发行准备

MVP 不在该导航下增加独立「文件中心」。文件能力嵌入对应业务页面。

### 4.2 各入口职责

| 二级入口 | 核心职责 | 不承担的职责 |
|---|---|---|
| 资产管理 | 创建、列表、详情、编辑和维护资产档案；按资产类型加载独立模板；管理权属与相关资料。 | 不直接配置某一轮发行的价格、发行数量或认购窗口。 |
| 权益结构 | 定义资产对应的法律/经济权利、权益范围、计量单位、可发行容量及 Token 映射基础。 | 不代替具体发行方案配置销售窗口、投资者限购或本轮发行价格。 |
| 项目管理 | 查看系统生成/关联的项目、资产和权益结构关系、发行方案轮次、整体状态和待处理事项。 | 不要求企业重复手动创建 Project；不复制 Offering 的详细配置表单。 |
| 发行方案 | 创建和维护某一具体发行轮次，配置发行数量、Token 数量/映射、价格、币种、认购窗口、限额及披露等。 | 不作为项目整体状态的唯一管理页面；不取代发行前最终准备检查。 |
| 发行准备 | 汇总本轮发行的所有必要信息，进行完整性和条件检查、投资者页面预览、企业声明及最终确认。 | 不取代法律意见、监管批准、真实资金到账、法定登记或真实链上执行的权威事实。 |

## 5. MVP 关键业务流程

### 5.1 资产准备

1. 企业进入资产管理。
2. 选择当前 MVP 可用的房地产模板。
3. 填写资产基础信息及模板要求的资料。
4. 上传权属、法律及其他必要证明文件，并关联到对应资产。
5. 保存草稿，检查必填、选填、条件必填及格式要求。
6. 完成资产档案后，进入权益结构配置。

字段级规则必须清晰区分：
- 必填：缺失时不能保存或提交相应步骤。
- 选填：允许留空，不影响当前步骤完成。
- 条件必填：满足特定资产情况、权利安排或发行选择时才要求填写。
- 自动计算：由系统根据已录入数据计算，并展示计算依据或关联字段；用户不得把自动计算结果误认为已获得外部核验。

### 5.2 权益结构配置

1. 从已有资产进入权益结构。
2. 定义投资者取得的权利、适用范围、计量单位、期限、限制及有效法律文件。
3. 设定权益容量或可发行上限。
4. 明确该权益结构与 Token 数量、Token 单位及映射比例的关系。
5. 保存并在后续发行方案中独立引用。

不同权益结构的单位和权利不可直接混加。房地产底层资产并不自动意味着投资者获得房地产所有权；投资者具体取得什么权利，应以权益结构及对应有效文件为准。

### 5.3 项目与发行方案

1. 当资产及权益结构进入发行流程时，系统自动创建或关联 Project。
2. 项目管理展示项目与资产、权益结构、发行方案的关系及总体进度。
3. 企业在发行方案中配置一轮具体发行。
4. 发行方案必须展示所引用权益池的剩余可发行额度及本轮最大可发行数量。
5. 发行数量、Token 数量、Token 单价、权益容量、Token 映射比例应分别展示和校验，不得混为一个数量字段。

### 5.4 发行准备与确认

发行准备作为发行前最终准备入口，至少围绕以下方面组织检查：

- 资产档案及必要资料是否完整；
- 权益结构及其法律/经济权利是否明确；
- 权益容量是否足以覆盖本轮发行；
- 发行数量、Token 数量、Token 单价及映射关系是否一致；
- 认购币种、认购窗口、投资者限额和资格条件是否完整；
- 投资者展示页面及披露文件是否可预览；
- 必要法律文件、企业声明和版本引用是否完整；
- 当前环境属于 Sandbox 还是具备生产准入条件的 Standard 环境。

企业完成最终确认后，系统才允许进入相应发布路径。Free Sandbox 的模拟发布不得产生真实资金交易、真实链上发行或真实投资者权益；Standard 订阅也不单独构成真实发行许可，仍需满足发行方 KYB、具体发行条件、合法外部主体及原有生产 Gate。

## 6. 权益容量与 Token 映射的产品要求

### 6.1 必须分开表达的数量

- 权益结构定义的总容量/授权上限；
- 已被既有发行或其他有效安排占用的数量；
- 已预留但尚未完成的数量（如适用）；
- 当前剩余可发行额度；
- 本轮发行数量；
- 本轮 Token 数量；
- Token 单位价格；
- 权益单位与 Token 单位之间的映射比例。

### 6.2 用户已明确要求的页面表现

- 发行方案必须显示权益池剩余可发行额度。
- 发行方案必须显示本轮最大可发行量，且不得超过可用权益容量。
- Token 数量和价格不得隐藏在单一发行总量字段中。
- Token 与权益结构之间必须有明确映射关系；不得默认所有资产或权益都采用 1:1 映射。
- 当剩余可发行额度不足时，页面必须清楚显示当前可用余量及无法继续配置的原因。

### 6.3 仍需后续确认的容量细则

现有历史参考材料中出现过 Total、Reserved、Tokenized、Consumed、Available 等容量口径，以及发行预留、失败/关闭释放未使用预留、并发预留冲突提示等规则。这些可作为后续设计的参考，但本文件不把它们全部视为本轮新 MVP 的最终字段或状态冻结。

R2 后续详细设计必须明确：
- 容量口径及计算公式；
- 已发行、已预留、已消耗和已承诺数量之间的关系；
- 发行失败、取消、暂停或关闭时如何释放或保留额度；
- 多个 Offering 同时配置时的并发与额度冲突处理；
- Token 精度、最小单位及映射比例的边界；
- 已生效权利不得因后台容量调整而被静默抹除。

## 7. 文件、版本及投资者披露

1. 文件上传必须是真实文件上传，不以名称、备注或外部链接替代文件本体。
2. 文件必须能关联 Asset、Instrument、Project、Offering 或发行准备中的具体事项。
3. 文件更新应形成新版本，保留历史版本及其创建时间、来源、适用业务对象和引用关系。
4. 需要区分内部工作资料与可向投资者展示/披露的文件；投资者可见性应由明确的披露设置控制。
5. 发行准备应展示本轮实际引用的文件版本，避免文件后来更新后改变历史发行所依据的材料。
6. 文件是否真实、有效、完整或具有法律效力，不由上传动作或系统文件摘要自动证明。

## 8. 异常与边界原则

| 场景 | 产品行为要求 |
|---|---|
| 必填资料缺失 | 标记具体字段与所属步骤，阻止对应提交，不只显示笼统错误。 |
| 条件必填未满足 | 解释触发条件及需要补充的资料。 |
| 文件上传失败 | 保留用户已填写的其他内容，明确失败文件及重试入口。 |
| 文件版本更新 | 新版本不得覆盖历史发行实际引用的旧版本。 |
| 权益容量不足 | 显示剩余额度、最大可发行量及阻断原因。 |
| Token 映射不一致 | 阻止发行准备通过，展示权益单位、Token 单位及差异。 |
| 项目自动关联失败 | 显示异常并保留原业务对象，不要求用户盲目重复创建。 |
| 发行准备未通过 | 展示未完成项、阻断级别和返回修复入口。 |
| Sandbox / Standard 不匹配 | 明确模拟与真实生产边界，不允许通过 UI 状态伪造真实执行结果。 |
| 外部 Provider / Signer / 链上执行 Unknown | 查询原始业务 Intent 与外部权威结果，不盲目重复执行。 |

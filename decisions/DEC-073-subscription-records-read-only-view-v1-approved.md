# DEC-073｜V1 认购记录与认购订单入口分工及 UI-Ready 收口

> **日期：2026-11-11**  
> **状态：V1 企业 SaaS 产品/UI 规则收口**  
> **决策依据：用户授权产品负责人独立完成各模块 MVP 闭环，并允许在详细设计中为易用性适度精简页面组织。**  
> **适用范围：Issuer 企业 SaaS「资产与发行 → 认购记录」。**

## 1. 背景

当前企业 SaaS 同时保留：
- 「资产与发行 → 认购记录」：跨资产、跨 Offering 查询；
- 「投资者与认购 → 认购订单」：订单全生命周期管理。

两个入口名称相近，但业务目的不同。若都展示所有状态、提供相同操作，会造成导航重复、状态重复和用户理解成本。

## 2. 决策

### 2.1 资产与发行 → 认购记录

定位为**已完成认购的跨资产历史查询视图**：

- 仅显示真实付款已确认且对应 Token 已真实交付的认购订单。
- 以原认购订单编号作为唯一记录引用，不新建第二套认购记录主账。
- 支持跨 Asset、跨 Offering 查询、筛选、查看详情和受控导出。
- 页面只读，不提供创建、取消、改价、手工确认付款、手工配售、Mint、退款或改写登记的操作。
- 法定登记状态单独展示；认购完成不自动代表法定持有人登记完成。
- 投资者信息按 DEC-069 最小必要脱敏展示。

### 2.2 投资者与认购 → 认购订单

定位为**认购订单全生命周期工作台**：

- 包含待付款、支付核对中、付款已确认待交付、已完成、异常、退款处理中等订单状态。
- 承载订单状态跟踪和进入资金、配售、Token 等责任模块的操作入口。
- 其完整字段、详情、异常和允许操作在后续「认购订单」模块独立完成 UI-Ready 设计。
- 两个入口复用同一订单编号、订单快照和权威状态，不复制订单主账。

### 2.3 已完成认购的定义

- 只有**真实支付已确认 + Token 交付已确认**，才将认购订单显示为「已完成」并纳入认购记录。
- KYC 通过、订单创建、钱包授权、交易提交或单独付款成功均不足以单独认定认购完成。
- 法定配售/登记、Token 交付、企业资金结算分别保留各自权威事实；法定登记或企业结算状态在认购记录中独立展示，不合并成一个成功状态。
- Payment Unknown、Token Delivery Pending/Failed 或对账无法确认的订单不得进入已完成记录。

## 3. 页面与隐私规则

- 认购记录列表显示订单编号、脱敏投资者引用编号、Asset、Offering、已交付 Token 份数、订单成立时单价 U、订单金额 U、完成时间及法定登记状态。
- 详情分别展示订单快照、脱敏投资者信息、付款确认、Token 交付和法定登记。
- 不展示或导出完整证件号码、原始 KYC 文件/报告、完整联系方式、完整投资者钱包地址或其他 Issuer 的资料。
- 支持按订单编号、平台投资者引用编号、Asset、Offering、完成时间和法定登记状态查询；默认按完成时间倒序。
- 导出仅限当前授权范围和脱敏字段，并记录审计。
- Free 新企业不展示模拟认购记录；Standard 降级 Free 后保留历史真实记录只读。

## 4. 权威来源与责任边界

| 事实 | 权威责任 |
|---|---|
| 认购订单与订单快照 | 认购管理 |
| 投资者脱敏引用与 KYC 状态 | 平台统一 KYC / 投资者身份管理 |
| 真实付款与退款 | 资金与结算 |
| 配售及法定登记 | 配售与权威登记 |
| Token Mint/交付 | Token 管理 |
| Offering 条款及固定版本 | 资产与发行 / Offering |

认购记录只聚合并展示可信事实，不创建第二套订单、资金、配售、登记或 Token 主账。

## 6. 不在本决策范围内

- 不改变九个 Issuer 一级导航和既有二级入口名称。
- 不重新设计「投资者与认购 → 认购订单」完整订单工作台。
- 不修改 193 项正式功能 ID、首次交付版本归属或 Frozen。
- 不授权真实支付、退款、资金托管、Signer、Mint、合约部署或生产发行。
- 不修改历史 DEC/SCOPE 原文，不关闭 X-01～X-13；PR #6 不变，PR #8 保持 Draft / Open / Unmerged。

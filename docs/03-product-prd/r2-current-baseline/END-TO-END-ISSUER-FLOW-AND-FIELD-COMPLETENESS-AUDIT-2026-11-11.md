# RWA SaaS V1｜企业注册至发行后管理端到端流程与字段完整性审计

> 审计日期：2026-11-11  
> 状态：**进行中（初轮证据核对与页面字段补缺已完成；全链路场景矩阵及重大决策门尚未收口）**  
> 范围：Issuer 企业 SaaS V1 及其与投资者端/外部服务之间的必要业务数据衔接；不设计 V 投资者前台、M 统一投资端或 P 平台运营后台页面。  
> 维护分支：docs/r2-current-product-baseline；PR #8 保持 Draft / Open / Unmerged。  
> 说明：本报告不代表源码、API、真实 Provider/Signer、真实资金、法定登记、合约部署或 UAT 已完成。

## 1. 审计目标

核验真实企业从 SaaS 注册到成功发行、投资者购买、付款、配售、持仓和发行后管理的业务路径，判断现有产品设计是否具备：
- 完整页面与唯一责任；
- 完整字段、控件、校验和数据来源；
- 对象、版本、数量、金额和状态在模块间正确传递；
- 每一步明确前置条件、成功结果和唯一下一步；
- 失败、超时、重复、Unknown、部分成功及状态冲突的处理；
- Free/Standard、KYB、法律、资金、Token 与生产准入边界。

本轮不重新逐页重写 PRD；以当前权威专项规格为依据，发现缺项直接修正普通字段/交互，重大商业、法律、资金、Token 或生产权限决策单独提交用户。

## 2. 审计方法

按实际用户旅程而非导航顺序审计：
1. 企业账号与企业主体；
2. 企业 KYB、Free/Standard、钱包；
3. Asset、Instrument、Offering；
4. 投资者门户展示及 KYC 结果回传；
5. 认购报价、签署、订单；
6. OP Mainnet USDT 付款、到账核验、FinalMatched；
7. 容量、配售、法定登记；
8. Token Mint/交付、持仓与锁仓；
9. 收益/本息、领取支付、到期/退出/清退；
10. 降级、异常和存续义务保护。

每个环节核对「输入字段 → 权威来源 → 输出对象/状态 → 下一模块消费字段 → 异常回退路径」。

## 6. 本轮已发现并直接修正的普通字段缺口

### E2E-F01｜Offering 缺少已批准的单投资者累计最高认购金额

**发现：** 历史 R2-04-03 R06 已批准「当前 Offering 下的累计最高认购金额」选项；认购额度按同一投资者在当前 Offering 下的有效订单/预留、已付款待配售和已确认配售金额累计。只有取消、过期或退款等释放条件得到权威确认后才释放；Unknown 不释放。最新 U02-09 曾错误写成不设置投资者累计认购限额。

**修正：**
- 恢复「单个投资者本期累计最高认购金额 U」选填字段；
- 当前 Tenant + Offering + 本企业投资者引用编号为累计范围；不跨 Offering、Issuer 或 V/M 账户合并；
- 同一订单状态迁移只累计一次；有效订单/预留、已付款待配售、已确认配售均继续占用；
- 只有权威确认取消/过期/退款等释放条件后才释放；Unknown、付款待核、退款待核和预留待核均不释放；
- U02-12 固定保存上限、历史已占用、本单计入及剩余额度摘要，不披露其他投资者订单。

文件：[U02-09 Offering](U02-09-OFFERING-MODULE-UI-READY-CLOSEOUT-2026-11-11.md)、[U02-12 认购订单](U02-12-SUBSCRIPTION-ORDERS-UI-READY-CLOSEOUT-2026-11-11.md)。

### E2E-F02｜付款来源地址未在到账详情明确展示

**发现：** 资金模块已有交易哈希、目标地址和金额等字段，退款规则也明确原始付款地址不必然等于退款受益人/退款目标，但到账详情没有明确列出链上发送方/付款来源地址。

**修正：**
- 增加链上发送方地址（from address），只读记录；
- 默认缩略展示，完整地址受权查看；
- 增加与投资者已验证钱包的匹配状态；
- 不因订单关联自动认定发送地址属于投资者本人；
- 付款来源地址、投资者账户、Token 接收钱包、合法持有人和退款目标继续分离。

文件：[U02-14 资金与结算](U02-14-FUNDS-AND-SETTLEMENT-UI-READY-CLOSEOUT-2026-11-11.md)、[U02-12 认购订单](U02-12-SUBSCRIPTION-ORDERS-UI-READY-CLOSEOUT-2026-11-11.md)。

## 7. 需用户决策的重大业务缺口（暂不擅自扩展）

### E2E-C01｜持有人转让未纳入 V1 是已批准边界，不属于缺项

经核对 DEC-009、后续补充决策 DEC-011 及 DEC-058：
- V1 交易能力仅支持一级发行认购；
- V1 不提供投资者之间的受控转让申请、受让资格办理、转让审批、交割、法定登记迁移或 Token 转移产品化流程；
- 不建设公开二级市场、C2C、订单簿、撮合或强制转账；
- V1 仍必须保留依法需要的 Token 转让限制/许可控制，以及对非预期 Transfer 事件的观察、告警、登记核对和审计；
- 受控转让工作流明确后置 V2。

**结论：** 当前 U02-13 只读查看合法转让结果、Token 模块观察 Transfer 事件的设计符合 V1 边界，不应新增 V1 转让申请页面或工作流。此项从「待补缺口」移为「已确认排除项」。

### E2E-D01｜投资者支付目标与最终收款路径属于独立生产决策门

**已核实的现行边界：**
- V1 投资者支付网络/资产固定为 OP Mainnet · USDT；
- 每个 Offering 由企业选择一个有效的最终结算收款钱包；
- 真实支付目标可按最终合法资金安排，采用受权收款合约、企业获权收款钱包或适格外部收款方；
- 最终结算收款钱包不等于投资者付款目标；资金 FinalMatched 后才进入配售等后续流程。

此前「支付到 Offering/Token 合约地址」属于推荐方向，没有检索到用户明确批准其为唯一强制路径。当前文档保留经法律/资金/生产准入确认后的适用收款路径，属于正确的开放决策门，不是缺少页面字段。不得擅自锁定合约地址，也不得让 SaaS 默认托管客户资金。

### E2E-D02｜投资者钱包与投资者身份的关联来源

Token 交付要求引用投资者已核验的 Token 接收钱包；付款事件另有链上发送方地址；法定持有人也可能与投资者账户不同。投资者端钱包绑定/签名验证页面不属于本轮设计，需在跨端数据契约中明确：
- 投资者账户与已验证钱包的关联及有效期；
- 付款来源地址是否匹配该账户授权钱包（不匹配不自动拒绝真实付款，但必须核对）；
- Token 接收钱包由谁确认、如何验证和变更；
- 法定持有人与投资者账户不一致时的合法映射依据。

### E2E-D03｜单个投资者累计认购上限的历史口径冲突（已解决）

已从此前用户批准记录核实：R2-04-03 R06 已明确批准可选的「当前 Offering 下的累计最高认购金额」，且 KYC 简化后仍保留；没有检索到后续取消或覆盖该规则的决策。

因此本次已恢复至 U02-09，并在 U02-12 保存订单时额度快照。该项不属于新增功能，也不构成投资者资格分级。

## 8. 明确不作为 Issuer 页面缺陷的外部生产门

以下是产品设计已设置守卫，但真实执行能力尚未获准/验证的独立事项：
- 真实 KYB/KYC Provider、MPC 钱包 Provider；
- 投资者付款目标/收款合约及其合法主体；
- 资金托管、退款、募集款释放与划拨责任方；
- 法定登记主体与登记回执；
- Token 标准、网络、合约模板、安全审计和链最终性阈值；
- Signer、密钥托管和生产执行授权；
- 各 Instrument/法域适用的法律文件、销售资格和披露要求。

不能把 Provider Connected、KYB 通过、Standard 订阅有效或 UI 资料 Ready 等同于真实生产准入。

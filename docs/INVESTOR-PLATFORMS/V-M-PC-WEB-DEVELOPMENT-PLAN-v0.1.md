## 一、三项最终交付

| 交付物 | 必须满足 | 明确不包含 |
|---|---|---|
| ① V/M 共用 PC Web 原型 | 可在浏览器直接打开，V 企业品牌/M 市场品牌都有首页、列表、详情、企业资料、账户、认购、订单、持仓、收益、消息、工单等实际可交互页面；UI 统一、符合桌面投资网站习惯 | 手机 APP 底栏、H5 移动适配、部署真实网站 |
| ② 完整模拟业务闭环 | 在页面内模拟邮箱 OTP、首次账户生成、自动 MPC 钱包、KYC、认购、USDT 合约付款结果、配售、登记、Token、收益、本金、异常工单；场景可一键填充/重置；明确标记为 Mock | 真实 KYC/MPC、签名、链上支付、API/数据库、智能合约开发 |
| ③ 最终产品 PRD（交接开发） | 根据**已批准设计 + 实际原型**，逐页说明页面、字段、按钮、文案、跳转、校验、状态、异常、V/M 差异、投资者操作步骤、跨端业务责任及验收场景；提供原型路由、截图和 GitHub 源码引用 | 接口定义、API Schema、数据库设计、后端服务拆分、合约代码和生产运维方案 |

**产品说明可以描述业务事实要求**（例如“只在实际付款核实后展示已付款”“付款失败后的退款需遵循合法条件”“合约/后台由工程师实现”），但**不输出或替工程师决定**接口协议、表结构、签名方式、链上重试实现和 Provider 集成方案。遇到后端不确定性，记录为“工程实现/法务待决”即可，不阻塞前端 Mock 页面开发。

## 二、工程和复用方式

- 建议新增 `apps/investor-portal`（或先由 Codex 结合现有仓库给出合理路径），沿用当前 React + TypeScript + Vite 技术风格；纯前端 Mock/本地演示状态，不引入真实 SDK/资金能力。
- **同一套页面和组件服务 V/M**：OfferingCard、OfferingList、AssetDetail、IssuerProfile、Account/KYC/Wallet、SubscribeSteps、Order、Holding、Distribution、Notification、SupportTicket；两套品牌皮肤和渠道筛选，不复制两份业务页面。
- V 首页：左上角企业 Logo/名称，主要展示 RWA 介绍和本企业可见资产；M 首页：跨 Issuer 的资产发现和分类。**V/M 资产详情与发行企业资料页同结构**，两端都可以点击企业进入资料页。
- PC 顶部横向导航；我的账户内允许局部左侧菜单，我的投资内为页签。不做移动 APP 式底栏。
- 原型渠道通过**演示配置/演示路由**区分企业 V 与市场 M 即可；不要求现在实现真实域名识别、后台权限或服务端登录。Mock 标识明确，防止与真实业务混淆。
- 不读写 `apps/issuer` 的 localStorage 当作主账；前端可以建立自己的模拟 Issuer/Offering/Order/Holder/Distribution 关系，保证 V/M 的同一 Mock Offering 和容量一致。
- 单独 Mock 控制台：一键载入住宅收益参与、单笔借款债权、普通股权、其余三类房地产样例；可切换账户/KYC/钱包/发行/付款/登记/收益/工单状态并重置。**正式页面不常驻不必要的 Mock 控制按钮**。

## 四、典型 Mock 场景（仅前端，统一状态关系）

| 场景 | 需要演示的真实页面行为 |
|---|---|
| 住宅收益参与权 | 住宅资产字段、合同参与比例、净收益分配、Record Date、收益记录；资产估值/发行额/实际收益各自独立 |
| 单笔企业借款 | 固定年利率 12%、按月付息、到期还本；投资者页面分开显示利息与本金 |
| 非上市普通股权 | 股权对应法律权利、合法股息决议有/无、非固定回报 |
| 写字楼/商铺/工业园仓储 | 各自差异字段、没有实际租金时不虚构年化收益 |
| V 可见、M 未通过 Listing | V 正常展示，M 不展示；M 通过模拟审核后上架展示 |
| 同邮箱 V/M 各自登录 | 账户/默认钱包/历史订单互不自动合并 |
| MPC 处理中/失败、KYC 待补件 | 原型页面有状态与下一步，可通过 Mock 控制台切换，不出现“真实分配成功” |
| 付款失败、回滚、待核、已入账后交付异常 | 交易进度分态；不伪造退款；人工工单可演示协作 |
| 已登记未交付 Token / 已交付但登记待核 | 持仓分开展示真实法律记录与链上交付状态 |
| 股息无决议、收益参与无可分配收益、债权部分还本 | 不产生错误收益；债权本金单独累计 |

演示数字只用于测试；“1 U = 8 CNY”若使用，必须标注为历史测试样例，绝不作为生产汇率。所有模拟支付按钮、钱包地址和交易状态显著标注“Mock/演示”，不会触发任何实际网络资金操作。

## 五、统一的 UI-Ready 原型验收标准

每个页面做到：PC 视觉布局可用、中文文案准确、必需字段/条件字段与校验齐全、有明确主要按钮与跳转、有 Loading/Empty/Invalid/Pending/Success/Failed/Unknown 的适用状态、能够实际点击操作、无越权出现另一渠道资产/私有记录。原型允许通过前端 Mock 模拟真实业务，但流程状态需与产品 PRD 一致。

验收不只看 Build。Codex 每批提交：变更文件与页面清单、实际运行测试命令和结果、关键 Chrome/Playwright 浏览器截图、操作步骤、正常与异常路径记录、仍未完成问题及下一 DEV 依赖。无环境/未跑的标记 NOT EXECUTED；用户人工验收关键视觉与流程。

## 六、最终《交付开发产品 PRD》必须包含

1. 产品总体介绍、V/M 职责区别、PC 目标和 V1 产品边界。
2. 两端导航、路由/页面索引，以及共享页面/专有页面的实际对应表。
3. **逐页**：功能目的、页面结构、展示字段（必填/可选/只读/动态）、控件、校验、主次按钮、弹窗、文案、跳转、当前状态、异常和下一步；引用实际截图/原型路由。
4. 六资产/三权益模板可展示字段矩阵、动态收益逻辑、合法披露和风险提示规则。
5. 登录、KYC、MPC、自有钱包、认购、订单、持仓、收益、本金、工单、通知全业务路径的**产品级**状态机；明确“这一步用户看到什么、能做什么、谁负责后续”。
6. V/M 数据权限边界，V→Issuer/P 工单协作职责、M Listing 审核上架与历史权益保留。
7. UI 文案、空态/错误提示、安全与隐私可见性、模拟与生产不同点。
8. 研发人员核对的验收用例及原型操作手册；每页对照 GitHub 原型文件及路由。
9. **工程待实现事项**统一简述成职责/业务结果要求，例如 KYC 服务返回状态、合约付款有权威回执；**不编写** API/数据库/合约或后端模块技术设计。

只有经过最终原型逐页审查，才能将“UI-Ready 设计稿”标为“与可运行原型一致的开发交接 PRD”。之前六批已通过的产品规则不因为前端演示而无审批擅自改变。
